# Everything Claude Code / ECC (affaan-m/ECC) — DeepWiki Knowledge Distillation

## What it is

Everything Claude Code (ECC) is a harness-native "operator system" for production-grade agentic engineering — originally an Anthropic Hackathon winner, grown into a suite of 61 agents, 246 skills, and 76 slash commands that provide a reusable substrate for AI-driven engineering across multiple platforms. It is explicitly not just a config-file collection: it bridges natural-language developer intent to code execution via structured skills, "instincts" (continuously-learned patterns), and automated safety hooks.

Core value props (as stated in the wiki): multi-harness portability (Claude Code, Codex, Cursor, OpenCode, Gemini, Zed, terminal-only); production-ready specialized agents (TDD, security review, architecture planning, build-error resolution); continuous learning that extracts patterns from developer sessions into reusable project-specific "instincts"; and integrated security scanning (AgentShield) plus automated quality gates.

Distribution: installable as a Claude Code plugin via marketplace (`/plugin marketplace add https://github.com/affaan-m/ECC` then `/plugin install ecc@ecc`), via a selective-install CLI (`npx ecc-install --profile core`) for non-Claude harnesses, or via direct git clone + `install.sh`/`install.ps1`. A parallel, in-progress Rust "control plane" (`ecc2/`) is rewriting session management, orchestration, and observability outside the Node.js event loop.

## Architecture

**Five core entity types**, all cross-referencing each other: **Agents** (`agents/*.md`, autonomous role-scoped assistants with restricted tool access and a model tier), **Skills** (`skills/*/SKILL.md`, atomic reusable "how-to" workflow knowledge — the canonical/preferred surface going forward), **Hooks** (`hooks/hooks.json` + `scripts/hooks/*.js`, event-driven scripts firing on lifecycle events like `PreToolUse`/`PostToolUse`/`SessionStart`/`Stop`), **Rules** (`rules/`, passive "must-follow" constraints layered as Common + per-language overrides, distinct from Skills' "how-to" framing), and **Commands** (`commands/*.md`, slash-entry human-facing triggers that ECC is deliberately migrating to treat as thin legacy shims over Agents/Skills rather than primary logic).

**Manifest-driven modular installation**: `manifests/install-modules.json` defines the smallest deployable units (module kinds: `rules`, `agents`, `commands`, `hooks`, `platform`, `orchestration`, `skills`, `docs`), validated against `schemas/install-modules.schema.json`. `manifests/install-components.json` groups modules into logical "families" (`baseline`, `language`, `framework`, `capability`, `agent`, `skill`) that users actually select — the system auto-generates "synthetic" components for any skill-directory not explicitly declared. Install profiles (`minimal`, `core`, `full`) are pre-defined module bundles. The install pipeline is two-stage: **Resolution** (`createInstallPlanFromRequest` in `scripts/lib/install/runtime.js` turns a profile/component/legacy-flag request into a deterministic `InstallPlan`, mapping legacy raw language names to canonical component IDs) then **Execution** (`applyInstallPlan` in `scripts/lib/install/apply.js`: create target directories, deep-merge JSON files like `mcp.json`/`hooks.json` rather than overwrite, replace `${CLAUDE_PLUGIN_ROOT}` placeholders with the real path, record everything in `install-state.json`).

**Cross-harness portability via Target Adapters**: each harness gets a dedicated adapter (`scripts/lib/install-targets/{claude-home,claude-project,cursor-project,zed-project,antigravity-project}.js`) resolved through a central registry. Adapters handle structural differences — e.g. Cursor doesn't support nested rule directories, so `cursor-project.js`'s `createFlatRuleOperations` flattens `rules/typescript/testing.md` into `.cursor/rules/typescript-testing.mdc`. A formal compliance matrix classifies each harness as **Native** (direct plugin/installer support), **Adapter-backed** (thin event-translation layer, e.g. OpenCode/Cursor/Zed), **Instruction-backed** (no runtime hook API, so logic is pushed into `AGENTS.md`-style instructions, e.g. Codex), or **Reference-only** (external design comparison, no adapter). `isForeignPlatformPath` guards against one harness's files leaking into another's directory. CI enforces portability via `validate-hooks.js` (standardizes hook event names across harnesses, validates any inline `node -e` JS with `vm.Script`), `validate-commands.js` (checks commands don't reference nonexistent agents/skills after projection), `check-unicode-safety.js` (scans all projected Markdown/TOML/JS for "tag smuggling" prompt-injection via zero-width/deprecated Unicode), and `catalog.js` (verifies README-advertised agent/skill/command counts match the actual filesystem across all localizations).

**ECC 2.0 Rust control plane (`ecc2/`)**: a `tokio`+`ratatui` Rust rewrite of session orchestration, decoupled from the JS runtime. `Session` structs move through a state machine `Pending → Running → {Completed, Failed, Stopped}`; `session/runtime.rs` captures agent stdout/stderr into a bounded ring buffer (`OUTPUT_BUFFER_LIMIT = 1000`) and broadcasts events via `tokio::sync::broadcast`; a dedicated `DbWriter` thread handles SQLite writes asynchronously so persistence never blocks the runtime. A background daemon (`session/daemon.rs`) does crash recovery (`resume_crashed_sessions` reclassifies `Running` sessions whose PID is dead as `Failed`), heartbeat enforcement for stale sessions, auto-dispatch of delegate sub-agents when a lead agent requests a handoff, backlog rebalancing across lead teams, and worktree pruning/auto-merge. Git-worktree isolation (`worktree/mod.rs`) gives each session its own branch + directory so parallel agents don't collide, with shared-dependency-directory syncing (e.g. symlinking `node_modules`) to avoid per-worktree reinstall cost. A TUI dashboard (`tui/dashboard.rs`) exposes five panes: Sessions, Output, Metrics (tokens/cost/tool-call frequency), Board (orchestration/team status), Log. Observability includes a 4-axis tool-call risk score (base tool risk + file sensitivity + blast radius + irreversibility, composited to 0.0-1.0) fed by a JS-side `session-activity-tracker.js` hook that captures per-tool activity/diffs and redacts secrets before persisting.

**Session management & persistence (JS side, current production path)**: session summaries persist to `~/.claude/session-data/` (canonical) with a legacy fallback at `~/.claude/sessions/`; filenames follow `YYYY-MM-DD-[short-id]-session.tmp`. `session-end.js` runs on the `Stop` hook, parses the JSONL transcript to extract the last 10 user messages, tools used, up to 30 modified file paths, current git branch, and worktree path, wraps it in `<!-- ECC:SUMMARY:START -->` markers, and writes/updates the `.tmp` file. `session-start.js` on next launch searches for matching session files, applies a **worktree guard** (only injects summaries from sessions matching the current `process.cwd()`, explicitly to prevent cross-project "context leakage"), and emits the restored summary via stdout as an `additionalContext` JSON payload that Claude Code ingests directly. A `SessionStart` mode check (`startup` vs `resume`) prevents re-injecting a summary into a session that has already progressed. Retention: sessions older than 30 days (configurable via `ECC_SESSION_RETENTION_DAYS`) are pruned on `SessionStart`. Human-readable session aliases live in `~/.claude/session-aliases.json`, written with atomic temp-file-and-rename plus a `.bak` fallback to survive concurrent-write corruption.

**MCP server integration**: a curated `mcp-configs/mcp-servers.json` ships pre-tuned configs for 20+ servers (jira, github, firecrawl, supabase, memory, context7, evalview, longhand, etc.). `scripts/codex/merge-mcp-config.js` is package-manager-aware (matches `npx`/`pnpm dlx`/`bunx` to the detected environment) and merges these into per-harness config files using an **ADD-ONLY strategy** — it never overwrites a user's existing MCP server entry, only fills in ECC-recommended ones that are missing, and logs drift warnings when an existing config diverges meaningfully from the recommendation. A `mcp-health-check.js` `PreToolUse` hook intercepts any `mcp__`-prefixed tool call, probes HTTP-based servers for reachability, caches health state in `~/.claude/mcp-health-cache.json` (survives context compaction), applies exponential backoff on repeated failures to avoid fail-loops, and supports a fail-open mode (`ECC_MCP_HEALTH_FAIL_OPEN`) so a broken health check doesn't itself block tool execution.

## Key patterns & techniques

- **Skills-first migration with commands as shims**: ECC is deliberately moving new workflow logic into `skills/` rather than `commands/`, treating slash commands as thin legacy-compatibility entry points that ultimately delegate to an agent/skill. Worth noting as a pattern for any plugin ecosystem that started command-first and needs to consolidate logic into a reusable, non-duplicated layer.
- **Worktree-scoped context injection with an explicit leakage guard**: rather than naively restoring "the last session," `session-start.js` specifically checks that a candidate session's recorded `cwd` matches the current working directory before injecting it as context — a small but important guard against bleeding one project's history into an unrelated one when a user has many repos.
- **ADD-ONLY config merging for third-party-managed files**: `merge-mcp-config.js`'s never-overwrite-existing-entries strategy is a reusable pattern for any tool that needs to inject its own defaults into a config file the user also edits by hand — safe merge beats "regenerate and clobber."
- **Deterministic project identity via git-remote hashing**: `detect-project.sh` resolves a stable project ID by checking `CLAUDE_PROJECT_DIR` env var → normalized `git remote get-url origin` (credentials stripped) → `git rev-parse --show-toplevel` → final fallback to a "global" scope, then SHA-256-hashes to 12 characters — ensures the same repo on different machines/clones maps to the same learned-instinct bucket.
- **Throttled, confidence-scored background learning (Continuous Learning v2 / "instincts")**: a lightweight `observe.sh` hook fires on every `PreToolUse`/`PostToolUse` event but only signals a background observer agent every N observations (default 20, via a `.observer-signal-counter`) to avoid "signal storms." The observer agent itself runs on the cheapest model tier (Haiku), samples only the last 500 lines of the observations log (`tail`-based, not full-file), assigns confidence 0.5/0.7/0.85 based on occurrence-count buckets (3-5 / 6-10 / 11+), and is guarded by an `ANALYZING` re-entrancy lock plus a 60-second `ANALYSIS_COOLDOWN` and a 30-minute `IDLE_TIMEOUT_SECONDS` auto-exit. Instincts are stored as Markdown-with-YAML-frontmatter (`id`, `trigger`, `confidence`, `domain`, `source`, `scope`, `project_id`), isolated in a separate "Homunculus" directory (not under `.claude/`) specifically to dodge sensitive-path guards. A CLI (`instinct-cli.py`) supports `status`, `promote` (project → global scope), `evolve` (cluster atomic instincts into a full Skill/Agent), and `prune` (auto-delete pending instincts >30 days old). This whole design is a template for "cheap, throttled, self-limiting background pattern-mining from live tool-use logs" — worth reusing wherever an agent system wants to learn without burning tokens or risking runaway background cost.
- **Self-observation guard layering**: the observation hook has five separate checks (`CLAUDE_CODE_ENTRYPOINT`, `ECC_HOOK_PROFILE`, `agent_id`, etc.) specifically to prevent the learning system from observing and learning from its *own* background processes — a reminder that any meta/reflective tooling needs explicit guards against recursively watching itself.
- **4-axis composite risk scoring for tool calls** (ecc2): base tool risk + file sensitivity + blast radius + irreversibility combined into a single 0.0-1.0 score, rather than a binary allow/deny — gives downstream policy (hooks, dashboards, auto-approval thresholds) a tunable dial instead of a hard gate.
- **Layered hook dispatch with a single consolidated pre-bash entry point**: rather than registering many separate `PreToolUse` hooks for bash, ECC funnels quality/tmux-reminder/security checks through one `pre-bash-dispatcher.js`, and uses a `plugin-hook-bootstrap.js` specifically to resolve the correct plugin root path across differing installation layouts (global vs project vs marketplace-installed) before any hook logic runs.
- **Supply-chain IOC scanning as a maintained deny-list + persistence-pattern detector**: `scan-supply-chain-iocs.js` keeps a large, actively-updated `MALICIOUS_PACKAGE_VERSIONS` table (keyed to specific known-compromised npm versions from real incidents — e.g. a "TanStack campaign", a "Mini Shai-Hulud" campaign) and separately checks for known attacker persistence artifacts (a `gh-token-monitor` LaunchAgent/systemd service, a `~/.config/gh-token-monitor/token` dead-man-switch file, dropped payloads like `transformers.pyz`). This dual approach — version-pinned deny-list plus behavioral/artifact detection — is a reusable template for any org building its own supply-chain monitoring rather than relying solely on `npm audit`.
- **Hardened CI supply-chain watch**: a scheduled (every 6 hours) workflow runs `npm ci --ignore-scripts` (blocks lifecycle-script malware execution), `npm audit signatures` (registry integrity), advisory refresh from CISA/Socket/TanStack sources, then the full IOC sweep — with credential persistence disabled and read-only permissions, minimizing what a compromised dependency could do even if it ran during this specific job.

## Practical how-tos

- **Install as a Claude Code plugin**: `/plugin marketplace add https://github.com/affaan-m/ECC` then `/plugin install ecc@ecc`.
- **Install selectively for other harnesses**: `npx ecc-install --profile core` or `npx ecc-install --modules rules-core,framework-language --target cursor`.
- **Manual/full clone install**: `git clone https://github.com/affaan-m/ECC.git && cd ECC && npm install && ./install.sh --profile full` (Windows: `install.ps1`).
- **Verify an install**: `/plugin list ecc@ecc` to confirm the plugin loaded; run `/ecc:plan "add user auth"` (plugin install) or `/plan "add user auth"` (manual install) to test a command; inspect `install-state.json` (e.g. `~/.claude/ecc/install-state.json`) for active modules; run `node scripts/doctor.js` for an environment health check.
- **Define a new agent**: create `agents/<name>.md` with YAML frontmatter — `name`, `description` (the "activation energy" text the primary model uses to decide when to delegate), `tools` (allowlist, e.g. `["Read", "Write", "Bash", "Grep"]`), `model` (`haiku`/`sonnet`/`opus` tier).
- **Model routing recommendation** (from the wiki's own guidance): use `haiku` for exploration/file-searching (lowest cost), `sonnet` for general implementation (best balance), `opus` for architecture/deep reasoning.
- **Multi-agent orchestration setup**: `multi-*` commands (`/multi-plan`, `/multi-execute`) require `npx ccg-workflow` to initialize the `codeagent-wrapper` and prompt templates under `~/.claude/.ccg/`.
- **Building ECC 2.0 from source**: the `ecc2/` Rust control plane requires a Rust toolchain to build its background daemon and TUI dashboard — it's alpha/opt-in, not required for the standard JS-runtime install.
- **Standard agent orchestration flow** (Plan-Execute-Review, as recommended by the docs): invoke `planner` to break the task into phases and surface risks, then `tdd-guide` to write failing tests before minimal implementation, then `code-reviewer`/`security-reviewer` immediately after code changes — independent sub-tasks can be parallelized, often via separate git worktrees.
- **Sweep for supply-chain compromise manually**: `npm run security:ioc-scan`, `node scripts/ci/scan-supply-chain-iocs.js --home`, `npm ci --ignore-scripts`, `npm audit signatures`.

## Gotchas & caveats

- ECC explicitly warns against mixing legacy per-language install flags with modern profile flags in the same install invocation — `install-apply.js` throws rather than trying to reconcile the two argument styles.
- Cursor and other harnesses without nested-rule-directory support get *renamed and flattened* rule files (`.mdc` extension, flattened path with dashes) — if debugging "why doesn't my rule show up on Cursor," check the flattened output path rather than assuming the original `rules/` tree structure is mirrored.
- MCP config merging is deliberately conservative: it will never overwrite a server entry a user already configured, even if that entry is stale relative to ECC's recommendation — it only warns about drift. Don't expect an ECC update to "fix" a manually-edited MCP server config; it has to be done by hand or by deleting the entry so ECC will re-add its version.
- The continuous-learning observer's Homunculus directory is intentionally kept *outside* `.claude/` — any tooling that assumes all ECC state lives under the standard Claude config path will miss instinct data.
- Instinct confidence is a simple occurrence-count bucket (3-5 → 0.5, 6-10 → 0.7, 11+ → 0.85), not a statistically rigorous measure — treat "confidence" as "how many times we saw this pattern," not a calibrated probability.
- The MCP health-check cache and backoff state persist in `~/.claude/mcp-health-cache.json` specifically to survive context compaction — clearing that file resets backoff state, which could unmask a server that was correctly being backed off.
- `ECC_MCP_HEALTH_FAIL_OPEN` exists precisely because a broken health-check implementation must not itself become a hard blocker on tool execution — but that also means health-check bugs can silently degrade to "always allow" rather than surfacing loudly.
- The ecc2 Rust control plane is explicitly described as "next-generation"/alpha and requires a separate Rust toolchain build step — it is not yet the default production path; the JS hooks/session-manager system is what's actually running for most installs at the time of this wiki snapshot.
- The supply-chain IOC scanner's malicious-version dictionary is a point-in-time snapshot tied to specific known incidents (TanStack campaign, "Mini Shai-Hulud," etc.) — it protects against *known* compromised versions, not novel/zero-day supply-chain attacks; it needs to stay actively updated (the 6-hourly CI watch job's "Advisory Refresh" step from CISA/Socket/TanStack sources is the intended update mechanism) to remain useful.
- The `insaits-security-monitor.py` bridge requires the Node hook runner to shell out to a Python binary (`python3`/`python` discovery) — environments without Python available will not get this specific security-monitoring layer even though the rest of the Node-based hook pipeline runs fine.
