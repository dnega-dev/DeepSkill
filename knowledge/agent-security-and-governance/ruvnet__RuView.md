# ruvnet/RuView — Distilled Knowledge

## What it is

RuView is an edge AI perception system that uses WiFi Channel State Information (CSI) to detect human presence, pose, and vital signs without cameras, wearables, or internet connectivity. Commodity WiFi routers/ESP32-S3 nodes (~$9 each) are turned into contact-free sensing devices by analyzing how WiFi signals scatter off moving/breathing bodies, reconstructing 17-keypoint COCO pose with DensePose part segmentation, breathing rate (6-30 BPM), heart rate (40-120 BPM), presence/motion, and multi-person tracking through walls (Fresnel-zone geometry). Runs entirely on edge hardware with no cloud dependency. Originally a Python implementation (`archive/v1`), fully rewritten in Rust as `v2` (a Cargo workspace of crates). Although the system's domain is RF sensing rather than "AI agent governance" per se, its architecture is directly relevant to this batch: it implements a structured, ADR-driven privacy-and-trust control plane (BFLD), a tiered edge-compute privilege/sandbox model (WASM budget-guarded modules), and a distributed mesh-coordination protocol (TDM) — all patterns transferable to agentic infra governance.

## Architecture

**End-to-end data flow**: ESP32-S3 mesh nodes (Hardware Layer, capturing CSI at up to 100 Hz) -> UDP port 5005 (binary frame format, ADR-018) -> Rust backend `sensing-server` (Axum, HTTP :8080 / WebSocket :8765) -> signal processing crates (`wifi-densepose-signal`: Hampel filtering, BVP extraction, feature computation; `wifi-densepose-ruvector`: attention/min-cut/solver; `wifi-densepose-nn`: DensePose inference; `wifi-densepose-vitals`: Goertzel-based BR/HR) -> application layer (RuView Desktop via Tauri v2, Observatory Web UI via Three.js, MQTT publisher for Home Assistant). A separate Training layer (DataLoader for MM-Fi/Wi-Pose datasets, AETHER/MERIDIAN training pipelines) produces portable `.rvf` model containers consumed by the inference crate.

**TDM (Time Division Multiplexing) mesh protocol**: coordinates N ESP32 nodes into N×(N-1) directed bistatic links — each node transmits in its own dedicated time slot while all others receive, avoiding self-interference and maximizing spatial (360-degree) diversity for pose/vitals estimation. A full TDM cycle is ~50ms, yielding a 20Hz update rate (demonstrated with a 4-node example: 4 sequential 4ms TX/RX slots followed by a fusion window). Synchronization uses shared slot numbering/node counts loaded from NVS plus SyncBeacons or GPIO pulses from an aggregator node. Nodes inject deterministic Null Data Packets (NDPs) via `esp_wifi_80211_tx()` to elicit CSI responses without payload overhead. Channel hopping across non-overlapping channels (1/6/11, configurable dwell time, default 50ms) mitigates multipath fading; cross-channel phase alignment (correcting for local-oscillator rotation introduced by hops) is handled by a `NeumannSolver`. A rate limiter (50 Hz) plus 100ms `ENOMEM` backoff on UDP sends prevents lwIP buffer exhaustion during high-rate promiscuous capture.

**Mesh security hardening**: SyncBeacons can be authenticated with HMAC-SHA256 (4-byte monotonic nonce + 8-byte HMAC tag); CSI frames carry a SipHash-2-4 MAC over header and I/Q data for integrity; QUIC/TLS is available for encrypted transport in advanced/cross-site deployments. A QEMU-based swarm testing environment (`qemu_swarm.py`) simulates star/mesh/line/ring topologies with mock CSI generation and generated NVS partition images, allowing multi-node coordination logic to be validated entirely without physical hardware.

**Tiered edge intelligence** (progressive-enhancement pipeline on the node itself, configurable via NVS `edge_tier` key, single firmware binary supports all tiers): Tier 0 Raw Passthrough (no on-device processing, ~100 KB/s/node, ~500ms server RTT — full server-side flexibility); Tier 1 Signal Processing (phase unwrap, Welford running-variance per subcarrier without storing history, Top-K subcarrier selection by variance, XOR+RLE delta compression cutting bandwidth 30-70%, ~30KB RAM, 30-50 KB/s/node); Tier 2 Vital Signs (adds 2nd-order Butterworth bandpass filters for breathing 0.1-0.5Hz and heart rate 0.8-2.0Hz, zero-crossing BPM estimation, adaptive presence-detection threshold calibrated over ~60s of ambient noise, optional mmWave sensor fusion emitting a 48-byte fused packet with a 0-100 confidence score, <50ms on-device latency, only 32 bytes @ 1Hz over the wire — designed for battery-powered safety-critical deployments); Tier 3 WASM Modules (hot-loadable custom sensing logic, ~160KB/slot). The dual-core ESP32-S3 pipeline puts WiFi/radio capture on Core 0 (writing into a lock-free SPSC ring buffer) and DSP/sensing on Core 1 (consuming the ring buffer through the tiered pipeline) — a clean producer/consumer split that keeps radio interrupt handling from blocking signal processing.

**WASM sandbox with a budget guard (Tier 3)**: hot-swappable sensing logic runs inside a WASM3 interpreter in an isolated PSRAM arena, avoiding firmware reflashing for custom logic. Each module declares a `manifest_budget_us`; if a module's execution time exceeds its declared budget, the runtime terminates it — a hard resource-isolation mechanism preventing one untrusted/buggy module from starving the WiFi and DSP tasks of CPU. Modules interact with the host pipeline only through defined host-import functions (e.g. `host_csi_get_phase`, `host_csi_get_bpm_breathing`), i.e. a capability-scoped API surface rather than raw memory/hardware access.

**BFLD (Beamforming Feedback Layer for Detection) — the privacy control plane**: a dedicated Rust crate that processes 802.11ac/ax Beamforming Feedback Information (BFI) and CSI for occupancy/motion sensing while explicitly measuring and mitigating identity leakage, so that high-fidelity RF sensing does not become a persistent biometric without operator consent. It is structured around **three invariants enforced by the codebase itself, not by policy alone**: I1 — raw BFI never exits the node; I2 — identity embeddings live in RAM only, never on disk or over the network; I3 — cross-site identity correlation is cryptographically impossible via per-site keyed BLAKE3 hash rotation.

**Privacy Classes vs. Privacy Modes**: `PrivacyClass` (0 Raw — local-only research data including raw BFI matrices, network transmission never allowed, enforcing I1 structurally; 1 Derived — LAN-only research including identity embeddings and risk scores; 2 Anonymous — **production default**, aggregate sensing only, no identity data; 3 Restricted — care-home mode, Class 2 minus risk scores and signature hashes) describes what data *content* is present in a frame/event. `PrivacyMode` is the operator-facing posture (`RawResearch`, `PrivateHome`, `CareWithConsent`, `StrictNoIdentity`), and selecting a mode pins a target `PrivacyClass` and enforces specific `PrivacyAction` bits (e.g. `SuppressIdentity`, `DropRaw`). A `PrivacyModeRegistry` maintains the currently active mode plus a BLAKE3 hash-chained audit log of `PrivacyAttestationProof` objects — every mode change produces a new proof chained to the prior one, giving a tamper-evident witness chain of the system's privacy posture over time (directly analogous to a Merkle audit chain pattern, applied to privacy-configuration state rather than to access decisions).

**Identity protection mechanisms**: the 128-dimensional `IdentityEmbedding` (from the AETHER encoder) is stored in a `subtle::Zeroizing` ring buffer capped at 64 entries, and the type deliberately lacks a `Serialize` implementation — a type-system-level guarantee (not just a runtime check) that it can never be emitted over MQTT or written to disk, enforcing I2 at compile time. A `SignatureHasher` computes an `rf_signature_hash` using BLAKE3 in keyed mode, combining a 256-bit site salt (generated once on first boot, kept local) with the current Unix day as an epoch — forcing the derived biometric-like signature to rotate every 24 hours and making it cryptographically impossible to correlate a signature across sites or across days (enforcing I3). A `coherence_gate` module computes a composite `identity_risk_score` (separability × stability × consistency, estimating how "identifiable" the current RF environment is) and, depending on score and active mode, can `Allow`, `Reject`, or trigger a `Recalibrate` action; an optional `SoulMatchOracle` lets the gate bypass recalibration if a signal matches a known, explicitly consented signature.

**MQTT/Home Assistant integration gated by privacy class**: Class 0 (Raw) and Class 1 (Derived) events are *never* published to the public MQTT topic tree — the topic router itself enforces the privacy boundary, not just the application logic upstream of it. Presence/motion/person-count/confidence topics require class >= 2; the identity-risk topic requires class exactly 2 (Anonymous only — not exposed even in the less-restrictive-sounding Derived class, because that class already contains raw risk-scoring inputs that shouldn't be doubly exposed). Home Assistant auto-discovery (HA-DISCO) publishes JSON config payloads so HA creates entities automatically; a production `rumqttc`-based publisher supports MQTT Last Will and Testament for reliable "offline" availability markers.

**Real-time introspection tap (ADR-099)**: the standard pipeline emits window-buffered events every 500-1000ms, but a parallel low-latency tap (`IntrospectionState`) provides per-frame updates at ~33ms latency, using `midstreamer-attractor` (computes Lyapunov exponents to classify signal "regime" as Idle/Periodic/Transient/Chaotic) and `midstreamer-temporal-compare` (Dynamic Time Warping match against a `SignatureLibrary`) — a pattern of running two parallel processing paths at different latency/fidelity tradeoffs off the same validated input stream.

## Key patterns & techniques (transferable)

- **Structural (type-system / codebase) enforcement of privacy invariants, not just policy documentation**: `IdentityEmbedding` lacking `Serialize` is a compile-time guarantee it can't leak over the wire — a strictly stronger guarantee than "our privacy policy says we don't transmit this," directly applicable to any system handling sensitive derived data that must never leave a trust boundary.
- **Hash-chained attestation of *configuration/posture* state, not just access decisions**: chaining privacy-mode-change proofs (BLAKE3) the same way an audit log chains authorization decisions extends the "tamper-evident history" pattern to system configuration itself — useful for governance systems where "what posture were we in at time T" is itself a security-relevant fact.
- **Time-boxed cryptographic identity rotation as a privacy control**: combining a per-site secret salt with a day-granularity epoch in a keyed hash forces any derived biometric signature to expire and become uncorrelatable after 24 hours — a generalizable technique for any system that must derive a stable-but-time-bounded identifier from sensitive raw signal.
- **Content-classification (what data) kept orthogonal to posture-classification (what's the operator's intent)**: separating `PrivacyClass` (data content tier) from `PrivacyMode` (named operator posture that *pins* a class) means adding a new deployment scenario (a new posture) doesn't require inventing new data-tier semantics — a clean separation of concerns for any privacy/access system with multiple audiences and multiple data sensitivity levels.
- **Enforcement at the transport/routing layer, redundant with application logic**: gating MQTT topic publication by required privacy class means even a bug in upstream application logic that produces a too-sensitive event still can't leak it onto a public topic — defense in depth applied to a message bus rather than just to the producer.
- **Resource-budget-guarded sandboxed plugin execution** (WASM3 + `manifest_budget_us` + forced termination on overrun): a minimal but effective pattern for letting untrusted/third-party logic run on a resource-constrained device without one bad module starving shared critical tasks (here, WiFi radio handling) — directly reusable for any plugin/extension system on constrained hardware.
- **Dual-latency parallel taps off one validated stream** (500-1000ms windowed pipeline + ~33ms introspection tap, both fed from the same `validate_frame` gate): rather than making the whole pipeline low-latency (expensive) or accepting only high latency, running a cheaper/faster analysis in parallel for specific signals (regime classification, pattern matching) while the heavier pipeline still produces the authoritative output.
- **TDM-based multistatic coordination for N-node sensor meshes**: scheduling every node into a dedicated TX slot while all others RX (rather than a central beacon-and-poll model) produces full N×(N-1) link diversity with bounded cycle time — a general pattern for coordinating any small mesh of resource-constrained radios that must avoid self-interference.
- **Producer/consumer core-affinity split on dual-core embedded hardware**: dedicating one core to interrupt-driven radio capture (writing to a lock-free SPSC ring buffer) and the other to signal processing avoids DSP compute latency ever blocking radio callbacks — a standard but important embedded-systems pattern worth calling out explicitly.

## Practical how-tos

- **30-second no-hardware demo**: `docker run -e CSI_SOURCE=simulated -p 8080:8080 -p 8765:8765 ruvnet/wifi-densepose:latest` then open `http://localhost:8080` — runs a simulated sensing server with synthetic CSI, no ESP32 hardware required.
- **Full Rust build/dev**: `git clone https://github.com/ruvnet/RuView.git && cd RuView/v2 && cargo build --release && cargo test --workspace --no-default-features`.
- **Provision and flash an ESP32-S3 node**: `python firmware/esp32-csi-node/provision.py --port COM9 --ssid "YourWiFi" --password "secret" --target-ip 192.168.1.20` then `idf.py -p COM9 flash` (requires ESP-IDF; ESP32-C3/original ESP32 not supported, ESP32-S3 required for full CSI-based sensing).
- **Test multi-node mesh coordination without hardware**: use `scripts/qemu_swarm.py` with a topology preset (star/mesh/line/ring) from `swarm_presets/*.yaml`; it drives `generate_nvs_matrix.py` to produce per-node NVS images and runs them under QEMU against a mock CSI generator.
- **Choose an edge-tier deployment**: set the NVS `edge_tier` key (0-3) per deployment scenario — Tier 0 for maximum server-side flexibility on a good link, Tier 2 for battery-powered/safety-critical nodes needing on-device vitals at minimal bandwidth (32 bytes @ 1Hz), Tier 3 when custom sensing logic needs to be pushed without reflashing.
- **Select a privacy posture for a deployment**: choose a `PrivacyMode` (e.g. `PrivateHome` pins Class 2/Anonymous for typical home use; `CareWithConsent` pins Class 1/Derived when identity-level detail is explicitly consented to, e.g. care-home fall-risk monitoring; `StrictNoIdentity` pins Class 3/Restricted to strip even risk scores) rather than configuring individual privacy flags by hand.

## Gotchas & caveats

- ESP32-C3 and original ESP32 are explicitly not supported for full CSI-based sensing — only ESP32-S3 (and ESP32-C6 per ADR-110 for Wi-Fi 6 extension); don't assume any ESP32 variant works.
- Raw BFI (Class 0) and identity embeddings (part of Class 1) are architecturally prevented from ever reaching the network or disk (I1/I2) — this is not a configurable setting that can be toggled on for convenience; it is a structural invariant of the crate.
- The MQTT identity-risk topic is only published at exactly Class 2 (Anonymous), not at Class 1 (Derived) despite Derived nominally containing "more" data — Derived already carries the raw risk-scoring inputs, so double-exposing the score there is treated as unnecessary risk amplification rather than being gated by "more permissive class = more topics."
- The 50Hz UDP send rate limit on Tier 0/raw-passthrough nodes exists specifically to prevent `ENOMEM` exhaustion of the ESP32's lwIP stack during high-rate promiscuous capture — running without this limiter (e.g. in a custom fork) risks silent packet loss or crashes under sustained high CSI rates.
- WASM Tier 3 modules are resource-isolated by a declared time budget (`manifest_budget_us`), not by a memory/capability sandbox alone — a module that stays within its host-API permissions but simply runs too long is still forcibly terminated; budget planning matters as much as functional correctness when authoring custom modules.
- Cross-channel phase alignment (needed whenever TDM channel-hopping is enabled) depends on the `NeumannSolver` correcting for local-oscillator rotation; deployments that disable channel hopping for simplicity lose the multipath-fading mitigation and multi-band bandwidth benefits it provides.
- Several architecturally significant pieces referenced in the ADR index (e.g. ADR-137 Fusion Quality Scoring, ADR-138 LinkGroup/MLO gating, ADR-139 WorldGraph digital twin, ADR-150 RF Foundation Encoder) are marked "Proposed" rather than "Accepted/Implemented" — treat these as design intent, not confirmed current behavior, without checking the ADR status field directly.
