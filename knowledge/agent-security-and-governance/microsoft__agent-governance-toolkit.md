# Microsoft Agent Governance Toolkit (AGT) — Distilled Knowledge

## What it is

The Agent Governance Toolkit (AGT) is a runtime infrastructure for governing AI agent actions — tool calls, resource access, inter-agent communication — using deterministic policies and zero-trust identity, rather than model-level text filtering. It operates at the application layer, intercepting agent actions before execution. It claims 10/10 coverage of the OWASP Agentic Top 10 risks and cites 13,000+ tests, and is compatible with LangChain, AutoGen, CrewAI, OpenAI Agents, and Google ADK. It is implemented as a monorepo across Python, TypeScript, .NET, Rust, and Go, with an explicit design goal of deterministic sub-millisecond (<0.1ms) policy evaluation because "governance must be predictable" and probabilistic (LLM-based) enforcement is considered unsuitable for security due to hallucination risk (ADR 0004).

Key packages: `agent-os-kernel` (PolicyEvaluator, StatelessKernel, Nexus control plane), `agent-mesh`/`agentmesh-platform` (zero-trust identity, IATP trust protocol, lifecycle), `agent-hypervisor` (privilege rings, SagaOrchestrator), `agent-sre` (SLOs, error budgets, chaos testing), `agent-compliance`/`agent-governance-toolkit` (unified `agt` CLI for OWASP verification and integrity checking), `agent-marketplace` (plugin trust tiers), `agent-lightning` (RL training governance), `agent-discovery` (shadow-AI discovery).

## Architecture

**Interception flow**: Agent Action -> Governance Interceptor -> PolicyEvaluator/PolicyEngine -> Allow (execute tool) or Deny (raise `GovernanceDenied`) -> Flight Recorder / audit log, regardless of outcome. The `govern()` wrapper (`agentmesh.governance.govern`) is the "2-line integration" entry point: wrapping any callable with `govern(my_tool, policy="policy.yaml")` causes every call to be checked against the policy and logged.

**Policy data model** (`agent_os.policies.schema`): a `PolicyDocument` (versioned, named) contains an ordered list of `PolicyRule` objects plus `PolicyDefaults` (fallback action, `max_tokens`, `max_tool_calls`, sandbox resource limits — CPU/memory/timeout — and a fail-closed `network_default: deny`). Each `PolicyRule` has a `PolicyCondition` (field + `PolicyOperator` — `eq`, `ne`, `gt`, `lt`, `gte`, `lte`, `in`, `not_in`, `matches` regex, `contains` — evaluated against runtime context fields like `tool_name`, `token_count`, `environment`), an `action` (`allow`/`deny`/`audit`/`block`), and a `priority` integer. `PolicyDocument.inherit` and `.scope` (glob) control hierarchical applicability.

**Evaluation pipeline** (`PolicyEvaluator.evaluate()`), strictly ordered "most specific to most general, native to external": (1) native `PolicyRule`s sorted by priority descending; (2) if no native rule matches, iterate registered `ExternalPolicyBackend`s (OPA/Rego, Cedar); (3) if nothing matches, fall back to `PolicyDefaults.action`. **Fail-closed semantics** are load-bearing throughout: any exception during native rule expression parsing is treated as a match triggering `deny`; `OPABackend`/Go SDK backends explicitly return `deny` on evaluation error rather than propagating the failure silently as an allow.

**Policy discovery and merging**: `discover_policies(action_path, root)` walks up the directory tree from an agent's location to a defined root collecting `governance.yaml` files; `merge_policies()` combines the resulting chain. The critical security invariant: a child policy can override a parent rule with `override=True` **unless the parent rule is a `deny`** — parent denies are immutable and dropped-overrides are silently ignored, specifically to prevent privilege escalation via a more-local policy loosening a stricter ancestor rule.

**Conflict resolution strategies** (`ConflictResolutionStrategy`): `DENY_OVERRIDES` (any matching deny wins — fail-safe default for high-security environments), `ALLOW_OVERRIDES` (any matching allow wins — used for "punch-through" exceptions), `PRIORITY_FIRST_MATCH` (default; highest-`priority` matching rule wins regardless of allow/deny), `MOST_SPECIFIC_WINS` (resolved primarily by `PolicyScope` — AGENT > ORGANIZATION > TENANT > GLOBAL — with priority as a tie-breaker within the same scope).

**External policy backends**: `OPABackend` supports remote OPA (REST JSON), local CLI (`opa eval` subprocess), and a regex-based built-in fallback for simple Rego patterns when no external engine is available. `CedarBackend`/`CedarEvaluator` supports `cedarpy` (Rust bindings), CLI, and a built-in pattern matcher; the Go SDK uses zero-dependency regex matching on `permit`/`forbid` statements. The .NET `OpaPolicyBackend` uses a static `HttpClient` with a bounded 2-minute `PooledConnectionLifetime` to balance DNS re-resolution against connection reuse.

**A2A (agent-to-agent) governance**: an `A2AGovernanceAdapter` bridges the core `PolicyEvaluator` into agent-to-agent protocols so inter-agent messages get the same scrutiny as tool calls. A `ConversationGuardian` runs non-deterministic monitoring on top: `EscalationClassifier` (detects coercive/escalating rhetoric), `FeedbackLoopBreaker` (breaks infinite agent-agent retry cycles), `OffensiveIntentDetector` (flags vulnerability-research or exfiltration language). An `AdvisoryCheck` layer (`PatternAdvisory` regex-based, `HttpAdvisory` calling external classifiers) runs strictly **after** deterministic rules pass and can only add restrictions — it can never override a deterministic deny, keeping non-deterministic ML-based checks subordinate to deterministic policy.

**Audit trail**: every `AuditEntry` captures agent identity, action, policy decision, and matched rule. Entries are SHA-256 hash-chained (each carries a `previous_hash`, forming a `MerkleAuditChain`) to make tampering detectable; a `SignedAuditEntry` additionally adds an HMAC-SHA256 signature for cryptographic proof of origin (NIST SP 800-107 aligned). `require_approval` decisions pause execution for a human via `CallbackApproval`, `WebhookApproval`, or `ConsoleApproval` handlers.

**Identity (AgentMesh)**: every agent is a first-class cryptographic principal, not a service account. `AgentIdentity` wraps an Ed25519 keypair and a `did:mesh:<128-bit-hex>` Decentralized Identifier (`AgentDID`), generated with 128 bits of entropy for Sybil resistance, and is bound to a human `sponsor_email` for accountability. Credential `status` moves through `active` -> `suspended` (policy violation or trust drop) -> `revoked` (permanent, compromise/decommission) — a managed state machine, not a static API key. Ephemeral `CredentialManager` tokens default to a 15-minute TTL; Rust `Credential.rotate()` marks the old credential `Rotated` and links a new one to it, preserving lineage. `MTLSIdentityVerifier` derives self-signed X.509 certs (RFC 8410) from the Ed25519 keys, embedding the Agent DID as a URI in the certificate's Subject Alternative Name, so mTLS and mesh identity share the same cryptographic root. Confidential/TEE-backed identity (ADR 0010) binds attestation evidence to `agent_did` + handshake challenge + Ed25519-public-key-hash via a canonical digest, specifically to prevent relay attacks.

**Delegation**: agent-to-agent capability delegation uses **scope chains** enforcing (a) a hard `MAX_DELEGATION_DEPTH` to prevent infinite chains, (b) **capability narrowing** — a child's capabilities must be a strict subset of the parent's, verified with wildcard-prefix support (`read:*`), and (c) **trust capping** — a child's initial trust score cannot exceed a lineage-bound `max_initial_trust_score`, so delegation cannot be used to bootstrap a more-trusted identity than its grantor.

**IATP trust handshake**: an Ed25519 challenge/response protocol targeting a **200ms SLA**. Responder issues a `HandshakeChallenge` (unique `challenge_id`, random 32-byte nonce, optional RFC 9334 freshness nonce); initiator signs the nonce and returns `HandshakeResponse` (DID, public key, current trust score); responder verifies the signature, checks the peer is `active` in the `IdentityRegistry`, and checks the trust score against a threshold. A verified-peer cache (default TTL 15 min) avoids redundant handshakes. Cached scores in `TrustBridge` are themselves protected against local tampering via an HMAC computed over the peer's DID+score+capabilities, checked before the bridge trusts a cached value — cache poisoning is treated as a real threat, not just remote tampering.

**Trust scoring**: 0–1000 scale (Python) mapped to tiers — `verified_partner` (900–1000, full cross-org delegation), `trusted` (700–899, elevated privileges), `standard` (400–699, default for new agents, read + non-sensitive writes), `untrusted` (0–399, blocked/sandboxed). Scores combine reliability (success/failure ratio) and consistency, updated via `RecordSuccess`/`RecordFailure` with reward/penalty factors, and undergo **temporal decay** on every interaction so standing reflects recent behavior, not historical peak trust — an agent cannot coast indefinitely on an old high score.

**Execution rings (Agent Hypervisor)**: a 4-tier OS-CPU-ring-inspired privilege model — Ring 0 (Root/System, trust 900–1000, kernel-level and admin operations, elevation to Ring 0 is explicitly forbidden through the request API so no agent can self-escalate to root), Ring 1 (Privileged, 700–899, write + external network + high-frequency calls, requires an external attestation/sponsorship token to elevate into), Ring 2 (Standard, 500–699, read + limited write), Ring 3 (Sandbox, <500 default, read-only, no network egress, strict rate limits). Elevation is temporary (`DEFAULT_TTL`/`MAX_ELEVATION_TTL` cap privilege duration to prevent creep) and gated by explicit trust thresholds (e.g. 0.6 for Ring 2, 0.9 for Ring 1). A `RingBreachDetector` tracks call frequency per agent and trips a circuit breaker on anomalous deviation from baseline — treated as a signal of possible sandbox escape or privilege abuse, not just noisy usage.

**Session isolation**: `SessionIsolationManager` enforces three levels — `SNAPSHOT` (read-only point-in-time, writes local to session), `READ_COMMITTED` (cross-session reads only via explicit `granted_sessions`), `SERIALIZABLE` (full isolation via `VectorClock` + `IntentLock` coordination). Vector clocks give component-wise causal comparison across agents in multi-agent sessions to detect causal-order violations.

**Sandbox hardening for Ring 3**: Docker-based `SandboxProvider` drops all capabilities (`--cap-drop ALL`), sets `no-new-privileges`, mounts the root filesystem read-only by default, and disables network egress by default. Code is piped via stdin into `docker exec` rather than interpolated into a shell command, specifically to avoid shell-injection vulnerabilities.

**Rate limiting and cost governance**: `AgentRateLimiter` applies per-agent, per-ring `TokenBucket`s (configurable refill rate/capacity), with higher rings getting more generous limits. A separate `CostGuard` tracks spend per task and per agent per day, and can trigger a **kill switch** automatically once spend crosses a threshold (e.g. 95% of daily budget); a `CostAnomalyDetector` flags cost spikes using Z-score analysis against a per-agent baseline — cost is treated as its own governable resource dimension, parallel to but independent from rate limits.

**STRIDE-mapped threat model** across four trust boundaries — Human→Agent (prompt injection, goal hijacking), Agent→Agent (spoofed identity, tampered trust signals, over-broad delegation), Agent→Tool (tool poisoning, rug pulls, exfiltration, destructive side effects), Agent→Platform (supply-chain tampering, unsigned artifacts). Mitigations: Spoofing -> Ed25519 DIDs; Tampering -> `MerkleAuditChain` SHA-256 hash chaining; Repudiation -> HMAC-SHA256-signed immutable audit trail (NIST SP 800-107); Information Disclosure -> `CredentialRedactor` strips secrets before logs are written; Denial of Service -> `CircuitBreaker` + SLO engine; Elevation of Privilege -> Ring 0 permanently denied to agents.

**OWASP Agentic Top 10 (ASI 2026) mapping** — the toolkit's own claimed coverage table: ASI-01 Goal Hijack -> `StatelessKernel` action interception + `PromptInjectionDetector`; ASI-02 Tool Misuse -> capability sandboxing + `MCPSecurityScanner` (detects invisible-unicode instruction smuggling, base64/hex-encoded hidden payloads, and "rug pulls" via `ToolFingerprint` schema-change detection); ASI-03 Identity/Privilege Abuse -> DID identity + `CredentialRedactor`; ASI-04 Supply Chain -> AI-BOM v2.0 (SHA-256 model-weight hashing, SPDX dependency tracking) + `IntegrityVerifier`; ASI-05 Unexpected Code Execution -> Execution Rings + sandbox isolation; ASI-06 Memory/Context Poisoning -> VFS policies + `PromptInjectionDetector`; ASI-07 Insecure Inter-Agent Comm -> IATP handshake + `MCPMessageSigner` (HMAC-SHA256, min 32-byte keys, nonce-based replay protection via `MCPNonceStore`); ASI-08 Cascading Failures -> `CircuitBreaker` + SLO enforcement; ASI-09 Human-Agent Trust Exploit -> approval workflows + audit entries; ASI-10 Rogue Agents -> kill switch + ring-based isolation. The toolkit's headline claim is a 0.00% policy-violation rate for its deterministic application-layer enforcement versus a cited 26.67% rate for prompt-based safety approaches.

## Key patterns & techniques (transferable)

- **Deterministic enforcement kept strictly outside the LLM control loop** (ADR 0004): treating a probabilistic model as unsuitable for the actual security decision, and instead gating every action through a separate, auditable, rule-based evaluator — a design stance directly reusable by anyone building agent governance who is tempted to "ask the model if this is safe."
- **Immutable parent-deny invariant in hierarchical policy merging**: allowing local/child policies to override parents for flexibility, but hard-blocking any override of a parent `deny`, closes the most common "policy layering" privilege-escalation bug (a more permissive local config silently defeating a stricter global one).
- **Fail-closed as a pervasive default, applied at every layer independently** (native rule exceptions -> deny; external backend errors -> deny; Go SDK backend failures -> explicit deny) rather than relying on one central fail-closed gate — defense in depth against any single evaluator having a bug that fails open.
- **Advisory (non-deterministic) checks explicitly subordinated to deterministic ones**: the `AdvisoryCheck` layer can add restrictions but never override a deterministic allow-then-caught-later scenario or loosen a deny — a clean way to bolt ML-based heuristics (PII scanning, anomaly detection) onto a system without letting them become the actual security boundary.
- **Trust as a decaying, multi-dimensional score rather than a static grant**: combining reliability/consistency with temporal decay means an agent's privilege is continuously re-earned, not a one-time credential check — directly transferable to any system doing risk-adaptive access control for long-lived autonomous principals.
- **Capability narrowing + trust capping as twin constraints on delegation**: bounding both *what* a delegated identity can do (subset of parent capabilities) and *how much it can be trusted* (capped below the grantor) closes two different escalation vectors that capability-narrowing alone would miss (a child could otherwise still inherit or exceed the parent's trust tier).
- **Ring-elevation TTL + explicit ban on self-elevation to the top tier**: privilege elevation is temporary by construction (capped TTL) and the highest tier is categorically unreachable via the elevation API — two independent guardrails against privilege creep that don't rely on catching misuse after the fact.
- **Tamper-evident audit via hash-chaining + separate HMAC signing**: chaining (detects reordering/deletion) and signing (proves origin) are treated as two distinct properties requiring two distinct mechanisms, rather than assuming one implies the other.
- **Tool fingerprinting for "rug pull" detection**: hashing a tool's schema/description at registration time and re-checking on each subsequent invocation catches a specific supply-chain attack (a tool silently changing behavior after being trusted) that a one-time approval process would miss entirely.
- **Cost as an independently governed resource with its own kill switch and anomaly baseline**: treating spend-per-agent as a first-class governance signal (not just a billing afterthought) with automated circuit-breaking is a pattern worth replicating for any system running metered, autonomous, potentially-runaway agents.

## Practical how-tos

- **Install**: `pip install agent-governance-toolkit[full]` (Python); `npm install @microsoft/agent-governance-sdk` (TypeScript); `dotnet add package Microsoft.AgentGovernance` (.NET 8+); `cargo add agent-governance` (Rust); `go get github.com/microsoft/agent-governance-toolkit/agent-governance-golang` (Go).
- **2-line integration**: `from agentmesh.governance import govern; safe_tool = govern(my_tool, policy="policy.yaml")` wraps any callable so every call is policy-checked and logged automatically.
- **Programmatic policy construction**: build a `PolicyDocument` with `PolicyRule`/`PolicyCondition`/`PolicyOperator`/`PolicyAction` objects directly (e.g. deny when `tool_name in ["delete_file", "shell_exec"]`), then `PolicyEvaluator(policies=[policy]).evaluate(context)`.
- **Verify OWASP compliance posture**: `agt verify` (optionally `--evidence <path>` for runtime evidence, `--strict` to fail the run on any governance gap).
- **Check installation integrity**: `from agent_compliance.integrity import IntegrityVerifier; report = IntegrityVerifier().verify()`, or `agt doctor`/`agt integrity` at the CLI, to detect tampered governance modules.
- **Wrap a specific framework**: install the matching adapter package (`agentmesh-langchain` for LangChain's `LangChainKernel`, `openai-agents-agentmesh`, `crewai-agentmesh`, `adk-agentmesh` for Google ADK) instead of hand-wiring `govern()` into framework internals.
- **Author starter policies**: the repo ships templates under `examples/policies/` — `sql-safety.yaml` (blocks DROP/DELETE/TRUNCATE via regex), `pii-detection.yaml`, `mcp-security.yaml`, `cli-security-rules.yaml` (blocks dangerous shell commands) — as a starting point rather than authoring rules from scratch.
- **Set up rate limiting**: configure a `TokenBucket` (capacity = max burst, refill_rate = tokens/sec) per agent/tool to protect external APIs from runaway agent call volume.

## Gotchas & caveats

- Deterministic policy evaluation governs what agents **do** (actions/tool calls), explicitly not what they **think** (reasoning) — it is not a general jailbreak/hallucination defense, only an action-layer gate; the toolkit's own docs frame this scope limitation directly.
- A child policy cannot loosen a parent `deny` under any `override` setting — if a locally-scoped policy seems to be "ignoring" an override flag, check whether the rule it's trying to override is a parent-level deny; that's enforced as a security invariant, not a bug.
- Elevation to Ring 0 is categorically blocked through the elevation request API — there is no configuration path to grant an agent root/system privilege at runtime by design; if Ring 0 access is genuinely needed it must happen outside the elevation mechanism entirely.
- Trust scores decay over time even without new negative events — a previously `verified_partner`-tier agent that goes quiet or inactive will not indefinitely retain that tier; don't assume a cached high trust score remains valid without re-verification.
- Advisory checks (PII scanners, HTTP-based classifiers) can only add restrictions after deterministic rules pass — they cannot be used to override a deterministic `allow` into a stricter posture retroactively in the same evaluation pass in a way that changes the deterministic decision path itself; understand this ordering before relying on an advisory layer as your primary control.
- The 0.00%-violation-rate / 26.67%-prompt-based-safety-rate comparison is the toolkit's own marketing claim from its documentation, not an independently verified benchmark — treat it as a directional claim about deterministic vs. probabilistic enforcement, not a load-bearing number.
- Multi-language SDK parity is not guaranteed to be identical: trust scores are 0–1000 in Python but often normalized to 0.0–1.0 internally in Go/TypeScript, and backend implementations (OPA/Cedar) differ in what fallback mode is used (built-in regex vs. CLI vs. remote) per language — check the specific SDK's backend docs rather than assuming behavior transfers across languages.
