# NVIDIA/OpenShell — Distilled Knowledge

## What it is

OpenShell is a safe, private runtime for autonomous AI agents. It provides isolated execution environments ("sandboxes") that protect data, credentials, and infrastructure, governed by declarative YAML policies that prevent unauthorized file access, data exfiltration, and uncontrolled network activity. It targets three specific risk categories: unauthorized file access (agents reading SSH keys/tokens or writing to system dirs), data exfiltration (outbound traffic carrying sensitive context/credentials), and uncontrolled network activity (connections to unauthorized services, internal infrastructure, or attacker-controlled endpoints). Built in Rust as a set of crates (`openshell-server`, `openshell-sandbox`, `openshell-policy`, `openshell-prover`, `openshell-cli`, a Python SDK). Runs on Linux and macOS; Linux-specific kernel features (Landlock, seccomp) provide the strongest isolation, with macOS relying on the Docker Desktop/MicroVM Linux VM for the same guarantees.

## Architecture

**Control plane / execution plane split.** The **Gateway** (`openshell-server` binary) is the authenticated control-plane API: it owns durable state (sandboxes, policy revisions, provider records) in a `Store` abstraction over SQLite or Postgres, multiplexes gRPC and HTTP traffic on one port via `MultiplexService`, and coordinates relay sessions for CLI-to-sandbox connectivity (SSH connect, exec, service forwarding) over mTLS or plaintext. It abstracts sandbox provisioning behind a pluggable `ComputeRuntime`/`ComputeDriverKind`: Docker, Podman, Kubernetes, and `libkrun`-based MicroVMs, auto-detected in that order (Kubernetes, Podman, Docker) unless overridden via `OPENSHELL_DRIVERS`.

The **Sandbox** is the execution plane: a workload (container or VM) supervised from inside by the `openshell-sandbox` binary. The supervisor initiates the *outbound* connection to the gateway (rather than being dialed — reduces attack surface for a compromised sandbox reaching back into the control plane), fetches its policy/config, prepares isolation, and only then spawns the agent as a restricted child process. `run_sandbox()` in `crates/openshell-sandbox/src/lib.rs` is the orchestration entry point; a `SandboxContext` carries process-wide metadata (sandbox ID, hostname, image) used to populate every audit log event.

**Two trust levels inside one workload**: the supervisor starts as root to prepare isolation (apply Landlock rules, seccomp filters, set up the network namespace) but the agent child process runs as an unprivileged, non-root user (`sandbox` by default; `run_as_user`/`run_as_group` in policy — root identity is strictly rejected). Enforcement happens in a `pre_exec` closure between `fork()` and `exec()`: switch group, switch user, drop all capabilities and clear the bounding set (so a later exec cannot regain privileges), apply Landlock, apply seccomp — in that order, and once `execve()` runs these are permanently locked in for the process's lifetime.

**Four policy domains, split static vs. dynamic**:
| Domain | Mechanism | Mutability |
|---|---|---|
| Filesystem | Landlock LSM path allowlists | Static — locked at creation |
| Process | setuid/setgid + capability drop | Static — locked at creation |
| Network (L4/L7) | HTTP CONNECT proxy + embedded OPA/Rego engine | Dynamic — hot-reloadable |
| Inference | Privacy Router (`inference.local`) | Dynamic — hot-reloadable |

Static domains are enforced once, in the kernel, before the agent process exists, and — because Landlock rulesets are additive-only, seccomp's `NO_NEW_PRIVS` blocks filter removal, and a non-root process cannot `setuid(0)` — cannot be relaxed later without restarting the sandbox. Dynamic domains are evaluated per-connection/per-request by the local proxy against an in-process OPA engine that can be atomically swapped at runtime.

**Network isolation.** Each sandbox workload gets its own Linux network namespace, wired to the host via a veth pair, so the *only* reachable endpoint from inside is the proxy listener (bound to the veth host IP, typically `10.200.0.1`, or `127.0.0.1` in loopback mode) — this makes "all egress must transit the proxy" a routing-level guarantee, not just a policy convention. A **Bypass Monitor** adds defense-in-depth on top of that guarantee, watching for processes attempting direct egress to external IPs, direct DNS queries bypassing the proxy, or probing internal segments/cloud metadata — logged as OCSF `DetectionFinding` events. The proxy also defers accepting connections until it has resolved the workload's symlinks via `/proc/<pid>/root/` (e.g. `/usr/bin/python3` -> `/usr/bin/python3.11`), specifically to prevent policy bypass through symlink manipulation of binary paths referenced in policy.

**HTTP CONNECT proxy request flow**: TCP accept -> read up to 8192 bytes (`MAX_HEADER_BYTES`) -> parse `CONNECT host:port` -> if `host == inference.local`, bypass OPA entirely and hand off to the inference-routing path; otherwise -> resolve which binary initiated the connection by walking `/proc/net/tcp` to the owning socket inode, then `/proc/<pid>/exe`, verified against a `BinaryIdentityCache` using SHA256 Trust-On-First-Use (TOFU) -> collect ancestor-process binaries and command-line paths -> call `OpaEngine::evaluate_network_action()` with the resolved binary identity and destination -> on Allow, resolve the hostname's IPs and reject if any resolve to an internal/always-blocked address (SSRF check, applied *after* OPA allow, so a policy cannot itself authorize a metadata-service or loopback hit) -> establish the tunnel and relay, optionally through L7 inspection.

**L7 protocol inspection** (`relay_with_inspection`) replaces raw TCP copy for endpoints declaring `protocol: rest|graphql|websocket|mcp`. The REST provider does strict UTF-8 validation and rejects bare LF in headers (anti request-smuggling), and can re-sign AWS SigV4 headers (Bedrock/S3, bodies up to 10 MiB) replacing credential placeholders with real secrets and recomputing body hashes. GraphQL inspection parses operations from POST bodies or GET query params and enforces rules by `operation_type` (query/mutation) and `fields`, with support for persisted queries via SHA256 hash allowlisting. MCP/JSON-RPC over WebSocket is inspected so only allowed MCP methods can be invoked.

**Provider/credential model**: Providers are named credential bundles (API keys/tokens) stored at the gateway, never written to sandbox disk. Injection uses a "placeholder and rewrite" scheme: the supervisor injects an opaque placeholder (e.g. `openshell:resolve:env:VAR`) into the agent's environment instead of the real secret; only when the proxy sees an outbound request to a policy-allowed endpoint does it resolve the placeholder to the actual credential and rewrite the request before forwarding. "Providers v2" turns providers into profile-backed access bundles (`ProviderTypeProfile`) that declare credentials, allowed endpoints/binaries, and refresh strategy (OAuth2, Google Service Account JWT) together — attaching a provider to a sandbox auto-composes `_provider_*`-prefixed network policy layers so a provider's traffic is confined to its own known-good endpoints and only the binaries it names (e.g. `harness: copilot`).

**Formal policy verification (`openshell-prover`)**: a Z3 SMT-solver-backed engine that checks proposed policy changes for risk before they're auto-approved. It combines a **Binary Capability Registry** (per-binary YAML docs like `claude.yaml`/`curl.yaml`/`git.yaml` declaring `can_construct_http`, `can_spawn_shell`, `can_exfiltrate` and the exfiltration mechanism) with an **API Scope Registry** (mapping HTTP method+path to an action and risk level, e.g. `PUT /repos/*/contents/**` -> `write_file` / High) to detect: L7 bypass (a binary capable of raw-byte traffic reaching an endpoint configured for `rest` inspection), data exfiltration (an exfiltration-capable binary granted write access without strict L7/deny-rule protection), credential exposure (reachability to an endpoint that consumes a sensitive credential, e.g. SigV4-signed AWS calls), and SSRF gaps (`allowed_ips` overlapping always-blocked ranges). High-risk findings require explicit human approval before the resulting policy is merged (`merge_policy`) and applied.

**Policy Advisor / mechanistic mapper**: network denials are aggregated by `(host, port, binary)`; the `MechanisticMapper` deterministically converts denial patterns into draft `NetworkPolicyRule` proposals, skipping proposals for destinations that are always-blocked (to avoid an infinite proposal loop for genuinely un-allowable targets), and including observed HTTP methods/paths as L7 rule samples when L7 inspection was active during the denial. Proposals get a confidence score from hit count and well-known-port heuristics, are submitted to the gateway (`SubmitPolicyAnalysis`), run through the prover, and — if `proposal_approval_mode` is `auto` and the prover finds no new risk — can be hot-reloaded onto the running sandbox without a restart.

**Live policy updates**: the supervisor polls the gateway for config revisions; a new dynamic policy must validate before being swapped in atomically — if validation fails, the supervisor keeps enforcing the prior **Last-Known-Good (LKG)** policy and reports the load failure, prioritizing availability/stability over blindly applying a broken update. Reload boundaries matter: existing keep-alive/L7-parsed connections are closed so the *next* request sees the new policy, but raw connection-scoped streams (WebSockets, SSE, TLS passthrough) are left alone until the client reconnects.

**Audit logging (OCSF)**: every security-relevant event — network CONNECT/deny, HTTP L7 decisions, SSH sessions, process start/exit, policy load/reload, detection findings — is emitted as an Open Cybersecurity Schema Framework (OCSF) v1.7.0 event via the `openshell-ocsf` crate, giving vendor-neutral SIEM-ingestible structured logs (class UIDs like 4001 Network Activity, 4002 HTTP Activity, 2004 Detection Finding, 5019 Device Config State Change). A human-readable "shorthand" projection (`<time> <severity> <CLASS:ACTIVITY> <action> <fields> [context]`) is generated alongside the JSON for real-time CLI/TUI monitoring, including a `reason_tag` on denials (e.g. `[reason:resolves to always-blocked address]`).

**Sandbox-local self-service API (`policy.local`)**: an in-sandbox-only virtual HTTP endpoint the agent itself can query: `GET /v1/policy/current` (active policy), `GET /v1/denials` (recent denials for self-diagnosis), `POST /v1/proposals` (submit a policy change request). Denied requests carry `next_steps` in the 403 body pointing the agent to this API and to a local skills doc, so an agent can self-serve an access request rather than the interaction dead-ending.

**Auth model**: mTLS for local single-user gateways, OIDC bearer tokens for shared/enterprise clusters, gateway-minted JWTs for supervisor-to-gateway RPCs (bound to a `Principal::Sandbox`, restricting which RPCs — e.g. `ConnectSupervisor`, `RelayStream` — a sandbox identity may call), and Cloudflare-JWT/trusted-proxy-header auth for edge/cloud deployments. Kubernetes supervisors bootstrap trust by exchanging a ServiceAccount token for a gateway JWT (`IssueSandboxToken`); Docker/VM drivers deliver the token via runtime-injected material instead.

## Key patterns & techniques (transferable)

- **Static/dynamic policy split mapped directly onto kernel-vs-userspace enforcement boundaries**: anything enforced once, before untrusted code runs (filesystem, process identity) is made deliberately immutable by relying on true kernel guarantees (Landlock additive rulesets, `NO_NEW_PRIVS`, non-root can't `setuid(0)`); anything that must adapt at runtime (network) lives entirely in userspace behind a hot-swappable engine. This gives strong startup-time guarantees without sacrificing runtime flexibility where it's actually needed.
- **Namespace-level routing as the backstop for a policy engine, not a substitute for it**: putting the sandbox in its own network namespace with only the proxy reachable makes "all traffic is inspected" true by construction; the OPA-based policy engine then decides what's allowed within that guaranteed choke point — two independent layers rather than one doing double duty.
- **Binary-identity binding via `/proc` + TOFU, not just destination-based rules**: resolving which executable initiated a connection (walking socket-inode ownership to `/proc/<pid>/exe`, cached and integrity-checked via SHA256 trust-on-first-use) lets network policy scope access to specific tools (`binaries: [{path: /usr/bin/curl}]`) rather than to the whole sandbox, meaningfully shrinking blast radius if one tool is compromised.
- **Ordering SSRF checks after policy allow, not folded into it**: resolving the allowed destination's IPs and separately rejecting internal/metadata addresses as a final gate means no policy author can accidentally (or maliciously) craft a rule that authorizes reaching `169.254.169.254` — a hard-coded safety net independent of user-authored config.
- **Deferred readiness gated on symlink resolution**: binding a listener immediately but delaying `accept()` until `/proc/<pid>/root/` symlink canonicalization completes closes a race window where an early request could exploit a not-yet-resolved literal path — a general pattern for "the policy target and the runtime target must agree before enforcement can be trusted."
- **Formal verification (Z3 SMT) as a gate on auto-approval, not a replacement for human judgment**: the prover only auto-hot-reloads a proposal when it finds *no new* risk; anything flagged still requires explicit human approval — treats the solver as a fast, sound "no-issues-found" filter rather than a full authorization authority.
- **Last-Known-Good fallback on config reload**: refusing to swap in an unvalidated policy and instead continuing to enforce the previous good one, while reporting the failure, is a directly reusable resilience pattern for any hot-reloadable security config.
- **Placeholder-and-rewrite credential injection**: never putting the real secret in the process environment or on disk — only an opaque token resolved by the trusted proxy at the moment of a policy-allowed outbound request — limits the blast radius of a compromised agent process to "can trigger allowed calls," not "can read the credential."
- **Capability/scope registries as structured input to automated risk analysis**: encoding what a binary *can do* (protocols, exfil mechanisms) and what an API *scope* actually grants (method+path -> action + risk tier) as first-class registries, separate from the policy itself, is what makes the formal verifier's reasoning tractable — the policy alone doesn't carry enough information to assess risk without this side data.

## Practical how-tos

- **Install**: unified installer `curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh` (Linux glibc >= 2.28, or macOS Apple Silicon via Homebrew); also available as RPM/DEB/Snap, or via Helm for Kubernetes cluster-wide deployment.
- **Create a first sandbox**: `openshell sandbox create --from base` (community base image) or `openshell sandbox create -- claude` to auto-detect the Claude provider and launch straight into the agent; `--` separates CLI flags from the in-sandbox command.
- **Verify the default-deny network posture**: create a sandbox, run `openshell sandbox exec -n <name> -- curl https://api.github.com` (blocked by default egress policy), then `openshell policy set <name> --policy policy.yaml` and re-run to confirm the now-allowed request.
- **Write a network policy rule**: under `network_policies`, map a rule name to `endpoints` (host — globbable in the first DNS label only, ports, `protocol` for L7 inspection, `enforcement: enforce|audit`, optional `allowed_ips` CIDR to permit specific internal ranges) and `binaries` (executable paths permitted to use that rule).
- **Grant filesystem access precisely**: use `read_only`/`read_write` path lists under `filesystem_policy` rather than broad access; set `include_workdir: true` to auto-add the CWD; paths must be absolute, no `..` traversal, max 256 entries.
- **Handle a denied request as an agent**: query `http://policy.local/v1/denials` to see recent denials, then `POST http://policy.local/v1/proposals` to request an exception — the 403 body's `next_steps` points here.
- **Debug via SSH/exec**: `openshell sandbox connect <name>` for a full SSH session (also usable for `--editor vscode`/`cursor` IDE integration), or `openshell sandbox exec -n <name> --tty -- <cmd>` for one-shot/interactive debugging.
- **Enable GPU passthrough**: pass `--gpu` at sandbox creation; requires NVIDIA Container Toolkit with CDI configured (Docker/Podman) or the NVIDIA Device Plugin (Kubernetes) or VFIO device IDs (MicroVM).

## Gotchas & caveats

- Static policy fields (filesystem, process, landlock) cannot be changed on a running sandbox under any circumstances — there is no override; a restart is required. Don't expect `openshell policy set` to touch these.
- SSRF protection (loopback, link-local, unspecified, cloud metadata IPs) is enforced unconditionally by the proxy *after* an OPA allow decision — `allowed_ips` can permit RFC 1918 private ranges but cannot be used to reach the hard-blocked always-blocked set, including `169.254.169.254`, regardless of policy intent.
- Live policy reload only affects *future* connections/requests cleanly for L7-parsed traffic; raw passthrough streams (WebSocket, SSE, TLS passthrough) already open at reload time are not retroactively re-evaluated — they run to completion under the old policy.
- An invalid policy update is silently rejected in favor of Last-Known-Good — a bad `openshell policy set` may appear to succeed at the CLI while the sandbox keeps enforcing the prior rules; check for a reported load failure rather than assuming the new policy took effect.
- Binary identity resolution and the associated bypass detection are Linux-only, dependent on `/proc` filesystem access — behavior and guarantees on macOS depend entirely on what the underlying Docker Desktop/MicroVM Linux VM provides, not the native host kernel.
- The formal prover only auto-approves proposals it finds *no new risk* in; anything it flags (exfiltration risk, credential scope increase, binary capability change) requires a human in the loop — it is a risk-detector plus auto-approval-eligibility gate, not a fully autonomous policy approval system.
- Root process identity (`run_as_user`/`run_as_group` = `root`/`0`) is strictly rejected at the policy validation layer — a common misconfiguration attempt that will fail policy loading rather than silently running as root.
