# Apache Kafka — Distilled Knowledge

## What it is

Apache Kafka is an open-source distributed event streaming platform functioning as both a message broker and a distributed storage system — publish/subscribe messaging, durable replicated storage, built-in stream processing (Kafka Streams), horizontal scalability via partitioning. It is a multi-module Gradle project: `:core` (broker/server logic, Scala), `:clients` (Producer/Consumer/Admin APIs, Java), `:streams` (stream processing library), `:connect` (external-system connector framework), `:raft` (the consensus implementation). Supports Java 17/25 for building, Java 11 compatibility for client/streams modules; Scala 2.13 only.

Core vocabulary: a **topic** is a logical channel divided into **partitions** (ordered, immutable, offset-sequenced logs — the unit of parallelism). A **broker** is a server process storing data and serving requests; brokers form a **cluster**. Each partition has multiple **replicas** across brokers, one **leader** and the rest **followers**. **Producers** publish, **consumers** subscribe (organized into **consumer groups** where each partition is owned by exactly one group member at a time); newer **share groups** allow record-level locking and shared consumption instead of strict per-partition ownership.

## Architecture (how it's built, key components)

**KRaft mode replaces ZooKeeper with an internal Raft-based metadata quorum.** Nodes run with `process.roles` set to controller-only, broker-only, or combined (single process running both `BrokerServer` and `ControllerServer`, via a shared `SharedServer` — used for dev/test). Cluster metadata (topics, partitions, configs, ACLs) lives in a special internal topic, `__cluster_metadata`, replicated via Raft across an odd-sized controller quorum (typically 3 or 5 nodes). The Raft leader among controllers is the **active controller**. Brokers don't participate in the metadata Raft group as voters — they read the metadata log and apply changes locally via `MetadataPublisher` implementations, and forward admin requests to the active controller via a `ForwardingManager`. Before a node can start, its log directories must be formatted with a cluster ID and node ID via `StorageTool` (`format`/`info`/`random-uuid` subcommands), producing a `meta.properties` file. Metadata format evolution is versioned via `MetadataVersion` (e.g. `IBP_3_3_IV3`=7 is the minimum supported level, `IBP_4_3_IV0`=30 is described as the latest production version in the wiki) — this decouples "what release you're running" from "what wire/log format the cluster has agreed to use," letting a rolling upgrade run mixed versions before finalizing a new metadata version cluster-wide.

**QuorumController — single-threaded event-driven metadata state machine.** All controller-side metadata mutations execute sequentially on one thread via a `KafkaEventQueue`; external requests become events on that queue. The controller delegates by domain to specialized managers (`ReplicationControlManager` for topics/partitions, `ClusterControlManager` for broker registry, `ConfigurationControlManager`, `AclControlManager`, `ClientQuotaControlManager`, `FeatureControlManager`), all reading/writing through a `SnapshotRegistry` that provides "timeline" (multi-versioned, point-in-time) state so different in-flight requests never see torn state. Writes go through a `RaftClient` and are only considered "real" once replayed back from the committed Raft log — the controller doesn't trust its own in-memory pending write until Raft confirms it, so replay-from-log is the single source of truth for state, not direct mutation.

**Broker registration and health tracking use registration + periodic heartbeat, not just a connection-alive check**: a `BrokerLifecycleManager` sends a `BrokerRegistrationRequest` (endpoints, supported features) to get a broker epoch, then sends periodic `BrokerHeartbeatRequest`s; the controller's heartbeat response reports `isCaughtUp`/`isFenced`. A broker that misses heartbeats is marked **fenced**, which prevents it from being selected as a partition leader even though it may still be technically reachable — separating "is the TCP connection up" from "is this broker safe to route traffic to."

**Group Coordinator is a sharded, replicated, event-sourced state machine — the same design pattern as the metadata controller, applied to group management.** All four group types (classic consumer groups, modern/heartbeat-based consumer groups, share groups, streams groups) are managed by one `GroupCoordinatorService`, which hashes each group ID to a partition of the internal `__consumer_offsets` topic (`partitionFor(groupId) = abs(groupId.hashCode()) % numPartitions`) and routes requests to the `GroupCoordinatorShard` that leads that partition. Each shard follows a strict two-phase mutation model: (1) a request handler (e.g. `consumerGroupHeartbeat`) computes a `CoordinatorResult` containing both the client response *and* a list of records to persist, without mutating in-memory state directly; (2) those records are written to the underlying log and only then `replay()`ed to actually update in-memory state (`GroupMetadataManager`, `OffsetMetadataManager`). This guarantees the persisted log and in-memory state can never diverge — a crash between "decided what to do" and "wrote it down" simply means the decision never happened, rather than leaving state half-applied. Internal state uses `TimelineHashMap`/`TimelineHashSet` from a dedicated `org.apache.kafka.timeline` package for efficient multi-versioned rollback.

**Two consumer group protocols coexist**: **Classic** (`JoinGroup`/`SyncGroup`/`Heartbeat`, client-side assignment — the elected group leader computes partition assignments and pushes them back through the coordinator, "stop-the-world" rebalances) versus **Modern** (`ConsumerGroupHeartbeat`, server-side assignment computed by the coordinator using pluggable `ConsumerGroupPartitionAssignor` implementations like `RangeAssignor`/`UniformAssignor`, single round-trip, incremental cooperative rebalancing instead of a global stop-and-restart). The modern client (`AsyncKafkaConsumer`) is architecturally a completely different beast from the classic client, described next.

**AsyncKafkaConsumer — two-thread, event-queue architecture separating application logic from network I/O.** The application thread (`AsyncKafkaConsumer`, `ApplicationEventHandler`, `BackgroundEventProcessor`, `FetchCollector`) never blocks on network calls itself; it enqueues `ApplicationEvent`s (e.g. `AsyncPollEvent`, `SyncCommitEvent`/`AsyncCommitEvent`, `TopicSubscriptionChangeEvent`, `SeekUnvalidatedEvent`) onto a thread-safe `LinkedBlockingQueue` and, for anything needing a result, wraps it as a `CompletableApplicationEvent` backed by a `CompletableFuture`. A separate `ConsumerNetworkThread` runs a continuous event loop (`runOnce()`), dequeues application events, drives per-concern `RequestManagers` (`MembershipManager` for group state, `HeartbeatRequestManager`, `CommitRequestManager`, `FetchRequestManager`), and pushes results back via a second queue of `BackgroundEvent`s (`ErrorEvent`, `ConsumerRebalanceListenerCallbackNeededEvent`). This is a clean, generalizable dual-thread + bidirectional-event-queue pattern for decoupling a synchronous-looking public API from asynchronous network machinery without exposing locks or callbacks directly to the caller.

**Producer pipeline**: `KafkaProducer.send()` — serialize (via configured `Serializer`) → select partition (via `Partitioner`, or the built-in sticky/adaptive partitioner) → append to `RecordAccumulator` (returns a `Future<RecordMetadata>` immediately) → background `Sender` thread periodically drains ready batches (full or `linger.ms` elapsed) grouped by destination broker, builds `ProduceRequest`s, sends via `NetworkClient`, and completes the caller's future/callback on response. This decouples the application thread entirely from network I/O — `send()` is a buffer-append plus optional callback registration, not a network call.

**Replication — leader/follower with an explicit In-Sync-Replica (ISR) state machine, not a simple "replicated = done" flag.** `ReplicaManager` (one per broker) owns all locally-hosted partitions (`allPartitions: ConcurrentHashMap<TopicPartition, HostedPartition>`, states `None`/`Online`/`Offline`), manages follower-fetcher threads (`ReplicaFetcherManager`) and ISR-change requests to the controller (`AlterPartitionManager`). Each `Partition` tracks its own `PartitionState`: `CommittedPartitionState` (stable, has a committed ISR set), `PendingExpandIsr` (a replica caught up and is being added — the *maximalIsr*, i.e. effective ISR used for `acks=all` and high-watermark purposes, already includes it even before the controller confirms), `PendingShrinkIsr` (one or more replicas fell behind and are being dropped from ISR, but the committed ISR hasn't shrunk yet). This "optimistic maximal set, pessimistic committed set" split lets the leader keep making forward progress on watermark/ack decisions without waiting for a round-trip to the controller on every ISR membership change, while still being conservative about what "committed" means. `makeLeader`/`makeFollower` transitions are driven by controller metadata deltas (`applyDelta`), not by any consensus the broker itself runs — the broker executes what the controller decided, it doesn't negotiate leadership locally.

## Key patterns & techniques (the transferable knowledge)

**KRaft consensus is a 6-state machine with a PreVote phase to avoid disruptive elections.** States: `Unattached` (no known leader) → `Prospective` (soliciting non-binding "PreVotes" without incrementing its own epoch) → `Candidate` (epoch incremented, soliciting real votes) → `Leader` → `Resigned` (graceful step-down) → `Follower`; `Observer` is a non-voting variant of `Follower` used for read replicas that never participate in elections. The PreVote step exists specifically to stop a node that experiences a *transient* network partition from bumping the cluster epoch and forcing an unnecessary re-election once the partition heals — it only commits to "I am a real candidate now, increment my epoch" after confirming a majority would actually grant it a real vote. A vote (real or pre-) is only granted if the requester's log is at least as up-to-date as the voter's own log (compared by log-end-offset), which is what prevents a stale node from being elected leader and silently losing committed data.

**Check Quorum**: a Raft leader that stops hearing from a majority of voters (tracked via a `fetchedVoters` set reset each `checkQuorumTimer` interval, default 1.5x the fetch timeout) must proactively resign rather than assume it's still leader — protects against a leader that's actually on the minority side of a partition continuing to accept writes that will never reach a majority and are doomed to be truncated later. Directly analogous to (and worth reusing in) any custom leader-election implementation: "can still talk to myself" is not sufficient evidence of continued leadership.

**Pull-based (not push-based) replication for the metadata log**: followers periodically send `FetchRequest`s to the leader rather than the leader pushing records out — this is the same shape as normal Kafka partition replication, reused for the metadata log itself. The leader tracks each follower's fetch state in `ReplicaState` objects inside `LeaderState`, and the high watermark only advances once a majority of voters have replicated a given offset (computed in `LeaderState.updateLocalState()`). Pull-based replication naturally handles slow/backpressured followers without the leader needing per-follower flow control logic — a follower just fetches less often or with smaller max-bytes, and the leader doesn't need to know why.

**Snapshots as a log-compaction / bounded-catch-up mechanism for a consensus log**, not just an optimization: `createSnapshot()` returns a `SnapshotWriter` letting the state machine periodically serialize its full current state, after which the underlying Raft log can be truncated. A follower that has fallen too far behind to catch up via normal `FetchRequest`s instead requests the whole snapshot (`FetchSnapshotRequestData`) and installs it wholesale (`handleLoadSnapshot`). Any system replicating an ever-growing log needs an equivalent "coalesce old history into a compact restart point" mechanism or storage grows unboundedly and slow followers become impossible to bring current.

**Idempotent + transactional producers as two escalating layers of exactly-once guarantees**: idempotence alone (every batch tagged with a monotonically increasing per-partition sequence number tied to a `ProducerId`+`Epoch`; the broker discards any batch whose sequence number is ≤ the last one it accepted) solves *duplicate delivery within one producer session* but says nothing about atomicity across multiple partitions. Transactions layer on top: `initTransactions()` fetches a producer ID/epoch, `beginTransaction()` starts local state, the first `send()` to a new partition within the transaction triggers `AddPartitionsToTxnRequest` (registering that partition with the transaction coordinator), and `commitTransaction()`/`abortTransaction()` send `EndTxnRequest`. The `TransactionManager` state machine (`UNINITIALIZED → INITIALIZING → READY → IN_TRANSACTION → COMMITTING/ABORTING_TRANSACTION → READY`) explicitly allows a retriable error during commit to fall back to an abort path rather than leaving the transaction in an undefined state.

**Sticky/adaptive partitioning as a batching optimization, not just load balancing**: the default partitioner doesn't spread records round-robin across partitions by default — it sticks to one partition until that partition's current batch is full or `linger.ms` elapses (maximizing batch fill, hence throughput), then switches. "Adaptive partitioning" goes further, observing per-broker latency and skewing more traffic toward faster-responding brokers. This is a reminder that naive round-robin load distribution can be actively worse for throughput than a "stick with it until it's full" strategy when batching is in play.

**Error classification into `RetriableException` subtypes drives automatic retry, not a blanket catch-and-retry-everything policy**: `NotLeaderOrFollowerException` (leadership moved, refresh metadata and resend), `TimeoutException`, `UnknownTopicOrPartitionException` (stale client-side metadata) are all explicitly retriable and handled transparently inside `Sender` with exponential backoff, bounded overall by `delivery.timeout.ms` as the hard ceiling for how long the client will keep trying before surfacing failure to the application. Distinguishing "this will probably succeed if I just try again with fresh metadata" from "this is a permanent failure" at the exception-type level (rather than a generic retry-on-any-exception loop) avoids masking real bugs as transient blips.

## Practical how-tos

- **Stand up a KRaft cluster from scratch**: run `StorageTool format` on each node's log directories with a shared cluster ID (generate one via `StorageTool random-uuid`) before first startup; use `StorageTool info` afterward to verify formatting matches the running configuration.
- **Diagnose "why isn't my broker taking leadership/traffic"**: check whether it's fenced (missed heartbeats to the controller) before looking at network-level connectivity — a broker can be fully reachable over TCP and still be fenced and therefore ineligible for partition leadership.
- **Reason about a stuck ISR shrink/expand**: inspect whether the partition is in `PendingExpandIsr`/`PendingShrinkIsr` versus `CommittedPartitionState` — a replica can already be serving reads/writes as part of the "maximal" ISR for ack/watermark purposes while the actual committed ISR change is still in flight to the controller; don't assume ISR membership is atomic.
- **Choose classic vs. modern consumer group protocol** for a new client: modern (`ConsumerGroupHeartbeat`, server-side assignment, `AsyncKafkaConsumer`) gives incremental cooperative rebalancing (no stop-the-world pause); classic (`JoinGroup`/`SyncGroup`, client-side assignment) is still the default for older client versions and gives full control over the assignor at the client.
- **Tune producer throughput vs. latency**: increase `batch.size` and `linger.ms` together to trade added per-record latency for larger, more efficient batches; enable idempotence for at-least-once-safe duplicate suppression at negligible cost, and wrap multi-partition atomic writes in a transaction (`initTransactions`/`beginTransaction`/`commitTransaction`) only when cross-partition atomicity is actually required, since it adds coordination overhead (`AddPartitionsToTxnRequest`, `EndTxnRequest` round trips).
- **Debug consumer group sharding**: a group's coordinator partition is deterministic — `abs(groupId.hashCode()) % numPartitions` on `__consumer_offsets` — so the same group ID always maps to the same shard, useful when correlating broker logs to a specific `GroupCoordinatorShard`.

## Gotchas & caveats

- KRaft controllers are not interchangeable with brokers for metadata-quorum purposes — only nodes running the controller role participate in the metadata Raft group as voters; brokers merely read the replicated `__cluster_metadata` log and apply it, they do not vote on it even in combined mode's underlying mechanics (combined mode just colocates both roles in one process).
- `MetadataVersion` gates feature availability across the *whole cluster*, not per-node — `FeatureControlManager` won't finalize a new feature level until the whole quorum supports it, so a rolling upgrade needs every relevant node updated before the new metadata version (and any features gated on it) can be turned on cluster-wide.
- The "maximal ISR" used for high-watermark advancement during a `PendingExpandIsr` window is optimistic — it already includes a replica that hasn't been confirmed by the controller yet. This is a deliberate availability/latency tradeoff, not a bug, but it means "is this replica in the ISR" can have two different correct answers (maximal vs. committed) depending on which decision you're making.
- Returning a resolved `Future<RecordMetadata>` from `send()` does not mean the record is durable in the sense `acks=all` implies — check the specific `acks` configuration in play; `acks=1` returns as soon as the leader appends locally, `acks=-1`/`all` waits for the record to be reflected in the high watermark (i.e., replicated to the full effective ISR) before completing.
- Idempotent producer sequence-number deduplication is scoped to **one producer session** (tied to a specific `ProducerId`+`Epoch`) — it does not protect against duplicates introduced by, e.g., two independently-configured producer instances writing logically-equivalent records; that requires application-level idempotency keys or transactional coordination.
- A transactional producer's commit path can itself fail retriably and fall back to abort (`COMMITTING_TRANSACTION → ABORTING_TRANSACTION` on a retriable error) — application code calling `commitTransaction()` should be prepared for it to actually result in an aborted transaction, not assume commit-or-exception-only semantics.
