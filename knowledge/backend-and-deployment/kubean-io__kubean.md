# Kubean — Distilled Knowledge

## What it is

Kubean is a production-ready Kubernetes cluster lifecycle management toolchain built on top of Kubespray (and designed to support other lifecycle engines like kubekey in future). It is a CNCF sandbox project. It exposes a declarative, Kubernetes-native API (CRDs) for deploying, upgrading, scaling, and resetting Kubernetes clusters — the operator itself runs inside a management cluster and drives Ansible/Kubespray jobs against target hosts over SSH. Distinguishing features per the docs: declarative API via CRDs, comprehensive offline/air-gapped packaging (OS packages, container images, K8s binaries) bundled with each release, AMD64/ARM64 multi-arch support including specialized support for Kunpeng+Kylin, and extensibility (custom pre/post-hook actions) without modifying Kubespray itself. Installed via Helm (`helm install kubean kubean-io/kubean --create-namespace -n kubean-system`).

## Architecture

**Operator pattern with three controllers plus an admission webhook**, all following controller-runtime's reconciliation model:
- `kubean-operator` process hosts: **ClusterOperation Controller** (drives cluster install/upgrade/scale/reset operations), **InfoManifest Controller** (manages `Manifest` CRs — version/compatibility registry), **OfflineVersion Controller** (manages `LocalArtifactSet` CRs — available offline artifacts), and a **Cluster Controller** (manages `Cluster` CR lifecycle).
- `kubean-admission` process hosts the **ClusterOperation Webhook**, a validating admission webhook.

**Core Custom Resources**:
- `Cluster` — represents a managed Kubernetes cluster; `spec.hostsConfRef`/`spec.varsConfRef` point to ConfigMaps (host inventory, Ansible vars), `spec.sshAuthRef` points to a Secret with SSH credentials.
- `ClusterOperation` — defines one operation against a cluster: `spec.cluster` (target), `spec.actionType` (`playbook` or `shell`), `spec.action` (e.g. `cluster.yml`, `upgrade-cluster.yml`, `reset.yml`, `scale.yml`, `remove-node.yml`), `spec.preHook`/`spec.postHook` (arrays of hook actions), `spec.image` (Kubespray container image to run).
- `Manifest` — version-compatibility registry: `spec.kubesprayVersion` (Kubespray git commit hash embedded in this Kubean release), `spec.kubeanVersion`, `spec.docker` (OS-specific Docker version ranges), `spec.components` (per-component `defaultVersion` + descending `versionRange` list, e.g. for `kube`, `calico`, `cilium`, `containerd`, `runc`).
- `LocalArtifactSet` — describes what's actually available in an offline/air-gapped environment: `spec.items` (software + version ranges) and `spec.docker` (OS + version ranges), typically labeled with the Kubespray release it corresponds to.

**ClusterOperation Controller reconcile loop** (the central execution path): check if operation already finished -> try to suspend an existing pod if needed -> fetch the referenced `Cluster` -> validate the container image name -> validate cluster data references (hosts/vars/SSH configmaps+secret exist) -> update owner references -> compute a status "digest" of the ClusterOperation spec to detect if it's been modified since last reconcile -> back up the referenced config data (`BackUpDataRef`) -> generate the entrypoint script and store it as a ConfigMap (`CreateEntryPointShellConfigMap`) -> create the Kubespray Job (`CreateKubeSprayJob`) -> `UpdateStatusLoop` polls job status and reflects it (`Running`/`Succeeded`/`Failed`) back onto the `ClusterOperation` resource, including start/end timestamps.

**Entrypoint script generation** (`pkg/util/entrypoint/entrypoint.go`) is the seam between a declarative CR and an imperative Ansible run: it renders a shell script with three sections — pre-hook commands, the main Kubespray/Ansible command, post-hook commands — built from `spec.preHook`/`spec.action`/`spec.postHook`. Each hook/action can be a **playbook action** (Ansible playbook run through Kubespray) or a **shell action** (raw shell command), and the script assembles proper `ansible-playbook` invocations including private-key auth flags when SSH keys are supplied, plus special flags for destructive operations like `reset`/`remove-node`. The resulting script is mounted into the Kubespray Job pod alongside the hosts config, vars config, and (optionally) SSH key mounts, with configurable resource requests and an `ActiveDeadlineSeconds` execution timeout.

**Admission webhook**: validates every new `ClusterOperation` by listing existing operations against the same target cluster and rejecting the create if one is already running — this is the sole mechanism preventing concurrent conflicting operations on one cluster (there is no separate queueing system; it's a hard reject at admission time).

**InfoManifest Controller**: on each reconcile it lists all `Manifest` resources, then either updates "local service" configuration (for offline/air-gap mode: image repositories, file repositories, YUM/APT repo endpoints, host mappings) or updates locally-available-image information in `Manifest.status`, then requeues after a loop interval. It also maintains a global manifest resource (`constants.InfoManifestGlobal`) as a system-wide default.

**OfflineVersion Controller**: on reconcile it fetches a `LocalArtifactSet`, ensures it carries a `sprayRelease` label (adding a default if missing), finds `Manifest` resources matching that release, and merges the artifact set's availability data into those manifests' status — this is literally how "what's available offline" gets attached to "what version combinations are compatible," letting the ClusterOperation controller later configure jobs using only artifacts actually present.

**Pre-check/validation system** (`playbooks/precheck.yml`) runs (optionally, as its own operation type) before install/upgrade: gathers minimal facts from every target node, checks SSH connectivity (Ansible ping module), detects OS type/kernel version (kernel 4.19+ required for Kubernetes 1.32.0+, checked explicitly with a warn-vs-fail toggle via a "SystemVerification ignored" flag), detects pre-existing Kubernetes/Docker installs, validates dual-stack (IPv4/IPv6) networking, and checks node time synchronization. All checks default to enabled and are individually togglable (`check_connection`, `fetch_os_type`, `check_existing_k8s_service`, `check_existing_docker`, `check_dual_stack_network`, `check_node_time_sync`). Results are consolidated and written to a ConfigMap referenced from the `Cluster` CR (`preCheckRef`), giving a durable, inspectable go/no-go artifact rather than only transient log output.

**Offline/air-gap packaging pipeline**: the CI build workflow generates, per release, four artifact types — container images (tarball, pushed to a container registry, multi-arch manifest lists built per architecture), OS packages (tarball via MinIO), Kubernetes binaries (tarball via MinIO), and OS ISO files (via MinIO) — for both amd64 and arm64 in parallel. Matching `Manifest` and `LocalArtifactSet` CRs are generated alongside the packages and published as release artifacts, together with dedicated import scripts (`import_iso.sh`, `import_images.sh`, `import_files.sh`, `import_ospkgs.sh`) that push each package type into the target air-gapped environment's MinIO/registry.

## Key patterns & techniques (transferable)

- **Version-compatibility as a first-class Custom Resource, decoupled from the controller code**: `Manifest` CRs (with `defaultVersion` + ordered `versionRange` per component) let the project ship new supported-version matrices without a code release — any system managing multi-component compatibility (K8s + CNI + container runtime + OS) can borrow this "compatibility matrix as data" approach instead of hardcoding version logic.
- **Merging two independently-produced CRs to derive availability** (`LocalArtifactSet` "what's present" merged into `Manifest` "what's compatible" by a dedicated controller): cleanly separates "what could work" from "what actually exists in this environment" — useful whenever a system must reconcile a capability catalog against an environment-specific inventory (e.g. air-gapped, restricted, or partially-provisioned deployments).
- **Admission-time mutual exclusion instead of an application-level queue**: rejecting concurrent `ClusterOperation`s on the same cluster at the Kubernetes API admission layer (rather than building custom locking/queueing in the controller) leans on a platform primitive that's already strongly consistent — a good default for any operator managing a resource that must not be touched by two reconciles at once.
- **Uniform hook execution model (pre-hook / main action / post-hook, each either "playbook" or "shell")**: a small, composable action taxonomy that supports both built-in operations and fully custom user-supplied logic through the exact same execution path — a reusable design for any "run something before/after the real work" extensibility point.
- **Config-data backup before execution** (`BackUpDataRef` copies hosts/vars/SSH-secret references before the job runs): guards against a referenced ConfigMap/Secret being mutated mid-operation, ensuring the job that actually ran used a frozen snapshot of its inputs — relevant to any controller whose job spec references external, mutable config objects.
- **Spec-change detection via a status digest** (the controller computes and compares a hash of the ClusterOperation spec to detect modification): a lightweight way to distinguish "this CR changed and needs re-processing" from "this CR was just re-listed by the informer," without depending on `resourceVersion` semantics directly.
- **Explicit warn-vs-fail toggle for environment checks that might be too strict** (kernel-compatibility check has a "SystemVerification ignored" escape hatch): acknowledges that automated pre-flight validation can be a false positive in edge environments, and gives operators an explicit, audited way to proceed anyway rather than forcing them to disable validation wholesale.
- **Durable ConfigMap as the output of a diagnostic pass**, referenced from the owning CR (`Cluster.spec-or-status.preCheckRef`): makes pre-flight results queryable/inspectable after the fact (for troubleshooting a later failure) instead of only existing in ephemeral job logs.

## Practical how-tos

- **Install Kubean**: `helm repo add kubean-io https://kubean-io.github.io/kubean-helm-chart/` then `helm install kubean kubean-io/kubean --create-namespace -n kubean-system` into a cluster with Helm and network access to the target hosts.
- **Deploy a new cluster**: create a `Cluster` CR pointing at ConfigMaps for hosts/vars and a Secret for SSH auth, then create a `ClusterOperation` CR with `action: cluster.yml` and typical `preHook` entries like `ping.yml` (connectivity) and `disable-firewalld.yml`, and `postHook: kubeconfig.yml` to extract credentials afterward.
- **Upgrade a cluster**: create a `ClusterOperation` referencing the same cluster with `action: upgrade-cluster.yml`; pick the target Kubernetes version by selecting a Kubean release whose `Manifest` version range includes it — check the release's default/supported-range table before upgrading, and prefer sequential minor-version upgrades over skipping versions.
- **Scale or remove nodes**: use `ClusterOperation` with `action: scale.yml` (add nodes) or `action: remove-node.yml` (remove nodes), updating the hosts ConfigMap referenced by the `Cluster` CR first.
- **Run pre-flight checks before installing**: create a `ClusterOperation` with `action: precheck.yml`; results land in a ConfigMap referenced by the `Cluster` CR (`preCheckRef`) for review before proceeding.
- **Prepare an air-gapped deployment**: download the release's offline packages (container images, OS packages, K8s binaries, optionally OS ISOs) plus the matching `Manifest`/`LocalArtifactSet` CRs and import scripts, run the appropriate `import_*.sh` script to push them into your internal registry/MinIO, apply the `LocalArtifactSet` CR (pointing at that registry/MinIO endpoint), and then run cluster operations as usual — the OfflineVersion controller will surface only compatible, actually-available versions.
- **Add a custom step to an operation**: define a custom playbook or shell script, reference it as a `preHook`/`postHook`/main `action` entry in the `ClusterOperation` spec — no Kubespray fork required.

## Gotchas & caveats

- Only one `ClusterOperation` can be in flight per cluster at a time — a second concurrent operation is rejected outright by the admission webhook, not queued; plan sequencing of operations (e.g. don't fire an upgrade and a scale simultaneously).
- Kubernetes 1.32.0+ requires kernel 4.19+; the pre-check kernel-compatibility check will fail the operation unless "SystemVerification" is explicitly set to be ignored — don't assume a failed pre-check always blocks; check whether the ignore flag was set.
- Kubean's supported-Kubernetes-version range moves forward with each release and old versions get dropped (e.g. v1.28.x support was dropped going from Kubean v0.19.0 to v0.20.0) — pin the Kubean release to your target Kubernetes version deliberately, don't assume the latest Kubean release supports an older cluster.
- The version-compatibility data (`Manifest`) is generated and distributed from a separate `kubean-manifest` repository via a `sync-manifest.sh` script, not committed directly alongside the main codebase change that motivated it — the manifest and the code that consumes it can be out of sync if that sync step is missed.
- `LocalArtifactSet` entries must carry the correct `sprayRelease` label to be matched against the right `Manifest`; the OfflineVersion controller auto-adds a default label if one is missing, which could silently associate an artifact set with the wrong release if the default doesn't match intent.
- Offline package import is a manual, per-package-type process (four separate scripts for images/files/OS-packages/ISOs) — there is no single one-shot importer, so a partial import (e.g. images but not OS packages) is possible and would only surface as a failure later during an actual cluster operation.
