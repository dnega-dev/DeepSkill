# timescale/timescaledb — Distilled Knowledge

## What it is

TimescaleDB is a PostgreSQL extension that turns PostgreSQL into a time-series database while keeping full SQL compatibility. It adds: automatic partitioning of tables into "hypertables" made of physical "chunks"; columnar compression (90%+ space reduction, per the wiki); continuous aggregates (incrementally-refreshed materialized views for time-series aggregation); time-series-specific query planner optimizations (early chunk pruning, custom scan nodes like `ColumnarScan` and `SkipScan`); and a background-worker policy system for automated compression/retention/refresh jobs. It integrates with PostgreSQL through three hook families: `ProcessUtility` (DDL interception), the planner hook (query optimization), and executor hooks (runtime enhancements/telemetry).

The extension ships as two separately-licensed shared libraries loaded into the same PostgreSQL process: an Apache-2.0 core (`timescaledb.so`, always loaded — hypertables, chunks, dimensions, basic planner hooks) and an optional Timescale-License (TSL) module (`timescaledb-tsl.so` — compression, continuous aggregates, background policies, vectorized execution). At the wiki's snapshot, current dev version is `2.27.0-dev`.

## Architecture (how it's built, key components)

**Dual-license dispatch via a function-pointer struct.** The `CrossModuleFunctions` struct (`src/cross_module_fn.h`) declares function pointers for every TSL-gated capability (compression, continuous-aggregate refresh, background-worker policy management, certain planner hooks). A single global pointer `ts_cm_functions` is initialized at core-extension load time to `ts_cm_functions_default` — a registry of "error stub" functions (`error_no_default_fn_community()` / `error_no_default_fn_pg_community()`) that throw a `FEATURE_NOT_SUPPORTED` error pointing to documentation. If the TSL module is present and loadable, its own `_PG_init()` overwrites `ts_cm_functions` to point at `tsl_cm_functions`, a struct populated with real implementations (e.g. `.compress_chunk = tsl_compress_chunk`). Apache-core code always calls through `ts_cm_functions->some_feature(...)` — it never links directly against TSL code, so the same core binary works whether or not TSL is present, and simply routes to an error or a real implementation depending on what's loaded. Two special-cased exceptions (`compressed_data_in`/`compressed_data_out`, I/O functions) will actively try to load the TSL module before failing, because replication workers need these type I/O functions to exist regardless of whether TSL is fully initialized elsewhere. Licensing is additionally gated by the `timescaledb.license` GUC.

**Hypertable / chunk data model.** A `Hypertable` (in-memory struct wrapping `FormData_hypertable` catalog data) is a logical table that PostgreSQL users interact with normally, but that TimescaleDB internally partitions into `Chunk`s — real physical PostgreSQL tables named `_hyper_<hypertable_id>_<chunk_id>_chunk`, typically in the `_timescaledb_internal` schema. Partitioning is defined by one or more `Dimension`s: **open** (unbounded, typically time — chunks get new time ranges as data arrives) or **closed** (space, fixed number of hash-partitioned buckets, e.g. device_id). All dimensions together form a `Hyperspace` (the N-dimensional space). Each chunk occupies a `Hypercube` — an N-dimensional box built from one `DimensionSlice` per dimension (a 1-D range, e.g. a time interval or a hash-partition range); slices are backed by real PostgreSQL CHECK constraints (`chunk_constraint` catalog rows) so plain constraint exclusion also works even without TimescaleDB-specific planning. All of this metadata lives in the `_timescaledb_catalog` schema: `hypertable`, `dimension`, `chunk`, `dimension_slice`, `chunk_constraint`, `bgw_job`, etc. A hypertable's `compression_state` field tracks 0=off / 1=enabled / 2=internal-compression-table, and `compressed_hypertable_id` links to its shadow "compressed hypertable" (compressed chunks are themselves stored as rows in a differently-shaped internal hypertable — see below).

**Compression: row store → columnar batch store.** Compression transforms a chunk's row-oriented heap storage into a columnar, batch-oriented format where **each row of the compressed table represents a batch of up to ~1000 original rows** (`GLOBAL_MAX_ROWS_PER_COMPRESSION`). Compressed-chunk schema, column by column: `_ts_meta_count` (int4, rows in this batch) → segmentby columns (stored **uncompressed**, original type — rows sharing the same segmentby values are grouped into the same batch) → `_ts_meta_min_N`/`_ts_meta_max_N` (or v2: `_ts_meta_v2_min_<col>`/`_ts_meta_v2_max_<col>`) per orderby column (sparse min/max index enabling batch-skipping on range queries without decompressing) → optional `_ts_meta_v2_bloom1_<col>` bloom-filter sparse index (accelerates equality lookups; auto-created heuristically — GUC-enabled, type must be hashable, excluded for time types since range queries dominate there, excluded for very small types since they already compress well, size threshold >= 4 bytes) → the actual data columns, each stored as an opaque `compressed_data` type, one independently-compressed blob per column per batch. `RowCompressor` (with per-column `PerColumn`/`Compressor` state machines: `append_val`/`append_null` → `is_full` check → `finish()`) drives the row-to-batch transformation.

Seven compression algorithms, auto-selected by column type (`compression_get_default_algorithm`) but overridable:
- **DeltaDelta** (default for `INT2/4/8OID`, `TIMESTAMP[TZ]OID`, `DATEOID`): stores the first value, then delta from previous, then delta-of-delta (second derivative), variable-length encoded — exploits near-monotonic/slowly-changing integer sequences (timestamps, counters, sequence IDs).
- **Gorilla** (default for `FLOAT4/8OID`): XOR each value against the previous one, count leading/trailing zero bits in the XOR result, store only the changed middle bits — exploits gradually-changing floating-point sensor data.
- **Dictionary** (default for `TEXT/VARCHAR/CHAR/NAME/CSTRINGOID`): builds a dictionary of unique values (max 32,767 entries, a compile-time-asserted int16 limit) and stores 16-bit indexes; falls back to Array if cardinality overflows the dictionary.
- **Array**: generic fallback (null bitmap + compressed value array) for any type without a specialized algorithm, or high-cardinality text that overflowed Dictionary.
- **Bool** (default for `BOOLOID`, GUC-gated): 8 booleans packed per byte plus a separate null bitmap — roughly 8:1 over uncompressed booleans.
- **Null** (GUC-gated): detects an all-NULL batch for a column and stores essentially zero bytes.
- **UUID** (default for `UUIDOID`, GUC-gated): exploits UUID structure — for UUIDv7 specifically, the first 6 bytes are a millisecond timestamp and the next 2 bytes carry sub-millisecond precision + version, enabling delta encoding for sequential/time-based UUIDs.

**Continuous aggregates: multi-view materialization + invalidation tracking.** A continuous aggregate (CAgg) is not one object but a small pipeline of views and a hypertable: a user-facing **User View** (what queries actually hit) sits atop a **Partial View** (computes partial/intermediate aggregate states from raw data) and a **Direct View** (preserves the original query definition, used for real-time aggregation), all backed by a **Materialization Hypertable** that physically stores the (partial) aggregate results. Real-time mode (default since TimescaleDB 1.7, controlled by the `materialized_only` flag on the catalog row) unions materialized historical data with a fresh aggregate computed on-the-fly over unmaterialized recent raw data, so queries never see stale results even before the next refresh runs; `materialized_only = true` restricts queries to only the pre-computed materialization table.

*Invalidation tracking* uses three catalog tables: `continuous_aggs_hypertable_invalidation_log` (raw log of all mutated time ranges on a source hypertable, appended to by `continuous_agg_dml_invalidate` on every DML), `continuous_aggs_materialization_invalidation_log` (per-aggregate log, populated by copying/refining entries out of the hypertable-level log), and `continuous_aggs_watermark` (per-aggregate high-water-mark of "materialized up to here"). *Refresh* runs across **two transactions deliberately** to avoid holding catalog locks for a long duration: transaction 1 (short) calls `invalidation_threshold_set_or_get()` and moves entries from the hypertable-level log into the per-aggregate log, then commits; transaction 2 (potentially long) actually executes the materialization SQL (`execute_materialization_plan` for DELETE then INSERT, or a single MERGE if `enable_merge_on_cagg_refresh` is set and the aggregate uses the "finalized" storage format — MERGE only touches changed rows instead of blanket delete+reinsert) and finally advances the watermark. Refresh windows are bucket-aligned two ways: **inscribed** bucketing (shrink the window to only fully-contained buckets — used for manual/policy refreshes, avoids partial-bucket updates) vs **circumscribed** bucketing (expand the window to any bucket that partially overlaps — used when processing raw invalidations, to guarantee nothing affected is missed). A "direct compression" optimization builds the materialization INSERT's `ORDER BY` to match the target's compression segmentby/orderby columns so freshly materialized data compresses cleanly as it lands, rather than requiring a later separate recompression pass.

**Query planning: pre-expansion chunk pruning.** Standard PostgreSQL planning for a partitioned/inherited table expands the full inheritance hierarchy (opens and gathers stats for every child table) and only applies constraint exclusion afterward — expensive at hundreds/thousands of chunks. TimescaleDB inverts this: during query preprocessing (`timescaledb_planner()`), hypertable range-table entries are marked for custom expansion (`ctename = "ts_expand"`, `inh = false`, checked via `ts_rte_is_marked_for_expansion()`) instead of being expanded immediately; a `ts_baserel_info` hash cache (keyed by relation OID) avoids repeated chunk-metadata lookups across the planning pass. Later, in the `timescaledb_set_rel_pathlist` hook, `ts_plan_expand_hypertable_chunks()` runs `collect_quals()` to gather WHERE/join/propagated-outer-join constraints, classifies them by dimension (time vs space vs generic), builds a `HypertableRestrictInfo`, fetches the chunk list, and filters chunks against dimension bounds **before** creating `AppendRelInfo`s and expanding planner arrays — only surviving chunks are ever opened/stat-analyzed. Exclusion logic per operator: `time < value` excludes a chunk if `value <= chunk.range_start`; `time > value` excludes if `value >= chunk.range_end`; equality checks both bounds; space-dimension (hash-partitioned) equality constraints compute `ts_hash_value(value)` and compare against each chunk's hash range (supporting `IN` lists by hashing each value). `time_bucket()` calls wrapping a comparison are algebraically rewritten before exclusion runs (e.g. `time_bucket(10, time) < 100` → `time < 110`; `time_bucket(width, col) > value` → `col > value`) so bucketed queries still get full chunk-pruning benefit instead of forcing a full scan. A separate mechanism, `chunk_column_stats` (enabled via `enable_chunk_skipping()`), extends the same min/max-based exclusion to arbitrary non-partitioning columns. Foreign-key-triggered internal queries (which PostgreSQL issues with `ONLY`, normally preventing hypertable expansion) are specifically pattern-matched (by RTE count, alias names, lock mode, and qual shape) and marked `TS_FK_EXPAND` so FK cascade/check queries still get chunk expansion.

## Key patterns & techniques (transferable knowledge)

- **Function-pointer struct as a runtime dual-license/plugin dispatch mechanism.** Rather than compile-time `#ifdef`s or separate binaries, ship one core binary whose feature-gated call sites always go through a single global struct of function pointers; populate that struct with "error stub" defaults at startup and let an optional module overwrite it if present. This is a general pattern for any "core + optional-plugin" architecture where the core must build and run standalone (open-core products, tiered feature licensing, optional accelerator modules).
- **Columnar batching with a fixed row cap per "row" of physical storage.** Storing ~1000 logical rows as one physical row with per-column compressed blobs plus lightweight per-batch metadata (count, min/max, optional bloom filter) is the standard technique behind most analytical column stores — the metadata lets a scan skip entire batches without touching compressed payload, and the batch-size cap bounds the cost/benefit of decompressing a batch you only partially need.
- **Match compression algorithm to statistical structure of the data, not just its type.** DeltaDelta for monotonic/slowly-incrementing integers, Gorilla's XOR-of-consecutive-values for gradually-changing floats, and dictionary encoding for low-cardinality strings are all exploiting a specific statistical regularity rather than being generic compressors — worth remembering that "best compression for a column" is a question about the data's temporal/statistical pattern, not just its declared type. UUIDv7's structure (embedded millisecond timestamp in the leading bytes) being specifically exploitable is a good example of "know your byte layout" paying off.
- **Sparse/zone-map indexes for batch/block skipping.** Storing coarse per-batch min/max (and optionally bloom filters) alongside compressed data lets a query planner exclude whole batches purely from cheap metadata scans, deferring decompression only to batches that could possibly match — a widely reusable pattern beyond time-series (Parquet row-group stats, ClickHouse skip indexes, etc. use the identical idea).
- **Segmentby vs orderby columns as two different compression roles, not incidental config.** Segmentby columns intentionally stay uncompressed and define batch grouping (rows sharing values are batched together); orderby columns drive sort order within a batch (which is what makes delta/XOR-style encodings effective) and get the min/max sparse index. Recognizing "grouping key" and "sort key" as distinct concerns from "which compression algorithm" is broadly applicable when designing any columnar layout.
- **Pre-expansion constraint pruning instead of post-expansion constraint exclusion.** When a planner/query-engine has to choose among many candidate partitions/shards, analyze constraints *before* materializing per-partition plan nodes rather than materializing all of them and filtering afterward — the cost of "open + stat every candidate" dominates at scale, so moving the filtering step earlier in the pipeline changes complexity from O(all partitions) to O(surviving partitions) for the expensive part.
- **Algebraic rewriting of a wrapped predicate to enable exclusion.** Recognizing `time_bucket(width, col) OP value` and rewriting it to an equivalent `col OP' value'` so constraint exclusion (which only understands raw column comparisons) still fires is a general technique: whenever a helper/wrapper function is monotonic with respect to its argument, its use inside a filter predicate can often be transformed back into a predicate on the bare argument.
- **Two-transaction refresh to bound lock duration.** Splitting a long-running maintenance operation into a short bookkeeping transaction (advance a watermark/threshold, commit quickly) followed by a potentially-long execution transaction (do the actual heavy work under the already-advanced state) is a reusable pattern for any background job that must avoid holding metadata locks for the duration of expensive work.
- **Real-time view = materialized ∪ live-computed-over-recent-raw, unioned transparently behind one user-facing view.** A general "show pre-computed history plus freshly-computed recent data" pattern for any incrementally-materialized aggregate, not specific to continuous aggregates — trading a small amount of per-query computation (aggregating just the not-yet-materialized tail) for always-fresh results without waiting on the refresh cadence.
- **Inscribed vs circumscribed window alignment as two distinct correctness requirements.** When work must be bucketed/aligned but a requested range doesn't fall on bucket boundaries, deliberately choose to shrink (inscribe, for user-initiated partial refresh — never re-touch a bucket outside what was asked) or expand (circumscribe, for invalidation-driven refresh — never leave a partially-invalidated bucket stale) depending on whether under- or over-inclusion is the safe failure mode for that caller.

## Practical how-tos

- **Diagnosing a "functionality not supported" error**: check whether the TSL module actually loaded — if `ts_cm_functions` is still pointing at the default error-stub registry, either `timescaledb.license` excludes TSL or the `timescaledb-tsl` shared library isn't present/loadable; the error message is generated by `error_no_default_fn_community()`/`error_no_default_fn_pg_community()` and should point to relevant docs.
- **Choosing compress_segmentby vs compress_orderby when configuring compression**: segmentby should be the column(s) you'll commonly filter/group by with equality (e.g. device_id) — it stays uncompressed and defines batch boundaries; orderby should be the column(s) whose ordering makes per-batch compression effective (typically the time column) and gets automatic min/max sparse-index metadata for range-query pruning.
- **Improving compression ratio for a low-cardinality text column with unexpectedly poor compression**: check whether cardinality exceeded the Dictionary algorithm's 32,767-entry limit, causing silent fallback to the generic Array algorithm.
- **Speeding up equality lookups against a compressed chunk**: consider `timescaledb.compress_index = 'bloom(<column>)'` (manual) or check whether `ts_guc_auto_sparse_indexes`/`ts_guc_enable_sparse_index_bloom` already auto-created one — bloom sparse indexes specifically target equality, not range, queries.
- **Debugging why a hypertable query is slow to plan (many chunks)**: verify the query's WHERE clause actually provides a constraint the planner can push into chunk exclusion (time or space dimension comparisons, or `time_bucket()`-wrapped comparisons that get rewritten) — queries without an exclusionary predicate force expansion of every chunk.
- **Investigating a stale continuous aggregate**: check `continuous_aggs_watermark` for that aggregate's materialization high-water-mark versus the current time, and check whether `continuous_aggs_hypertable_invalidation_log`/`continuous_aggs_materialization_invalidation_log` have unprocessed entries — a refresh policy that isn't running, or an invalidation threshold that isn't advancing, are the two most likely causes.
- **Deciding between materialized-only and real-time mode**: real-time mode (`materialized_only = false`, the default) is appropriate when queries need up-to-the-moment data; materialized-only trades that freshness for avoiding the per-query cost of aggregating the live tail, useful for high-QPS dashboards querying already-settled historical ranges.

## Gotchas & caveats

- The dual-license dispatch mechanism means Apache-only builds can silently fail on TSL-gated SQL functions with a generic-looking error rather than a missing-function error — always check whether TSL is expected to be loaded before assuming a bug in feature logic itself.
- Compressed batches cap at roughly 1000 rows (`GLOBAL_MAX_ROWS_PER_COMPRESSION`) — very wide or unusual segmentby cardinality patterns can produce many small batches, reducing compression efficiency; segmentby choice materially affects batch size distribution, not just filter performance.
- Dictionary compression has a hard 32,767-unique-value ceiling (signed int16 index) and falls back to Array silently — a column expected to compress well via dictionary encoding but with runaway cardinality growth over time can degrade compression ratio without any error being raised.
- Segmentby columns are explicitly NOT compressed — choosing a high-cardinality or large-payload column as segmentby defeats much of the point of compression, since that column's bytes are stored per-batch, uncompressed, original type.
- The refresh mechanism's two-transaction design means a crash or cancellation between transaction 1 (threshold/log update) and transaction 2 (materialization) can leave the invalidation log advanced without the corresponding data actually materialized — treat refresh as needing to be re-triggerable/idempotent rather than assuming atomicity across the whole refresh.
- `time_bucket()`-wrapped predicate rewriting only fires for recognized comparison shapes; predicates that don't match the expected transformation patterns don't benefit from chunk pruning even though they're logically equivalent to ones that would.
- Foreign-key-triggered internal queries use `ONLY`, which normally blocks TimescaleDB's custom hypertable expansion — this is specifically pattern-matched and special-cased (`TS_FK_EXPAND`); a custom FK-adjacent query shape that doesn't match the recognized patterns could silently fail to get proper chunk exclusion, degrading (not breaking) performance on FK-adjacent hypertables.
- Direct-compression-on-materialization only applies when the target continuous aggregate has compression enabled AND uses the "finalized" storage format required for `PLAN_TYPE_MERGE` — older-format continuous aggregates fall back to the less efficient DELETE+INSERT materialization path.
