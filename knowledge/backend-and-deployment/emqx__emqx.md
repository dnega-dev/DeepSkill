# EMQX — Distilled Knowledge

## What it is

EMQX is a high-performance, distributed MQTT broker for IoT, written in Erlang. A single cluster is described as supporting over 100 million concurrent connections with millions of messages/second at sub-millisecond latency. It fully implements MQTT 5.0/3.1.1/3.1, adds MQTT-over-QUIC transport (via the `quicer` library, for faster connection setup and seamless migration on unstable networks), and supports additional IoT protocols (CoAP, LwM2M, MQTT-SN, STOMP, ExProto/gRPC) through a pluggable gateway framework. Clustering is masterless (no single point of failure). As of v5.9.0, all Open Source and Enterprise features were unified under a single Business Source License (BSL) 1.1 offering. Built as an Erlang/Elixir umbrella project — many independent OTP applications sharing one build/release process.

## Architecture (how it's built, key components)

**Layered pipeline, one Erlang process per connection.** Transport (`emqx_listeners` spawning `emqx_connection` for TCP/TLS, `emqx_ws_connection` for WebSocket, `emqx_quic_stream`/`emqx_quic_connection` for QUIC) → Protocol/Channel (`emqx_channel`, embedding all MQTT protocol logic as a record inside the connection process — not a separate process) → Session (`emqx_cm` channel manager registers the process; session logic dispatches to `emqx_session_mem` in-memory or `emqx_session_ds` durable) → Routing (`emqx_broker` local pub/sub, `emqx_router` Mnesia-backed distributed routing table) → Integration (`emqx_rule_engine` → `emqx_bridge`/`emqx_connector` → external systems). Configuration flows in via `emqx_conf` (HOCON), management via `emqx_dashboard`/`emqx_mgmt` REST API.

**Boot sequence is topologically sorted, not hardcoded**: `emqx_machine:start/0` starts clustering (`ekka`) first, then `emqx_machine_boot` computes a dependency graph over all business applications (`sorted_reboot_apps/0`) and starts them via `application:ensure_all_started/1` in dependency order. Some "soft"/runtime dependencies aren't declared in `.app` files and are injected manually during boot rather than relying on OTP's own dependency resolution. A small set of apps (`mria`, `ekka`, `esockd`, `emqx`) are "permanent" — if any fails to start, the whole node shuts down, versus other business apps which may fail more gracefully. Shutdown is the mirror image: `emqx_machine_terminator` stops applications in reverse startup order before halting the VM. A restricted Erlang shell (`emqx_restricted_shell`) blocks dangerous console operations (like `init:stop()`) while still allowing normal debugging — a deliberate safety rail on an otherwise very powerful live-debugging surface (the Erlang remote shell).

**Per-client actor model**: `emqx_connection` is deliberately *not* a `gen_server` — it's built directly on `proc_lib:spawn_link` running a custom `recvloop/2` receive loop, presumably for lower overhead than the generic `gen_server` machinery given how many of these processes may exist simultaneously (potentially 100M+). Lifecycle: `start_link` spawns → `init` waits for the transport handshake (`Transport:wait(RawSocket)`, handles TLS) → `init_state` collects `peername`/`sockname`/`peercert` and calls `emqx_channel:init()` to build the embedded protocol state → `run_loop` arms the socket and an idle timer (closes the connection if no CONNECT arrives in time) → `recvloop` blocks in `receive`, dispatching every message through `process_msg/2` → `handle_msg/2`. The process hibernates when idle to reduce per-connection memory footprint, and a GC tracker forces garbage collection after every N (`ActiveN`) packets received — an explicit tradeoff of periodic GC pauses against unbounded heap growth across millions of long-lived lightweight processes.

**Channel Manager (`emqx_cm`) is the cluster-wide identity registry and takeover coordinator**, using multiple ETS tables for fast lookup: `emqx_channel` (ClientId→pid), `emqx_channel_info` (attributes/stats), `emqx_channel_conn` (connection module/pid). MQTT's "only one active connection per ClientId" rule is enforced here via an explicit **takeover** protocol: `takeover_session_begin/1` initiates it, `takeover_kick/1` forcibly closes the old connection, and the old session's state (subscriptions, inflight window) is transferred into the new channel process rather than starting fresh — this is what lets a reconnecting IoT device resume mid-stream instead of losing unacknowledged messages.

**Session behavior abstraction cleanly separates "what a session does" from "how it's stored.**" `emqx_session` defines a behavior (Erlang's interface mechanism) with callbacks `create/4`, `open/4` (resume existing), `subscribe/3`, `publish/3`, `deliver/3`, `replay/3` (retransmit unacked messages on reconnect) — implemented identically-shaped by both `emqx_session_mem` (state lives in the channel process heap: `subscriptions` map, `inflight` window via `emqx_inflight`, `mqueue` via `emqx_mqueue` for buffering when offline/inflight-full, `awaiting_rel` for QoS2 handshake state) and `emqx_persistent_session_ds` (durable, backed by the `emqx_ds` storage layer). The channel layer only ever talks to the `emqx_session` interface, never to a concrete implementation directly — swapping ephemeral for durable sessions is a config choice, not a code branch in the channel.

**Pub/sub engine splits node-local dispatch state (ETS) from cluster-wide routing state (Mnesia), and further splits exact-match routes from wildcard routes.** Node-local ETS: `emqx_suboption` (`{TopicFilter,SubPid}`→SubOpts), `emqx_subscriber` (`Topic`→`[SubPid]`, bucketed for high-fanout topics), `emqx_subscription` (`SubPid`→`TopicFilter`). Cluster-replicated Mnesia: `emqx_route` (exact-topic routes, a `bag`), `emqx_route_filters` (wildcard routes indexed via `emqx_topic_index`, an `ordered_set` for trie-like prefix search), `emqx_routing_node` (which nodes have active routes), `emqx_shared_subscription`. Subscribe path: channel calls `emqx_broker:subscribe` → local ETS inserts happen synchronously → if this is the topic's first local subscriber, a route-add is pushed asynchronously through `emqx_router_syncer` (which **batches** route mutations before committing to Mnesia — smoothing out write amplification when many subscribes/unsubscribes happen in a burst) → `emqx_router` performs the actual Mnesia insert. Publish path: `emqx_broker:publish` → `emqx_router:match_routes(Topic)` (exact lookup in `?ROUTE_TAB` plus trie search in `?ROUTE_TAB_FILTERS` via `emqx_topic_index:matches/3`) → for each matched route, either local dispatch (ETS subscriber lookup, with high-fanout topics partitioned into fixed-size buckets — e.g. 1024 — and optionally dispatched asynchronously via a `dispatcher_pool` when `async_fanout_shard_dispatch` is enabled) or forwarded to `emqx_shared_sub` for shared-subscription topics.

**Shared subscriptions decouple "who gets this message" from plain fan-out**: multiple clients subscribe to the same `$share/Group/Topic`, and exactly one member of the group receives each message, selected per a configurable strategy: `random`, `round_robin`, `sticky` (reuse the last pick per-publisher for locality), `local` (prefer same-node subscribers to avoid cross-node hops), `hash_clientid`, `hash_topic`. If delivery to the chosen member fails for a QoS1 message, it can be redispatched to another group member when `shared_dispatch_ack_enabled` is set — this is essentially a competing-consumers pattern layered on top of MQTT pub/sub, directly analogous to a message-queue consumer group.

**Router cluster-membership cleanup is asymmetric between node types**: `emqx_router_helper` monitors `ekka` membership events; when a *replicant* node departs, its routes are automatically purged after a 15-minute timeout, but *core* (Mnesia-writer) nodes are never auto-purged — they must be explicitly evicted from the cluster. This reflects a deliberate trust asymmetry: replicants are treated as disposable/replaceable, cores are treated as authoritative and their departure must be a deliberate operator action, not something inferred from a timeout.

**Persistent (durable) sessions solve replay by persisting stream-replay-state, not by persisting the messages redundantly.** `emqx_persistent_session_ds` implements *both* the `emqx_session` behavior (so the channel layer can use it like any session) and a separate `emqx_ds_client` behavior (for consuming from the durable storage layer). Rather than storing per-session copies of messages, it persists small "Stream Replay State" (`#srs`) records — a DS iterator position plus sequence-number ranges — for each active durable-storage stream the session is consuming. On reconnect, the session re-fetches the exact same batch from the shared `emqx_ds` store using that iterator, and reconstructs the identical packet-ID-to-message mapping it had before disconnecting, rather than needing its own private copy of in-flight messages. This is a memory/storage-efficient design: N sessions all subscribed to the same busy topic share the same underlying durable log, and each only needs to remember "where was I" (small, O(1)-ish state), not "here's a full copy of everything I hadn't acked yet."

## Key patterns & techniques (the transferable knowledge)

**Chain-of-responsibility with a three-way (allow/deny/ignore) result, used for both authentication and authorization, structurally identical in both subsystems.** For AuthN (`emqx_authn_chains`): providers (Mnesia/built-in DB, HTTP, LDAP, Redis, JWT, ...) are tried in configured order; a provider returns `ignore` if it's simply inapplicable to this request (e.g., a password-based provider seeing a request with no password field — move to the next provider), `{ok, Extra}` to allow (stops the chain, `Extra` can carry `is_superuser` and other derived attributes), or `{error, Reason}` to explicitly deny (also stops the chain). For AuthZ (`emqx_authz`): sources are evaluated the same way — `allow`/`deny` stop the chain, `ignore` falls through to the next source, and if the *entire* chain is exhausted with no match, a global `no_match` setting (default `deny`) is the final fallback. This three-state result (rather than a plain boolean) is the key structural idea: it lets each check in the chain honestly say "I have no opinion" versus "I have an opinion and it's negative" versus "I have an opinion and it's positive," which is what makes composing independent, order-sensitive security checks tractable without each one needing to know about every other one in the chain.

**Chains are reorderable and mutable at runtime, not fixed at startup**: `emqx_authn_chains` exposes `create_authenticator/2` and `move_authenticator/3` as first-class operations — the ordered list of security providers is itself a piece of live-editable configuration, not a compiled-in sequence, which is what lets an operator add/remove/reprioritize an auth backend without a restart.

**HTTP-delegated auth as a general integration technique**: `emqx_authn_http` treats an arbitrary external HTTP service as an authentication backend by templating the outgoing request (`body_template`, `base_path_template` rendered with client variables like username/clientid) and interpreting the response purely by HTTP status + a `result` field in the body — `204 No Content` means allow outright, `200 OK` requires parsing the JSON/form body and checking `result == "allow"`. This is a minimal, protocol-agnostic contract for delegating a yes/no security decision to any external system without needing a bespoke SDK or client library per backend.

**Actor-per-connection with explicit takeover, rather than shared connection pooling**, is the concurrency model of choice for a protocol (MQTT) where "exactly one live connection per identity, but the old one might still think it's alive when the new one arrives" is a first-class protocol requirement. The takeover-then-kick sequence (register new, explicitly terminate old, transfer state) is a clean pattern for any system needing to guarantee single-writer/single-owner semantics per logical entity when the old owner may not have gracefully disconnected.

**Router batching (`emqx_router_syncer`) as a write-amplification smoothing layer**: rather than writing every subscribe/unsubscribe directly to the replicated Mnesia routing table (expensive per-write due to replication), route mutations are pushed to a syncer process that batches them before committing. This is the same "batch before the expensive replicated write" idea Kafka's producer applies to network sends — worth generalizing to any system where you control both a cheap local operation and an expensive replicated/networked one and can decouple their cadence.

**Splitting a matching problem by pattern shape (exact vs. wildcard) into separate data structures** (`?ROUTE_TAB` — a plain key lookup — versus `?ROUTE_TAB_FILTERS` — a trie/prefix-index via `emqx_topic_index`) rather than one generic structure that handles both is a recurring performance technique: exact matches are the overwhelmingly common case and deserve O(1) lookup; wildcard matches are rarer and can afford the extra cost of a trie traversal. Don't force every match request through the most general (and slowest) data structure just because it's capable of handling all cases.

## Practical how-tos

- **Add a new auth backend**: implement the small three-outcome contract (`{ok, Extra}` / `{error, Reason}` / `ignore`) against the `emqx_authn` (or `emqx_authz_source`) behavior, register it into the chain via `create_authenticator/2`, and place it at the desired position with `move_authenticator/3` — no changes needed to the core connection/channel code.
- **Debug a "duplicate connection" / "client keeps getting kicked" issue**: check `emqx_cm` for takeover activity — if a `ClientId` connects while a previous connection under the same ID is still registered, EMQX will always kick the old one; this is by design, not a bug, so look for two devices/processes sharing one ClientId rather than assuming broker misbehavior.
- **Debug unexpected message loss for a QoS1/2 subscriber**: check the session's `inflight` window and `mqueue` state — messages are enqueued in `mqueue` when the inflight window is full or the client is offline, and `mqueue` has configurable bounds (`max_mqueue_len`) and an explicit choice about whether to even buffer QoS0 (`mqueue_store_qos0`) — a full queue silently drops messages per its configured policy, it doesn't block the publisher.
- **Choose shared-subscription dispatch strategy**: use `local` when cross-node hops matter for latency, `sticky` when a given publisher's messages benefit from consistent downstream handling (e.g., stateful processing keyed by publisher), `hash_clientid`/`hash_topic` when deterministic (reproducible) assignment matters more than load evenness.
- **Reason about persistent session behavior on reconnect**: the exact packet IDs a client sees after reconnecting are reconstructed from the same underlying durable-storage batch via the persisted `#srs` iterator state, not from a separately-stored copy of "your pending messages" — so a very long-disconnected client replaying a large backlog is re-fetching from the same shared durable log every other subscriber to that stream is also reading from, not paying an isolated storage cost.
- **Investigate a route not propagating cluster-wide**: check whether the change is still sitting in the `emqx_router_syncer` batch window before assuming Mnesia replication itself is broken — route writes are intentionally batched, so there's a bounded but real point of latency between "subscribe call returned" and "route visible cluster-wide."

## Gotchas & caveats

- `emqx_connection` bypasses `gen_server` entirely (`proc_lib` + custom receive loop) — debugging/instrumentation tooling built assuming standard `gen_server` behavior (e.g., generic process-introspection helpers that expect `gen_server` callbacks) may not work against connection processes without adjustment.
- Core (Mnesia-writer) nodes are **never** automatically purged from the routing table on departure — only explicit eviction removes them; a core node that crashes and never comes back will leave stale routing state indefinitely unless an operator intervenes, unlike replicant nodes which self-clean after 15 minutes.
- The GC-after-every-N-packets tracker (`ActiveN`) is a deliberate periodic-pause-vs-heap-growth tradeoff — under very bursty traffic this means predictable small GC pauses are traded for bounding per-connection memory, which is the right call at scale but can look like odd micro-latency jitter if you're not aware it's happening by design.
- Authentication chain evaluation stops at the first non-`ignore` result — a misconfigured earlier provider that unexpectedly returns `{error, ...}` instead of `ignore` for a credential shape it doesn't actually understand will incorrectly deny access before later, correctly-applicable providers ever get a chance to evaluate the same request.
- Persistent sessions share the underlying durable storage stream across subscribers — the tradeoff for that storage efficiency is that the session's replay state is only a *position* into someone else's shared log, not its own private buffer, so any question about "what exactly will I receive on replay" needs to be answered in terms of the DS iterator/sequence-number state, not a simple mental model of "my personal message queue."
- Shared-subscription redispatch on QoS1 failure only happens if `shared_dispatch_ack_enabled` is explicitly turned on — with it off, a failed delivery to the chosen group member is not automatically retried against another member, which can silently look like message loss under load if the operator assumed redispatch was default behavior.
