# Keycloak — Distilled Knowledge

## What it is

Keycloak is an open-source Identity and Access Management (IAM) system providing authentication, authorization, and user management. It is a large monorepo combining a Java backend (Jakarta EE, RESTEasy Reactive, Hibernate ORM) running on the Quarkus runtime, and a JavaScript frontend monorepo (React 18, TypeScript, PatternFly 5, Vite, pnpm workspace) for its Admin UI and Account UI applications. It supports OpenID Connect (OIDC), OAuth 2.0, and SAML 2.0 as both an Identity Provider and (via brokering) a client/relying-party to external IDPs. Persistence uses JPA + Liquibase across multiple database vendors (PostgreSQL, MariaDB, MySQL, Oracle); distributed session state and caching use Infinispan.

## Architecture (how it's built, key components)

**Four architectural layers**: (1) **Frontend** — Admin UI (`js/apps/admin-ui`, client ID `security-admin-console`, builds into `theme/keycloak.v2/admin`) and Account UI (`js/apps/account-ui`, client ID `account-console`, builds into `theme/keycloak.v3/account`), both depending on shared libraries `ui-shared` and `keycloak-admin-client`; these are modern React replacements for the legacy FreeMarker-based admin consoles. (2) **Backend Services** — the `services` Maven module holds REST API implementations, authentication flow processing (`AuthenticationProcessor`), and protocol implementations (`OIDCLoginProtocol`, SAML), built on the `core` module for token handling and crypto. (3) **Quarkus Runtime** — `KeycloakProcessor` performs build-time optimization (a Quarkus "build step" pattern: heavy reflection/classpath-scanning work happens once at native-image/build time rather than per-request), and `KeycloakRecorder` executes the recorded bytecode at runtime to initialize `QuarkusKeycloakSessionFactory`. (4) **Infrastructure** — feature flags (`Profile` system), Infinispan caching/clustering, database connection management (`DefaultJpaConnectionProviderFactory`) and schema migration (`LiquibaseJpaUpdaterProviderFactory`).

**Provider SPI pattern (the core extensibility mechanism)**: nearly every subsystem is defined as an SPI (Service Provider Interface) with a default implementation swappable via configuration — e.g. `IdentityProvider` SPI (external IDP brokering), `LoginFormsProvider` SPI (implemented by `FreeMarkerLoginFormsProvider`), `UserProfileProvider`, `UserStorageProvider` SPI (for LDAP/AD federation), `CryptoProvider` SPI. Providers are obtained per-request via `session.getProvider(SomeProvider.class)` from the `KeycloakSession`, which acts as a request-scoped service locator/registry for the whole SPI ecosystem. This is the load-bearing design that lets Keycloak be embedded/customized without forking — new auth mechanisms, storage backends, or token formats plug in as additional SPI implementations rather than core code changes.

**REST API layered resource pattern**: Admin REST resources follow a strict collection→item hierarchy — e.g. `UsersResource` (`/admin/realms/{realm}/users`, handles search/list/create) delegates to `UserResource` (`/admin/realms/{realm}/users/{user-id}`, handles single-entity CRUD, sessions, credentials, role mappings) via `@Path("{user-id}")`. The same pattern repeats for `GroupsResource`/`GroupResource`, `ClientsResource`/`ClientResource`. `RealmAdminResource` is the entry point delegating to all realm-scoped sub-resources. A newer "Admin API v2" (currently scoped to client management) introduces `PATCH`-based JSON Merge Patch updates and a `BaseClientRepresentation` base type with protocol-specific subtypes (`OIDCClientRepresentation`, `SAMLClientRepresentation`) rather than one monolithic representation class — a cleaner OO alternative to a single "kitchen sink" DTO holding fields for every possible protocol.

**Permission evaluation is centralized per-resource-type, not scattered inline**: every admin REST operation calls into an `AdminPermissionEvaluator`, which exposes per-domain sub-evaluators (`UserPermissionEvaluator`, `GroupPermissionEvaluator`, `ClientPermissionEvaluator`, etc.) with intention-revealing methods like `auth.users().requireManage(user)`, `auth.users().requireView(user)`, `auth.users().requireQuery()`, `auth.clients().requireConfigure(client)`. A failed check throws `ForbiddenException`. This "require*" naming convention (throw-on-failure guard methods, one per capability, scoped to a specific object instance) is a clean pattern for expressing fine-grained per-object authorization checks without duplicating the underlying policy logic inline in every handler.

**Login/registration/2FA pages are server-rendered via FreeMarker**, not React: `FreeMarkerLoginFormsProvider` (implementing the `LoginFormsProvider` SPI) is the central class handling every user-facing auth page (login, registration, password reset, TOTP setup, required actions). It maps a `LoginFormsPages` enum value to a `.ftl` template file and a "Bean" class supplying template variables (e.g. `LOGIN`→`login.ftl`+`LoginBean`, `OAUTH_GRANT`→`oauth-grant.ftl`+`OAuthGrantBean`). `createResponse(page)` loads the realm's theme, resolves locale/message bundle, populates page-specific bean attributes, then calls `processTemplate()`. Common attributes populated for every page include `client` (`ClientBean`), `realm` (`RealmBean`), `social` (`IdentityProviderBean`, drives "login with Google/Facebook" buttons), `url` (`UrlBean`), `auth` (`AuthenticationContextBean`).

**Required Actions** are a distinct mechanism from the login flow itself: post-authentication tasks a user must complete before being fully logged in (e.g. `UPDATE_PASSWORD`, `VERIFY_EMAIL`, `CONFIGURE_TOTP`, `UPDATE_PROFILE`), each mapped to its own template and triggered by `AuthenticationManager.checkRequiredActions()` → `LoginActionsService` → `FreeMarkerLoginFormsProvider.createResponse(RequiredAction)`. This separates "did the credentials check out" from "is the account in a fully-usable state," letting policies force password resets or profile completion independent of the primary auth mechanism.

## Key patterns & techniques (the transferable knowledge)

**OIDC token endpoint as a grant-type dispatcher**: `TokenEndpoint` is the single entry point for all OAuth2/OIDC grant requests (`POST /token`, `application/x-www-form-urlencoded`). It performs client authentication (`client_secret_basic`, `client_secret_jwt`, `private_key_jwt`), then dispatches by the `grant_type` parameter to a specific `OAuth2GrantType` implementation (`AuthorizationCodeGrantType`, `RefreshTokenGrantType`, `TokenExchangeGrantType`, `JWTAuthorizationGrantType`, etc.), each of which calls into a shared `TokenManager` to actually mint signed JWTs. This is a clean "one endpoint, strategy-pattern dispatch on a discriminator field" design directly analogous to Pydantic's discriminated unions or a plugin registry — worth reusing whenever multiple mutually-exclusive request shapes hit one endpoint.

**Sender-constrained tokens (DPoP, RFC 9449)**: rather than a bare bearer token (stealable and replayable by anyone who intercepts it), DPoP binds a token to a private key the client holds. Flow: client sends a `DPoP` header containing a self-signed JWT proof with `htu` (target URL), `htm` (HTTP method), and its public key; `DPoPUtil.Validator` checks the proof against the actual request; on success, Keycloak injects a `cnf` (confirmation) claim containing the JWK thumbprint into the issued access token via a transient protocol mapper. Later requests bearing that token must present a matching DPoP proof again, or the request is rejected — the resource server can verify possession, not just presentation. Token Exchange (RFC 8693) additionally checks that if a `subject_token` is sender-constrained, the exchange is rejected unless the requesting client matches the token's `azp` (authorized party) — closing a hole where a stolen sender-constrained token could otherwise be laundered into an unconstrained one via exchange.

**Backchannel logout is a server-to-server push, not just a redirect**: besides RP-initiated (front-channel redirect-based, using `id_token_hint`) and session-cookie-based logout, Keycloak implements OIDC Back-Channel Logout — a `logout_token` (a specialized JWT with an `events` claim and *no* `nonce`, per spec) is POSTed directly server-to-server to registered clients, letting a client immediately invalidate a session even without an active browser tab for that user. Useful reference for any multi-service logout/session-invalidation design where "the user might not have a browser open right now" is a real constraint.

**Discovery documents are generated dynamically, not hand-maintained**: `OIDCWellKnownProvider` builds `.well-known/openid-configuration` by inspecting which features are actually enabled (CIBA, Device Flow, DPoP, etc.) and current realm settings — the discovery document can never drift out of sync with reality because it's computed from the same feature-flag state the server itself uses to decide what to accept, rather than being a separately maintained static file.

**SAML brokering security validation is layered, not a single signature check**: `SAMLEndpoint` (acting as SP/broker) runs incoming assertions through `DestinationValidator` (does the `Destination` attribute match this actual endpoint URL — prevents assertion replay against the wrong endpoint), `ConditionsValidator` (checks `NotBefore`/`NotOnOrAfter` time-window constraints), and `XMLSignatureUtil` (cryptographic signature verification) as three independent checks, any of which can reject the assertion. Supports three bindings with different trust models: HTTP-Redirect (URL-encoded query param — size-limited, no confidentiality), HTTP-POST (base64 in a hidden form field — larger payloads, browser-mediated), HTTP-Artifact (browser carries only an opaque reference; actual SAML message is fetched via a direct backchannel SOAP call — avoids exposing the full assertion to the browser/URL at all).

**Fine-Grained Admin Permissions (FGAP) reuses the general-purpose authorization engine for the admin console itself**: rather than a separate hardcoded RBAC system for "who can manage which realm objects," Keycloak's own Authorization Services framework (Resource/Scope/Policy/Permission model — the same one exposed to application developers for their own APIs) is applied internally via `AdminPermissionsSchema`, which declares standard `ResourceType`s (`Users`, `Groups`, `Clients`) and their scopes (e.g. `IMPERSONATE` for `Users`). This is "eat your own dogfood" applied to an authorization framework: don't build a bespoke permission system for your own admin surface if you already have a general one — apply it to itself.

**Multi-tier caching split by data volatility/scope, not one cache for everything**: Infinispan caches are explicitly split into **local** (per-node, not replicated — `realms`, `users`, `authorization`, `keys` with 1hr TTL, `crl`) versus **distributed** (clustered, sharded across nodes — `sessions`, `clientSessions`, `offlineSessions`, `authenticationSessions`, `loginFailures`, `actionTokens`) versus **replicated** (`work` — cache-invalidation messages sent to every node). Local caches are invalidated via messages broadcast on the `work` cache when the underlying DB record changes on any node — a cheap way to get read-mostly, rarely-changing config data fast without needing full replication, while session data (which genuinely needs cross-node visibility for failover) pays the distributed-cache cost. Session caches also persist to the database as the ultimate source of truth, so Infinispan is a performance layer, not the only copy.

## Practical how-tos

- **Add a new resource server-side integration**: implement the `IdentityProvider` SPI (extending `AbstractIdentityProvider`) for the new protocol/vendor; register a `performLogin` (builds the outbound auth request) and a `callback` (handler for the IDP's response, populating a `BrokeredIdentityContext` that gets mapped to a local user).
- **Query/search admin resources**: use `search` (general text match across common fields), `q` (advanced `key1:value1 key2:value2` attribute query, parsed by `SearchQueryUtils.getFields()`), `first`/`max` for pagination, `briefRepresentation` to reduce payload size on list endpoints.
- **Trace an authorization decision**: an admin REST call reaches its resource handler → calls `auth.<domain>().require<Capability>(entity)` → internally consults `AdminPermissionEvaluator` → domain-specific evaluator (`UserPermissionEvaluator` etc.) → policy evaluation against the `StoreFactory`/`PolicyEvaluator` → `ForbiddenException` on denial.
- **Debug a failed SAML login via broker**: check, in order, whether the assertion's `Destination` matches the actual endpoint (`DestinationValidator`), whether it's within its validity window (`ConditionsValidator`, `NotBefore`/`NotOnOrAfter`), and whether the signature verifies (`XMLSignatureUtil`) — these are independent failure points, not a single pass/fail signature check.
- **Configure sender-constrained tokens**: enable DPoP on the client (`isUseDPoP`); clients must then send a `DPoP` header with every token request and every resource request using that token, or the server rejects with `invalid_dpop_proof`.
- **Extend user attribute validation**: hook into `UserProfileProvider` — `UsersResource`/`UserResource` create a `UserProfile` from raw attributes and validate it against the realm's configured profile policy before persisting.
- **Audit an admin action**: every mutating admin operation logs through `AdminEventBuilder` (e.g. `.operation(OperationType.UPDATE).resourcePath(...).representation(rep).success()`), giving a queryable audit trail without needing to add logging calls manually in each handler.

## Gotchas & caveats

- Admin API v2 currently only covers client management — don't assume `PATCH`/JSON-Merge-Patch semantics or the `BaseClientRepresentation` hierarchy are available for other resource types (users, groups) yet; those remain on the original v1 monolithic-representation API.
- Backchannel logout tokens have a specific required shape (`events` claim present, `nonce` claim absent) per the OIDC Back-Channel Logout spec — a `logout_token` that includes a `nonce` should be treated as invalid, which is the opposite of normal ID token validation where `nonce` is often expected.
- DPoP enforcement is per-client (`isUseDPoP`) — a client not configured to require DPoP will happily accept bare bearer tokens, so sender-constraining must be deliberately enabled per client rather than being a realm-wide default.
- Token exchange rejects sender-constrained subject tokens unless the requesting client matches the original token's `azp` — don't assume any authenticated client in the realm can freely exchange any valid token; DPoP/mTLS-bound tokens have an additional ownership check baked into the exchange path.
- Local Infinispan caches (`realms`, `users`, `authorization`, `keys`) are per-node and only kept consistent via invalidation messages on the `work` cache — a network partition or lost invalidation message can leave a node serving stale cached realm/user data until the next natural cache eviction or restart; this is a real consistency-window tradeoff traded for read performance, not full linearizability.
- The frontend Admin UI/Account UI are separate React apps from the legacy FreeMarker-rendered login/registration pages — customizing the *login* experience (branding, extra fields) means touching FreeMarker templates and theme resources, not the React codebase, even though the rest of the admin experience has moved to React.
