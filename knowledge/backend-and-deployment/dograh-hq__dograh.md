# Dograh (dograh-hq/dograh) — DeepWiki Knowledge Distillation

## What it is

Dograh AI is an open-source, self-hostable voice AI agent platform positioned as an alternative to proprietary tools like Vapi and Retell. It lets developers build conversational voice agents via a drag-and-drop workflow builder (`@xyflow/react`), then deploy them across multiple telephony providers (Twilio, Vonage, Vobiz, Cloudonix, Telnyx, Plivo, Asterisk/ARI) or browser-based WebRTC calls. It's built on the **Pipecat** framework for real-time audio/LLM orchestration, is provider-agnostic for LLM/STT/TTS (bring-your-own-key or Dograh's managed services), and includes campaign management for bulk outbound dialing with retry logic and circuit breakers. Stated goal: zero to a working bot in under 2 minutes; current version at time of wiki generation was 1.35.0.

## Architecture

**Containerized multi-service stack** (Docker Compose): Next.js 15+ UI (port 3010) → Nginx reverse proxy → FastAPI backend (port 8000, business logic + pipeline orchestration) → PostgreSQL (pgvector/pgvector:pg17, workflows/runs/campaigns via SQLAlchemy) + Redis 7 (task queue, pub/sub, rate limiting) + MinIO (S3-compatible storage for call audio) + Coturn (TURN/STUN server for WebRTC NAT traversal). ARQ background workers consume Redis-queued jobs; a `campaign_orchestrator` and `ari_manager` run as separate singleton processes (not multiplexed across FastAPI workers) for campaign dispatch and Asterisk integration respectively.

**Transport-agnostic pipeline core**: telephony (`run_pipeline_telephony`) and WebRTC (`run_pipeline_smallwebrtc`) entry points both converge on a single `_run_pipeline` core function. Each transport has its own `AudioConfig` (Twilio/ARI/Cloudonix use 8kHz MULAW; Vonage/WebRTC use 16kHz PCM), but the internal pipeline is capped at 16kHz max to stay compatible with the `SileroVADAnalyzer` — transports handle resampling if the wire format is higher (e.g. WebRTC browser audio is often 48kHz).

**Two pipeline shapes** assembled by `pipeline_builder.py`:
- **Standard** (discrete STT/LLM/TTS): Input → STT → (Voicemail detector) → User Context Aggregator → LLM → Callback Processor → Recording Router → TTS → Output → Audio Buffer → Assistant Aggregator.
- **Realtime** (speech-to-speech, e.g. OpenAI Realtime or Gemini Live): Input → User Aggregator → Realtime LLM → (Voicemail) → Callback Processor → Output → Audio Buffer → Assistant Aggregator — simplified because the realtime service handles STT/TTS internally.

**`PipecatEngine`** (in `api/services/workflow/pipecat_engine.py`) is the conversational brain sitting between the abstract `WorkflowGraph` and the live Pipecat pipeline. It owns: current-node state, LLM context composition per node (Jinja2-rendered system prompts combining a global node's instructions + the current node's instructions + call context vars), function/tool registration (built-in, transition, custom, knowledge-base), variable extraction coordination, call lifecycle (graceful `EndFrame` vs immediate `CancelFrame` termination), and interruption control (`should_mute_user()` checks three flags: teardown-in-progress, queued-transition-speech-in-progress, and bot-speaking-with-`allow_interrupt=False`).

**Workflow as a validated directed graph**: the visual builder emits a `ReactFlowDTO` (Pydantic-validated JSON) which is converted into a runtime `WorkflowGraph` of `Node`/`Edge` objects. Node types: `startCall` (exactly one required, no incoming edges, handles greeting/pre-call fetch/delayed start), `agentNode` (standard conversational state), `endCall` (termination + disposition capture), `globalNode` (shared instructions prepended everywhere, no outgoing edges), `webhook`, `trigger` (public inbound API entry), `qa` (post-call analysis config). Every outgoing edge from the current node is converted into an LLM-callable "goto" function; `Edge.get_function_name()` sanitizes the edge label into a valid identifier via regex.

**Dual-channel real-time communication for browser calls**: a WebSocket channel (`/api/v1/ws/signaling/{workflowId}/{workflowRunId}`) carries SDP/ICE signaling and live feedback JSON, while a separate WebRTC/RTP channel carries actual audio. Signaling deliberately uses WebSocket (not HTTP PATCH) so it works correctly across multi-worker FastAPI deployments where in-memory peer-connection maps can't be shared between processes.

## Key patterns & techniques

**Service factory pattern for AI providers**: `service_factory.py` reads `user_config.stt.provider` / `.tts.provider` / `.llm.provider` and instantiates the matching Pipecat service class (Deepgram, OpenAI, Cartesia, ElevenLabs, Groq, Google, etc.), including a `DograhSTTService`/managed fallback. All TTS services get wrapped with an `XMLFunctionTagFilter` so the bot never speaks raw function-call XML tags aloud. Realtime (speech-to-speech) providers get special handling: OpenAI Realtime uses an `ExternalUserTurnStartStrategy` since the provider emits its own speaking-state signals; Google/Gemini Live keeps a local `SileroVADAnalyzer` running alongside server-side VAD for early user-turn-start tracking.

**Transcription self-correction via reference-text alignment**: because some TTS providers (e.g. ElevenLabs) can corrupt the text that gets echoed back for transcript aggregation, the engine tracks the actual LLM generation text (`_current_llm_generation_reference_text`) and runs a two-pointer scan (`correct_corrupted_aggregation`) to re-align corrupted aggregated text against the known-good reference — a documented workaround for a specific vendor quirk rather than a generic algorithm.

**Recording-router marker protocol**: LLM output can embed special marker characters that a `RecordingRouterProcessor` intercepts before TTS — `●` (`RECORDING_MARKER`) suppresses live TTS and plays a pre-recorded audio clip instead, letting a node mix scripted/compliance audio with dynamically generated speech in the same conversational turn.

**Transition-speech-then-switch, not switch-then-speak**: when the LLM calls a transition ("goto") function with accompanying speech text, the engine queues a `TTSSpeakFrame` for that speech *before* calling `set_node()`, and uses `FunctionCallResultProperties` with an `on_context_updated` callback to guarantee the LLM sees its own prior tool-call result in context before generating the next turn — avoiding a race where the model could reference a node it hasn't "arrived" at yet.

**Two-tier context model**: `_call_context_vars` (immutable, set at call start from `WorkflowRunModel.initial_context` — CSV campaign columns beyond `phone_number`, telephony variables like `{{caller_number}}`, built-in time variables with timezone suffix support e.g. `{{current_time_America/New_York}}`) versus `_gathered_context` (mutable, accumulates `nodes_visited`, `call_disposition`, and LLM-extracted variables throughout the call, persisted to the run record and available in webhook payloads). A **pre-call data fetch** step can enrich `initial_context` with an HTTP POST to an external CRM/ERP before the agent starts speaking (10s timeout), looking for the payload under `initial_context` or the legacy `dynamic_variables` key.

**Per-node variable extraction runs on a separate "inference LLM"**: because realtime speech-to-speech services may not support arbitrary structured-output inference calls, `PipecatEngine` keeps a distinct `inference_llm` reference used only for out-of-band tasks (variable extraction, context summarization, QA) — the primary conversational `llm` never has to double as a structured-extraction model. The `VariableExtractionManager` builds a formatted conversation-history text (stripping tool-response metadata like `status`/`status_code`, truncating any tool response over 2000 chars) before firing the extraction call.

**Provider abstraction via an ABC with a registry+factory**: `TelephonyProvider` defines the mandatory interface (`initiate_call`, `get_call_status`, `validate_config`, `verify_webhook_signature`, `get_webhook_response`, `parse_status_callback`, `handle_websocket`, `configure_inbound`, etc.); seven concrete classes (Twilio, Vonage, Vobiz, Cloudonix, ARI, Telnyx, Plivo) implement it. `get_telephony_provider_by_id()` loads a `TelephonyConfigurationModel` row, normalizes it with associated phone numbers, and instantiates the class from a registry lookup — the standard multi-tenant "load config from DB, dispatch by string key to class" pattern. Inbound webhook matching (`find_telephony_config_for_inbound`) keys off provider name + `account_id`, falling back to the org's default config for providers with no account-id concept (like ARI).

**Campaign call dispatching uses `SELECT FOR UPDATE SKIP LOCKED`** to let multiple background workers safely claim batches of queued calls from the same campaign without double-processing — the standard Postgres pattern for horizontally-scaled work-queue consumers. Concurrency and rate limits (`CONCURRENT_CALL_LIMIT`, calls/second) are enforced via Redis-based Lua scripts for atomic slot acquisition and sliding-window counting; phone-number-pool allocation spreads outbound traffic across multiple caller IDs.

**Circuit breaker implemented as a Redis sliding window with a Lua script**: `CircuitBreaker.record_call_outcome()` writes each outcome into `cb_failures:{campaign_id}` / `cb_successes:{campaign_id}` ZSETs, trims entries outside the window (`ZREMRANGEBYSCORE`), and does O(1) `ZCARD` counting — all inside one atomic Lua script to avoid race conditions across concurrent dispatcher workers. Trips when `total >= min_calls_in_window AND failures/total >= failure_threshold`; a capped list of up to 20 recent failures (`cb_recent_failures:{campaign_id}`) is retained for operator diagnostics. A tripped breaker pauses the campaign; `CampaignRunnerService.resume_campaign()` explicitly resets the breaker state on manual resume.

**Retry-as-child-queued-run**: failed calls (busy/no-answer/voicemail, per configurable flags) spawn a new `QueuedRunModel` row linked to the parent via `parent_queued_run_id` rather than mutating the original row — giving a clean audit trail of retry chains and enabling infinite-loop prevention. Redial campaigns similarly track lineage via `orchestrator_metadata["parent_campaign_id"]` and skip source re-sync, jumping straight to `running`.

**Zero-downtime deploys via a dual-band blue-green port strategy** (not container orchestration): `rolling_update.sh` runs Uvicorn workers on one of two fixed port bands (Band A: `8000+w`, Band B: `8100+w`; active band tracked in a `run/active_band` file) and cycles through: run Alembic migrations → start new-band workers → poll `/api/v1/health` on every new worker until 200 OK (default 30 attempts, 2s interval) → regenerate the Nginx upstream config and `nginx -t && systemctl reload nginx` to atomically cut traffic to the new band → send `SIGTERM` to old-band workers and wait up to `DRAIN_TIMEOUT` (default 300s) for in-flight WebRTC/WebSocket calls to finish before `SIGKILL` → restart non-multiplexable singleton services (`ari_manager`, `campaign_orchestrator`, `arq` workers) sequentially, since those don't support running two live instances at once. Any phase failure (health check, Nginx config test) triggers `rollback_new_workers()`, which `SIGKILL`s the new band's PIDs and exits with the old band still serving traffic. Nginx is configured with `least_conn` load balancing specifically because long-lived WebSocket connections don't distribute evenly under round-robin.

## Practical how-tos

- **Add a new telephony provider**: implement the `TelephonyProvider` ABC in `api/services/telephony/providers/<name>/provider.py`, register it in the provider registry/factory, and add its config schema to the discriminated union in `telephony_config.py`.
- **Give an agent a custom action**: create a Tool row (HTTP API, End Call, Transfer Call, Calculator, or MCP category) via the tools UI/API; `CustomToolManager` converts it to a `FunctionSchema` at call time and calls `llm.register_function()`. HTTP tools support Jinja2-templated `preset_parameters` referencing `initial_context`/`gathered_context`, plus optional credential-based auth header injection.
- **Debug why the bot muted the user unexpectedly**: check the three `should_mute_user()` conditions — call teardown in progress, a queued transition speech not yet finished playing, or the current node has `allow_interrupt=False` while the bot is speaking.
- **Trace a call's decision path for QA**: `realtime_feedback_events` carry `node_id` per segment; post-call QA (`run_per_node_qa_analysis`) splits the transcript by node, generates a summary of what each node should have accomplished, and evaluates each segment against `qa_system_prompt`, threading a `previous_conversation_summary` between sequential nodes for continuity. Results trace to Langfuse.
- **Roll out a code change with zero downtime on a bare-metal/VM deployment**: run `scripts/rolling_update.sh`, which handles migrations, band switch, health-gating, and graceful draining automatically — do not restart Uvicorn directly, since that will drop in-flight calls and skip the Nginx atomic cutover.

## Gotchas & caveats

- The internal pipeline sample rate is hard-capped at 16kHz regardless of transport, purely because `SileroVADAnalyzer` requires it — a provider offering higher-fidelity audio (WebRTC at 48kHz) still gets downsampled before VAD/STT.
- `ari_manager`, `campaign_orchestrator`, and `arq` workers are architecturally singleton per-host processes that do NOT support the dual-band multiplexing used for the FastAPI/Uvicorn tier — a rolling update has to sequentially restart them (brief interruption), unlike the HTTP tier's zero-downtime swap.
- WebRTC signaling was deliberately built on WebSocket instead of the more common HTTP PATCH-based ICE trickling specifically because a multi-worker FastAPI deployment can't share an in-memory peer-connection map across processes — any contribution reverting to HTTP-based signaling would break horizontal scaling.
- Rolling back a remote/Docker deployment via saved `.bak.<timestamp>` files does not automatically reverse database migrations — schema changes applied by a bad update stay applied even if the code is rolled back.
- The realtime (speech-to-speech) pipeline variant requires a distinct `inference_llm` for out-of-band tasks; conflating the primary realtime LLM with the extraction/summarization LLM is explicitly called out as unsupported because realtime services may not expose standard structured-output inference.
- `PhoneNumberPoolExhaustedError` handling in campaign dispatch fails the whole campaign after only 3 exhaustion attempts (`MAX_PHONE_NUMBER_POOL_EXHAUSTED_ATTEMPTS`) — a small number pool under a large campaign can halt dispatch quickly.
