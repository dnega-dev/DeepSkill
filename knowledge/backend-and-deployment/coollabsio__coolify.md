# Coolify — Distilled Knowledge

## What it is

Coolify is a self-hosted application deployment platform (open-source alternative to Heroku/Netlify/Vercel) built with Laravel 12 that orchestrates Docker-based applications, databases, and services across multiple servers via SSH. It runs as a centralized control plane (PostgreSQL + Redis + Laravel Horizon) while workloads execute on decentralized, user-controlled infrastructure reached over SSH. Current stable version: 4.0.0-beta.463. Backend: PHP 8.4 / Laravel 12, Livewire 3.7 for the primary UI, Vue 3.5 for stateful widgets (terminal), Vite 7.3 build, Tailwind CSS 4.1, PostgreSQL for state, Redis for queues/broadcast (via Soketi/Echo), Laravel Horizon for background job supervision.

## Architecture

**Layered flow**: Livewire Components (UI) -> Laravel Actions (`app/Actions/`) -> Queue Jobs (`app/Jobs/ApplicationDeploymentJob.php` etc.) -> Remote Helpers (`bootstrap/helpers/remoteProcess.php`) -> `SshMultiplexingHelper` (persistent SSH sockets) -> remote Docker Engine. State lives in PostgreSQL (Eloquent models); Sentinel agents push metrics back into the control plane.

**Resource hierarchy** (strict 4-level multi-tenancy chain): `Team` (isolation boundary, owns Servers/S3Storage/Projects, RBAC roles Owner/Admin/Member via pivot table) -> `Project` (logical grouping, auto-creates a "production" `Environment` and `ProjectSetting` on creation) -> `Environment` (deployment stage, e.g. Production/Staging; holds direct FKs for Applications/Databases/Services) -> `Application`/`Database`/`Service` (the actual workload, `morphTo` a `Destination`). Team ID 0 is the "Root Team," exempt from Cloud-mode subscription/server limits.

**Server model** (`app/Models/Server.php`): represents an SSH-connected host; server ID 0 is special-cased as "localhost" (where Coolify itself runs). Each server has 1:1 `ServerSetting` (health flags: `is_reachable`, `is_usable`, `force_disabled`), M:1 `PrivateKey`, and 1:N `StandaloneDocker`/`SwarmDocker` "destinations" (deployment targets). Lifecycle hooks: `saving()` trims/normalizes IP and tracks `ip_previous`; `saved()` calls `refresh_server_connection()` if the private key changed (clears stale mux sockets); `created()` bootstraps a default `ServerSetting` and a Docker destination. An **identity map** (`Server::findCached($id)` / static cache) avoids N+1 queries when many resources reference the same server in one request; `flushIdentityMap()` runs on `updated()`.

**SSH execution layer**: Coolify never opens a fresh SSH connection per command. `SshMultiplexingHelper` implements OpenSSH `ControlMaster`: a background master connection (`ssh -fNM`) is established once per server and a Unix socket at `/storage/app/ssh/mux/mux_{uuid}` is reused (`-o ControlPath`) by every subsequent command; connection age is tracked in Laravel Cache and refreshed/closed (`ssh -O exit`) when expired or unhealthy. Two execution helpers wrap this: `remote_process()` (async, dispatches through `PrepareCoolifyTask`, backs deployments/long jobs with `Activity` logging) and `instant_remote_process()` (synchronous, returns output immediately, used for quick checks). Both are wrapped in `SshRetryHandler`/`SshRetryable`, which matches ~40 known transient SSH error patterns (e.g. `kex_exchange_identification`, "Connection reset by peer") and retries with exponential backoff (`retry_base_delay` x `retry_multiplier`, capped by `ssh.max_retries`, default 3). Private keys are stored encrypted in the DB and materialized to disk at `/storage/app/ssh/ssh_key@{uuid}` with `0600` permissions only when needed.

**Server provisioning**: onboarding is a Livewire state machine (`Boarding\Index`): welcome -> select server type (localhost / remote-by-IP / Hetzner Cloud) -> SSH key select/generate -> create Server record -> `ValidateAndInstall` pipeline: `validateConnection()` (`ls /` over SSH) -> `validateOS()` (parses `/etc/os-release`; supports debian/rhel/sles/arch) -> `validatePrerequisites()` (installs `curl`, `wget`, `git`, `jq` if missing) -> `validateDockerEngine()`/`validateDockerVersion()`. `InstallDocker` action backs up `daemon.json`, merges required `json-file` logging config (10m max size), restarts Docker, and creates the `coolify` (standalone) or `coolify-overlay` (swarm) network. Validation allows up to 3 retries and persists failures to `validation_logs`. Hetzner Cloud integration (`HetznerService`) can create the VM directly via API, wiring in the chosen SSH key.

**Proxy management**: a dedicated `coolify-proxy` container (Traefik v3.x or `lucaslorentz/caddy-docker-proxy`) is the single HTTP/HTTPS entry point per server. `Server::setupDynamicProxyConfiguration()` generates dynamic routing config (Traefik: `coolify.yaml` with routers for `coolify-http`/`coolify-https`/websocket endpoints; Caddy: `coolify.caddy` with `reverse_proxy` directives) so Coolify's own UI/websockets are routed through the same proxy as user apps. `setupDefaultRedirect()` configures catch-all behavior (redirect to a URL, or 503) for unmatched requests — for Traefik this is a `catchall` router at priority `-1000`. `RestartProxyJob` sequences stop -> `ensureProxyNetworksExist()` -> `docker compose up -d --wait` -> `connectProxyToNetworks()` (reconnecting the proxy container to every network any routed app uses, discovered via `collectDockerNetworksByServer()`). A separate job (`CheckTraefikVersionForServerJob`) detects the running Traefik version from the remote compose file and compares it to `versions.json` to notify of available updates. Cloudflare Tunnel is supported as an alternative ingress path for servers without public IPs.

**Monitoring (dual-mode)**: (1) push-based — a lightweight `coolabsio/sentinel` agent container runs on each server (deployed via `StartSentinel`, authenticated with a per-server `sentinel_token`), posts container/system stats to `/api/v1/sentinel/push`, and `Server::sentinelHeartbeat()` updates `sentinel_updated_at`; a server is "Sentinel Live" if the last push was within `sentinel_push_interval_seconds * 3` (min 120s). (2) polling-based fallback — `ServerCheckJob` connects via SSH (`docker ps`) for servers without Sentinel, and separately verifies/restarts the `coolify-proxy` container if it's missing and not intentionally stopped. `ContainerStatusAggregator` maps Docker container states + health checks (e.g. `running:healthy`) back to Coolify resources using labels like `coolify.applicationId`; if one container in a multi-container Service is down, the aggregate resource status reflects it. Log draining to New Relic/Axiom/Highlight/custom Fluentbit-Vector config runs via a `coolify-log-drain` sidecar container, also supervised by `ServerCheckJob`.

**Deployment queue** (Laravel Horizon + Redis): every deployment request creates an `ApplicationDeploymentQueue` row (status `QUEUED`/`IN_PROGRESS`/`FINISHED`/`FAILED`/`CANCELLED_BY_USER`; fields include `deployment_uuid`, `commit`, `pull_request_id` — 0 for normal, N for PR previews — `force_rebuild`, `restart_only`). `queue_application_deployment()` is the single entry point and enforces three concurrency levels before dispatching `ApplicationDeploymentJob`: (1) **server queue limit** — default 25 `QUEUED` rows per server, else returns `queue_full` (surfaced as HTTP 429 with `Retry-After` on webhooks); (2) **per-application concurrency** — only one active deployment per `(application_id, pull_request_id)` pair, so normal deploys and PR-preview deploys of the same app can run in parallel with each other but not with themselves; (3) **server concurrent-builds limit** — configurable `concurrent_builds` cap on simultaneous `IN_PROGRESS` deployments per server. Cancellation sets status to `cancelled-by-user` and calls `next_after_cancel()`, which walks the server's queued deployments in creation order and dispatches the first one that still satisfies the concurrency checks.

**Build strategies**: `ApplicationDeploymentJob::decide_what_to_do()` branches on `restart_only` -> PR deploy -> inline Dockerfile -> `build_pack` (`nixpacks` default/auto-detect, `static` for SPAs via nginx:alpine with SPA 404->index.html rewriting, `dockerfile` with configurable location/target/context for multi-stage builds, `dockercompose` for multi-container stacks, `dockerimage` to skip building and pull a pre-built tag). Docker Compose deployments parse `docker_compose_raw` with `Yaml::parse`, inject Coolify-specific labels/networks via `validateDockerComposeForInjection`, and assign per-service domains. Build-time secrets flow through `EnvironmentVariable` rows flagged `is_build_time`, written to a temp `.env` or passed as `--build-arg`. If an app targets multiple servers or a Swarm cluster, the built image is pushed to a registry so other nodes can pull it rather than rebuilding locally.

**Backup system**: `ScheduledDatabaseBackup` (cron `frequency`, S3 toggle, `disable_local_backup`, retention by amount/days/max-storage-GB) is checked every minute by the Console Kernel scheduler, which dispatches `DatabaseBackupJob`. That job detects DB type + credentials via `docker exec ... env` on the running container, runs the type-specific dump (`pg_dump`/`pg_dumpall`, `mysqldump`/`mariadb-dump`, `mongodump`) over SSH, tracks each run in `ScheduledDatabaseBackupExecution` (status/size/duration), optionally uploads to an S3-compatible `S3Storage` (team-scoped, reusable across projects), and deletes the local copy if local backups are disabled. Restore (`Import` component) supports upload, an absolute server path, or picking an existing S3 object, with strict validation against shell metacharacters (`$(`, `|`, `;`) in bucket/path inputs before they reach a shell command. General-purpose `ScheduledTask` (non-backup cron jobs against a running container) explicitly disables SSH multiplexing (`disableMultiplexing: true`) to avoid race conditions between concurrent task runs sharing a socket.

## Key patterns & techniques (transferable)

- **SSH ControlMaster multiplexing as the backbone of a remote-orchestration control plane**: one persistent master socket per managed host, reused via `-o ControlPath` for every command, with age/health checks that trigger transparent re-establishment — avoids the latency and resource cost of a fresh TCP+SSH handshake per remote operation, which matters a lot when a control plane issues dozens of commands per deployment.
- **Three-tier concurrency gate before dispatching a background job** (global-per-server queue cap -> per-entity mutual exclusion -> per-server concurrent-execution cap): a clean, reusable structure for any system that must prevent both unbounded queue growth and resource contention on a shared execution target, while still allowing safe parallelism (e.g., prod vs. PR-preview deploys of the same app).
- **Static identity-map cache scoped to a model class** (`Server::findCached`/`flushIdentityMap`) as a lightweight N+1 mitigation when the same row is looked up repeatedly within one request — cheaper than eager-loading everywhere, invalidated explicitly on update.
- **Dual-mode monitoring (push agent + polling fallback) with an explicit liveness window derived from the push interval** (`interval * 3`, floor 120s): gives resilience against agent failure without hardcoding a single "is it alive" threshold independent of configured push frequency.
- **Command-injection defense applied at multiple layers for the same input** (regex validation on write, `escapeshellarg()` at command-construction time, stripping dangerous characters again on the Eloquent `saving` hook): defense-in-depth for any system that interpolates user input into shell commands over a remote-execution channel.
- **Encrypt-at-rest, materialize-on-demand secret handling for SSH keys**: private keys live encrypted in Postgres and are only ever written to a locked-down (`0600`) filesystem path when a connection actually needs them — reduces the attack surface of long-lived plaintext key material on disk.
- **Strict hierarchical multi-tenancy (Team -> Project -> Environment -> Resource) with cascading auto-bootstrap** (creating a Team seeds notification channels; creating a Project seeds a default "production" Environment): removes a class of "orphaned/half-configured resource" bugs by making structural invariants a side effect of creation, not a manual follow-up step.
- **Explicitly disabling a shared-resource optimization (SSH multiplexing) for a specific job class prone to races** (`ScheduledTaskJob` sets `disableMultiplexing: true`): a concrete example of not applying a performance optimization universally when it conflicts with a correctness requirement (concurrent independent task runs).
- **Registry push-on-multi-target-build**: rather than rebuilding an image independently on every target server/Swarm node, build once and push to a registry so other nodes pull — a standard but important pattern for keeping multi-node deployments byte-identical and build time bounded.

## Practical how-tos

- **Self-host Coolify**: `curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash` on the control-plane host; Coolify Cloud is the managed alternative with HA and support.
- **Add a remote server**: go through the Boarding onboarding wizard — pick "remote" server type, provide/generate an SSH key, enter connection details; Coolify validates connectivity, OS, prerequisites (curl/wget/git/jq), and installs Docker automatically if missing, retrying up to 3 times.
- **Enable metrics for a server**: toggle Sentinel in server settings; this deploys the `coolabsio/sentinel` container with a generated `sentinel_token`, `PUSH_INTERVAL_SECONDS`, and retention config — changing these settings auto-restarts Sentinel via the `ServerSetting` `updated` hook.
- **Choose a build strategy**: set `build_pack` on the Application to `nixpacks` (zero-config, most languages), `dockerfile` (custom multi-stage builds), `dockercompose` (multi-container stacks), `static` (SPA/static sites via nginx), or `dockerimage` (pull pre-built image) depending on the source repo.
- **Configure a database backup**: create a `ScheduledDatabaseBackup` with a cron `frequency`, choose retention by count/days/max-size, optionally enable S3 upload and local-delete-after-upload; monitor individual runs in `BackupExecutions`.
- **Restrict deployment concurrency on a resource-constrained server**: lower `ServerSettings.concurrent_builds` (level-3 gate) and/or `deployment_queue_limit` (level-1 gate, default 25) in server settings.
- **Route external traffic through Coolify's proxy for a self-hosted app not managed by Coolify**: add a dynamic Traefik/Caddy config via the "Dynamic Configurations" UI, which is written into the same `dynamic/` directory the `coolify-proxy` container watches.

## Gotchas & caveats

- Server ID 0 is hardcoded as "localhost" (the machine running Coolify itself) — logic branches on this ID in several places (network assignment, Cloudflare Tunnel UI availability), so it is not just a convention but load-bearing application logic.
- SSH multiplexing sockets must be explicitly torn down (`refresh_server_connection()`) when a server's private key changes, or stale connections using the old key will linger.
- The three concurrency levels are independent: a per-application deploy can be blocked by the server-wide `concurrent_builds` cap even if that specific application has no other deployment running — don't assume "my app isn't deploying" implies "my app is misconfigured."
- `disableMultiplexing: true` is deliberately used only for `ScheduledTaskJob`; assuming multiplexing is always-on when writing new remote-execution code paths could reintroduce the race condition it was added to avoid.
- Root Team (ID 0) bypasses subscription/server-limit checks in Cloud mode — a detail relevant to anyone reasoning about Coolify's multi-tenancy or billing enforcement.
- Backup restoration commands accept user-provided S3 paths/bucket names; the wiki explicitly documents regex and shell-metacharacter validation as a hardening measure, implying this was a real injection-risk surface addressed defensively rather than by construction.
