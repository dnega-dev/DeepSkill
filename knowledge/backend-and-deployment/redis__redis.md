# redis/redis — Distilled Knowledge

## What it is

Redis is an in-memory data structure server: strings, lists, sets, sorted sets, hashes, streams, HyperLogLog, bitmaps, geospatial indices, and (as of the 8.x line documented here) Vector Sets (HNSW-based similarity search) and a new sparse Array type. All data lives in RAM for sub-millisecond access; optional durability comes from RDB point-in-time snapshots and an Append-Only File (AOF) write log. Historically single-threaded for command execution, modern Redis (8.x) adds multi-threaded I/O and memory prefetching to raise throughput without abandoning the single-threaded execution model for command logic itself. The server entry point is `main()` in `src/server.c`, which initializes one global `struct redisServer server` (defined in `src/server.h`, hundreds of fields), loads configuration, and starts the event loop.

## Architecture (how it's built, key components)

**Global state and core structs.** Everything hangs off the single global `server` variable: `redisServer` (event loop pointer, database array, client list, command table, replication/persistence/cluster/memory/module state), `redisDb` (per-database `kvstore *keys` plus an `estore *expires` for expiring keys and, new in 8.x, `ebuckets *hexpires` for per-hash-field expiration), `client` (per-connection query/output buffers, argv/argc, ACL state, IO-thread assignment), `kvobj` (the object representation — a specialized `robj` that in 8.x supports embedded keys and metadata bits, e.g. for expiration, at negative offsets from the object pointer instead of separate allocations), and `redisCommand` (name, proc pointer, flags, subcommand dict).

**Event loop (`ae.c`).** A single-threaded, non-blocking reactor over platform-specific multiplexers (`ae_epoll.c` on Linux, `ae_kqueue.c` on BSD/macOS, `ae_evport.c` on Solaris, `ae_select.c` as universal fallback), chosen at compile time. `aeEventLoop` tracks an array of `aeFileEvent`s (indexed by fd, mask `AE_READABLE`/`AE_WRITABLE`), a linked list of `aeTimeEvent`s, and a `beforesleep`/`aftersleep` hook pair. Main loop: `aeMain()` repeatedly calls `beforeSleep()` → `aeProcessEvents()` (computes the shortest wait until the next timer, polls via the platform backend, dispatches fired file events, then runs any expired time events) → implicit `afterSleep()`. `beforeSleep()` is where a lot of "outside the strict callback model" work happens: flushing the AOF buffer, cluster state/failover checks, unblocking clients that were waiting on keys/modules, and handing client sockets off to IO threads. `afterSleep()` refreshes cached time/metrics right after waking from the poll call. The single most important time event is `serverCron` (frequency set by `hz`, default `CONFIG_DEFAULT_HZ` = 10): active TTL expiration, incremental dict rehashing, stats updates, and the replication cron (master-replica timeout/ACK bookkeeping).

**Multi-threaded I/O.** `server.io_threads_num` background threads (`iothread.c`) can take over socket reads, RESP parsing into argv, and writing output buffers, while the main thread remains the sole executor of command logic. Client state (`client.tid` = assigned IO thread, `client.running_tid` = thread currently touching it, `client.pending_read`/`pending_write` atomics) coordinates handoff between main and IO threads. This is additive to, not a replacement of, the single-threaded event loop for command execution — it targets the I/O-bound parts of the pipeline specifically.

**Command processing pipeline (one event-loop iteration per non-blocking command).** (1) `readQueryFromClient` (the registered `aeFileEvent` read handler) reads bytes into `client->querybuf` (or a thread-local reusable buffer when `querybuf` is NULL, to reduce allocation churn for short requests). (2) `processInputBuffer` runs a small state machine over two wire formats: `PROTO_REQ_INLINE` (plain space-separated line, e.g. for telnet) via `processInlineBuffer`, or `PROTO_REQ_MULTIBULK` (standard RESP) via `processMultibulkBuffer`, which tracks `client->multibulklen` (args remaining) and `client->bulklen` (current arg's byte length) across possibly-multiple socket reads until `argc`/`argv` are fully populated. (3) `processCommand` looks up `client->argv[0]` in `server.commands` (a dict, case-insensitive); `isCommandReusable()` skips the dict lookup entirely when the previous command on the same client was the same single-word command. (4) Pre-execution checks in a fixed order: command-found → arity check → authentication (`authRequired`) → ACL permission check → OOM check → cluster slot-ownership routing (`getNodeByQuery`, when `cluster_enabled`). (5) For pipelined/`MULTI`-queued commands, `memory_prefetch.c` can prefetch the memory for upcoming commands' keys while the current one executes, cutting cache-miss stalls. (6) `call()` in `server.c` is the actual dispatch point: sets `server.current_client`, invokes `cmd->proc(c)`, and propagates the write to AOF/replicas if the command mutated data. (7) Replies are written to `client->buf` (fixed-size, `PROTO_REPLY_CHUNK_BYTES`) and overflow into a linked list of `clientReplyBlock`s (`client->reply`); actual socket writes happen in `beforeSleep` via `handleClientsWithPendingWrites`, falling back to registering `sendReplyToClient` as a writable-event handler if the socket buffer is full.

**Dictionary (`dict.c`) — the core hash table.** Separate chaining, power-of-two bucket counts (`1 << ht_size_exp[i]`). Every `dict` actually holds **two** hash tables (`ht_table[0]`, `ht_table[1]`) to support **incremental rehashing**: normally only `ht_table[0]` is live; when a resize is triggered (`_dictExpandIfNeeded`, based on load factor), `ht_table[1]` is allocated and `rehashidx` set to 0, and `dictRehash()` migrates a bounded number of buckets per call (capped search length of `n*10` if it hits a long run of empty buckets, to bound worst-case latency) rather than all at once; once `ht_used[0]` hits zero the tables swap and the old one is freed. Rehashing can be explicitly paused (`dictPauseRehash`) during iteration to avoid duplicating or skipping entries mid-scan. A `dictType` supplies pluggable `hashFunction`/`keyCompare` plus flags: `no_value` (dict behaves as a pure set, storing no value — used with a slimmer `dictEntryNoValue` struct that omits the value union) and `keys_are_odd` (an optimization enabling pointer tagging). **Pointer tagging**: because `zmalloc` returns 8-byte-aligned pointers, the low 3 bits of any pointer are always zero; Redis reuses those bits directly in a bucket slot to distinguish a normal `dictEntry*` (`000`) from a directly-embedded odd-address key pointer (`XX1`) or an encoded even-address key pointer (`010`) — avoiding a full `dictEntry` allocation for single-item buckets in cases like sets. `kvobj` further folds metadata (expiration, etc.) into negative-offset bytes before the `robj` header rather than a separate allocation; `dictType.keyFromStoredKey` lets a lookup use a bare SDS key while the table actually stores the richer `kvobj`.

**kvstore — multi-dictionary container.** `kvstore` wraps an array of `dict`s and is the backing structure for both per-database keyspaces and cluster hash-slot sharding. It maintains a Fenwick tree of cumulative per-dict key counts for O(log N) fair random-dictionary sampling (`kvstoreGetFairRandomDictIndex` — needed e.g. for eviction/expiration sampling across shards with skewed key distribution), coordinates incremental rehashing budgets across all its constituent dicts (`kvstoreIncrementallyRehash`), and can allocate individual dicts lazily on first insert (`KVSTORE_ALLOCATE_DICTS_ON_DEMAND`) rather than eagerly for every possible slot/shard.

**Compact encodings for small collections.** Redis auto-selects a memory-dense encoding for small hashes/sets/lists/sorted-sets and promotes to a full hash-table/skiplist once a size threshold is crossed (configurable per type: `hash-max-listpack-entries`, `set-max-listpack-entries`, `set-max-intset-entries`, `zset-max-listpack-entries`, `list-max-listpack-size`, etc.). `listpack` is the modern compact structure (single contiguous allocation: 4-byte total-length + 2-byte element-count header, then a sequence of `[encoding][data][backlen]` entries, terminated by an `0xFF` EOF byte; `backlen` — a variable-length back-pointer — enables O(1) reverse traversal from the tail). `ziplist`/`zipmap` are legacy formats kept only for reading old RDB files; current code writes `listpack` in their place. `intset` is used for all-integer sets. `quicklist` (a linked list of listpack nodes) backs large lists. Streams use a rax (radix tree) of listpacks regardless of size.

**Persistence — RDB (point-in-time binary snapshot).** File layout: 9-byte header (`"REDIS"` + 4-digit version, current `RDB_VERSION 14`) → a stream of opcodes/serialized objects → an `RDB_OPCODE_EOF` byte + 8-byte CRC64 footer. Opcodes signal metadata/state transitions inline in the stream (`RDB_OPCODE_SELECTDB` switches active DB, `RDB_OPCODE_EXPIRETIME_MS` attaches an 8-byte millisecond expiry to the following key, `RDB_OPCODE_AUX` carries auxiliary metadata like the writer's Redis version, `RDB_OPCODE_SLOT_INFO` carries cluster slot info). All I/O goes through a `rio` abstraction (`rioInitWithFile`/`rioInitWithBuffer`/`rioInitWithConn`) that transparently maintains a running checksum regardless of the underlying target (file, memory buffer, or a live socket — the last of which is what enables direct-to-replica diskless RDB transfer). `SAVE` (`rdbSave()`) blocks the server. `BGSAVE` (`rdbSaveBackground()`) forks; the child calls `rdbSave()` and reports Copy-on-Write byte counts and keys-processed back to the parent over a pipe (`childinfo.c`) so the parent can update stats like `stat_rdb_cow_bytes` without blocking on the child. Loading (`rdbLoad`) is a dispatch loop reading one type byte at a time — either an opcode (consume associated metadata) or an object type code (read key, then value) — verifying the header signature/version up front and the trailing CRC64 at the end; keys whose loaded expire time is already in the past are dropped during load rather than being inserted and immediately expired.

**Persistence — AOF (multi-part, manifest-governed write log).** `server.aof_state` is a 3-state machine: `AOF_OFF`, `AOF_ON` (all writes logged), `AOF_WAIT_REWRITE` (enabled but buffering — waiting for an in-flight rewrite to finish before cutting over to a new INCR file). The AOF is not one file but a set of component files tracked by a manifest (`<appendfilename>.manifest`, one line per file: `file <name> seq <n> type <b|i|h> [startoffset <n> [endoffset <n>]]`). Three types: **BASE** (`b`, at most one — a full snapshot as of the last rewrite, optionally in RDB format if `aof-use-rdb-preamble` is set, for faster loading), **INCR** (`i`, possibly several, ordered — write commands since the last successful rewrite), **HISTORY** (`h` — former BASE/INCR files superseded by a completed rewrite, kept briefly then removed). This design makes rewrite transitions atomic (swap the manifest, not the data files) and recovery from a partial/interrupted write safe. Command logging: `feedAppendOnlyFile` serializes each write as a RESP multi-bulk array into `server.aof_buf`; `flushAppendOnlyFile` (called from `beforeSleep`, before the event loop blocks on I/O) drains that buffer to the current INCR file descriptor. Durability policy (`appendfsync`) is one of `no` (OS decides when to flush), `always` (synchronous `fsync(2)` after every write — and specifically, the reply to the client is held until that fsync completes, making the ack durability-true), `everysec` (a BIO background thread calls `fsync(2)` roughly once a second — bounding worst-case data loss to ~1s of writes without synchronous cost per command). **Rewrite** (compaction) forks a child (`rewriteAppendOnlyFileBackground` → child runs `rewriteAppendOnlyFile`, iterating the current in-memory `kvstore` and writing it out fresh) while the parent keeps serving clients and buffering new writes plus a rewrite-diff buffer; on child completion the parent merges the diff, renames the temp file into place, and updates the manifest — former BASE/INCR become HISTORY and get cleaned up. Startup loading (`loadAppendOnlyFiles`) reads the manifest, loads BASE then each INCR file in sequence, executing everything through a **fake client** (`createClient(NULL)`, `id == CLIENT_ID_AOF`) so ordinary command-execution code paths can replay the log; `isAOFLoadingContext()` lets other code detect it's inside a replay.

**Replication (async, PSYNC2).** Master pushes writes into a shared **replication buffer** — a linked list of refcounted `replBufBlock`s (a block frees only once both the backlog and every replica have moved past it), letting replicas at different offsets reference the same underlying memory rather than each getting a private copy. A `rax` tree (`blocks_index`) inside the master's circular-ish **replication backlog** maps offsets to blocks for O(log N) lookup when a replica requests a specific resync point. `feedReplicationBuffer()` formats a command into the replication stream, appends it, bumps `server.master_repl_offset`, and marks connected replicas pending-write. **PSYNC2**: replicas carry the master's `replid` (and a `replid2` for post-failover continuity); `masterTryPartialResynchronization()` validates the requested replid+offset against the current backlog window — if satisfiable, responds `+CONTINUE` and streams from that offset (partial resync, no RDB needed); otherwise responds `+FULLRESYNC <runid> <offset>` and a full RDB transfer begins. Full resync can be **disk-based** (fork, save RDB to disk, then stream the file) or **diskless** (`rdbSaveToSlavesSockets()` — the forked child writes the RDB directly to replica sockets, never touching disk; `repl-diskless-sync-delay` lets the master wait briefly for more replicas to join so one fork/save serves several recipients at once). An **RDB Channel** feature opens a second connection specifically for the bulk RDB transfer while the original "main channel" keeps streaming live commands, so replication catch-up and ongoing command application aren't serialized on the same socket. Replica-side handshake is an explicit state machine (`syncWithMaster()`): `REPL_STATE_CONNECTING` → receive PING reply → send AUTH → send listening port → `REPL_STATE_SEND_PSYNC` → `REPL_STATE_TRANSFER` (receiving RDB) → `REPL_STATE_CONNECTED`; any step failing triggers `cancelReplicationHandshake()` and a retry.

**Redis Cluster (sharding).** 16,384 fixed hash slots (`CLUSTER_SLOTS`), distributed across master nodes; each master can have replicas. `keyHashSlot()` computes `crc16(key or hashtag) & 0x3FFF`, honoring `{...}` hash-tag syntax so multiple keys can be forced onto the same slot for multi-key operations. `patternHashSlot()` (8.x) statically determines whether a glob pattern can only ever match a single slot (no wildcards outside a hash tag) — enabling optimized multi-key pattern operations in a sharded deployment without full-cluster fanout. Nodes talk over a dedicated cluster-bus connection (`clusterLink`, TCP or TLS per `server.tls_cluster`). Client requests are routed/redirected via `getNodeByQuery()`, returning `CLUSTER_REDIR_NONE` (serve locally), `CLUSTER_REDIR_MOVED` (permanent — slot lives elsewhere, client should update its slot map), `CLUSTER_REDIR_ASK` (temporary — slot is mid-migration, client must send `ASKING` to the destination before retrying there), or `CLUSTER_REDIR_TRIMMING` (`-TRYAGAIN` — the slot is currently being trimmed). **Atomic Slot Migration (ASM, 8.x)** moves slots between nodes via an explicit `asmTask` state machine with separate main (control/handshake) and RDB (bulk transfer) channels: connecting → auth → (importing side) accumulate incoming writes into a sync buffer while the RDB streams in, then switch to live streaming, then takeover; (migrating side) wait for the RDB channel, fork and stream bulk + live writes, hand off, then clear the local slot data. New 8.x cluster admin commands: `SFLUSH` (delete all keys in given slot ranges via `clusterDelKeysInSlot()`), `TRIMSLOTS` (background-via-BIO or active-via-cron key trimming by slot), and the `CLUSTER MIGRATION` subcommand family (`IMPORT`, `STATUS`, `CANCEL`) as the primary ASM control interface. `DUMP`/`RESTORE` (an RDB-versioned single-object payload with its own CRC64 footer) underlie slot data transfer at the individual-key granularity.

## Key patterns & techniques (transferable knowledge)

- **Single global mutable state struct as the "one source of truth."** All server state (config, connections, data, replication, cluster) hangs off one `struct redisServer server` — trades some encapsulation purity for extremely simple reasoning about "what's the current state of everything," which matters a lot in a single-threaded-core design where you must reason about exactly what's visible/mutable at each callback boundary.
- **Two-hash-table incremental rehashing to avoid a stop-the-world resize.** Keep the old and new table simultaneously, migrate a bounded amount of work per operation/tick rather than all at once, and only free the old table once fully drained. This general "old + new side by side, migrate incrementally, swap at completion" pattern is reusable for any resize/reshape of a hot data structure that can't tolerate a large pause (also seen, differently shaped, in TimescaleDB and elsewhere).
- **Pointer tagging using guaranteed-zero low bits from aligned allocation.** When you control the allocator and know its alignment guarantee, the low bits of every returned pointer are free real estate for a small tag — letting you special-case "a bucket holding exactly one item" without paying for a full node allocation. A narrowly-applicable but highly effective micro-optimization technique whenever a hash table's dominant case is single-item buckets.
- **Refcounted shared buffer blocks for one-to-many streaming at different consumption offsets.** The replication buffer lets N replicas at N different replay positions all reference the same underlying memory blocks instead of each replica getting a private copy of the stream — a block is freed only once every reader (including the backlog itself) has moved past it. Reusable for any fan-out log/stream where readers progress independently but the underlying bytes are identical.
- **Manifest-governed multi-file log instead of one ever-growing file.** AOF's BASE/INCR/HISTORY file split, coordinated by an atomically-swappable manifest, means "rewrite/compact the log" becomes "write new files, then atomically repoint the manifest" rather than "rewrite in place" or "swap one file for another" — safer under crash/partial-write scenarios and a general pattern for log compaction (similar in spirit to LSM-tree manifest files).
- **Fork-based background snapshot via Copy-on-Write instead of an in-process live-serialization pass.** Both BGSAVE and AOF rewrite fork a child process and let the OS's CoW page semantics provide a consistent point-in-time view without needing to lock or copy the dataset explicitly — the parent keeps serving writes to its own pages while the child reads the frozen fork-time view. A powerful pattern anywhere the host OS provides fork+CoW and the in-memory dataset is otherwise expensive to snapshot consistently under concurrent mutation.
- **Full-vs-partial resync decided by a bounded backlog window, not by policy alone.** PSYNC2 doesn't just check "did we see this replica before" — it checks whether the requested offset is still present in a bounded circular backlog; too old (already trimmed) or too new both force a full resync. This "small bounded catch-up window, else fall back to full transfer" pattern generalizes to any incremental-sync protocol with a memory-bounded history buffer.
- **Splitting bulk transfer onto its own channel from the live/control stream.** The RDB Channel (replication) and the ASM main/RDB channel split let a slow, large one-time transfer proceed independently of a latency-sensitive ongoing command/control stream on the same logical connection — useful whenever a protocol mixes an expensive bulk-catch-up phase with an ongoing low-latency stream.
- **Deterministic, versioned redirect codes instead of generic errors for a sharded system's "wrong node" case.** MOVED (permanent, update your map) vs ASK (temporary, needs an extra handshake command first) vs TRYAGAIN (transient, slot busy) each carry different client-side retry semantics baked into the protocol itself, rather than one generic "not here" error — worth remembering when designing any client-routable sharded protocol.
- **Auto-promoting compact encodings based on measured size, not declared type.** Small collections of any type get a memory-dense, CPU-cheaper-to-scan encoding (listpack/intset) until a configurable threshold, then transparently convert to a full hash-table/skiplist — a general technique for balancing memory footprint against algorithmic complexity, applicable whenever a collection's typical size in production skews small even though the API must support arbitrarily large collections.

## Practical how-tos

- **Debugging a slow rehash/resize event**: check whether the dict's rehash step hit a long run of empty buckets (capped at `n*10` probes) — rehashing progress under sparse tables can appear stalled even though it's bounded by design, not actually broken.
- **Investigating unexpected memory usage for a set/hash/zset**: check the relevant `*-max-listpack-entries`/`*-max-intset-entries` config against actual collection sizes — crossing the threshold silently promotes to a much larger full encoding (hash table or skiplist), which is a legitimate but easy-to-miss cause of a memory jump.
- **Diagnosing an AOF that won't load cleanly**: check the manifest file first — `AOF_TRUNCATED`/`AOF_FAILED` return codes usually mean the sequence of BASE→INCR files described by the manifest doesn't match what's on disk (e.g. a crash mid-rewrite before the manifest swap completed).
- **Choosing an `appendfsync` policy**: `always` gives per-write durability at real latency cost (the client reply is held for the fsync); `everysec` bounds loss to ~1s of writes via a background BIO thread without per-command latency cost; `no` defers entirely to OS page-cache flush timing — pick based on the actual RPO/latency tradeoff needed, not a default assumption.
- **Debugging replication falling back to full resync unexpectedly**: check whether the requested offset has aged out of the replication backlog (backlog size is bounded) — a replica disconnected longer than the backlog can hold will always need a full RDB transfer regardless of replid match.
- **Handling `-ASK` vs `-MOVED` correctly in a cluster client**: `MOVED` should update the client's persistent slot-to-node cache (the mapping changed); `ASK` should NOT update that cache (it's a one-off redirect for an in-flight migration) and requires sending `ASKING` to the destination node immediately before the retried command.
- **Investigating pipeline throughput**: check whether `memory_prefetch.c`'s prefetch mode is active for the workload — prefetching only helps when multiple commands are actually queued together (pipelining or `MULTI/EXEC`), not for one-command-at-a-time request/response traffic.

## Gotchas & caveats

- Rehashing progress is intentionally bounded per step (including a capped search length through empty buckets) — don't assume a dict resize completes "immediately" even under light load; it's spread across multiple event-loop iterations/cron ticks by design.
- Rehashing can be paused during iteration (`dictPauseRehash`) — code that holds an iterator open for a long time while also expecting background rehashing to keep progressing will observe it stalled, which is correct behavior to prevent duplicate/missed entries, not a bug.
- The compact-encoding thresholds (`hash-max-listpack-entries`, etc.) are configuration, not automatic based on measured memory — a collection can silently stay in a less memory-efficient full encoding if it was already large before a config change lowered the threshold (conversion is generally one-directional, compact→full, not full→compact on shrink).
- AOF's `always` fsync policy holds the client's reply until the fsync completes — this is a deliberate durability/latency tradeoff, not an accidental stall; conflating it with a performance bug will lead to the wrong fix.
- The replication backlog is bounded (circular-like) — a replica that's been disconnected too long ages out of partial-resync eligibility regardless of matching replication IDs, forcing a full resync even though the IDs "look right."
- `-ASK` redirects are one-shot and must not be cached as if they were `-MOVED`; caching an ASK target as the new permanent owner of a slot will misroute future requests once the migration completes or is cancelled.
- Diskless replication's wait delay (`repl-diskless-sync-delay`) deliberately trades a short startup delay for amortizing one fork/save across multiple simultaneously-joining replicas — a replica connecting just after the wait window will trigger a fresh full-sync cycle rather than joining the in-progress one.
- AOF rewrite and RDB BGSAVE both rely on fork+CoW; on systems/configurations where fork is expensive (very large `maxmemory`, huge resident sets) both operations can cause a real, visible latency spike at fork time even though the child itself runs asynchronously afterward.
- Pointer-tagging optimizations for single-item dict buckets are only valid because of the specific 8-byte alignment guarantee from `zmalloc` — this is an internal invariant, not something external code should assume holds for arbitrary pointers stored elsewhere in the codebase.
