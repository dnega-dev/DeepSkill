# danielmiessler/Fabric — Distilled Knowledge

## What it is

Fabric is an open-source AI augmentation framework, written in Go, that addresses AI's **integration problem** rather than its capabilities problem — it organizes AI prompts by real-world task into reusable, standardized templates called **Patterns**, so the same prompt logic works consistently across many AI providers and interfaces (CLI, REST API, web UI) [README.md:19-30, 55-68]. It is not a memory-store or agentic-loop framework in the mem0/agentmemory sense; it's closer to a "prompt-as-package-manager" system: hundreds of curated, versioned, git-synced prompt templates, plus the plumbing (vendor abstraction, template engine, strategy overlays) to apply any of them against any supported LLM. Distribution: Go install, Nix, pre-built binaries, or a one-line installer script.

## Architecture

**Three-tier design, single core orchestrator**: User Interfaces (CLI, SvelteKit web UI, REST API) → Core Fabric System (`core.Chatter` orchestrator, `core.PluginRegistry`, `fsdb.Db` file-system database) → AI Vendor Plugins (`ai.VendorsManager` + individual vendor clients for OpenAI, Anthropic, Gemini, Ollama, Bedrock, Copilot, Azure, and dozens of OpenAI-compatible providers via a `ProviderMap` loop). All three interfaces converge on the same `Chatter` object — there is no separate code path for "CLI mode" vs. "API mode" once a request reaches the core.

**`Chatter` orchestration** (`internal/core/chatter.go`): `BuildSession()` constructs the session by loading existing history from `fsdb` or initializing fresh from patterns/contexts, and normalizes message role alternation (`domain.NormalizeMessages`). `Send()`/streaming path calls `vendor.SendStream()`, processes `domain.StreamUpdate` packets (content, usage, thinking), optionally strips `<think>` blocks from final output if `SuppressThink` is set, and has specialized handling for a `create_coding_feature` pattern that parses and applies file changes directly to the local project root — i.e. Fabric can act as a code-mutation tool, not just a text-in/text-out prompt runner, when that specific pattern is used.

**Plugin architecture — dual-layer abstraction**: Layer 1, `Plugin` interface (`GetName`, `IsConfigured`, `Configure`, `Setup`, `SetupFillEnvFileContent`) handles configuration/lifecycle and is implemented once by `PluginBase`, inherited by every vendor. Layer 2, `ai.Vendor` interface (`ListModels`, `Send`, `SendStream`, `NeedsRawMode`) defines the actual AI operations and must be implemented per-vendor. `PluginBase` centralizes environment-variable naming: `NewVendorPluginBase(name, configure)` auto-derives an env-var prefix from the vendor's display name (e.g., "LM Studio" → `LM_STUDIO_`), so adding a new vendor doesn't require inventing a naming convention. `SetupQuestion` (interactive config prompts) supports a special `reset` keyword that clears a value and skips validation even on required fields — an explicit "unset" affordance, not just "leave blank."

**File-system-as-database (`fsdb`)**: Fabric deliberately avoids a real database engine. Everything — patterns, contexts, sessions, strategies — lives as plain files under `~/.config/fabric/`, on the stated rationale of transparency (editable in any text editor), portability (copy the directory), and version-control-friendliness. `StorageEntity` is the generic file CRUD base class; `PatternsEntity` extends it with pattern-specific resolution logic (custom-dir override, direct file-path loading, template processing).

## Key patterns & techniques

**Pattern precedence: custom overrides default, by name, at lookup time**: patterns live in two directories — the main synced directory (`~/.config/fabric/patterns/`, refreshed via `fabric --update` from the official GitHub repo) and a separate `CustomPatternsDir` for user-authored patterns that update never touches. `getFromDB()` checks the custom directory *first*; if found there, that version wins outright — this means a user can permanently pin a modified version of a stock pattern (e.g. a tweaked `summarize`) and it will never be silently overwritten by an upstream sync, since sync only ever writes to the main directory.

**Sentinel-token protection against recursive template injection**: the template engine uses `{{variable}}` substitution processed in a loop "until no more `{{` remain," which creates an obvious hazard — if user input itself contains a substring like `{{plugin:sys:env:SECRET}}`, that raw text could get mistaken for a live template directive during resolution. Fabric's fix: before running the substitution loop, the literal `{{input}}` placeholder is swapped for a fixed sentinel string (`__FABRIC_INPUT_SENTINEL_TOKEN__`, `template.InputSentinel`), all *other* `{{...}}` tokens (variables, `{{plugin:...}}`, `{{ext:...}}`) are resolved normally against the sentinel-bearing content, and only at the very end is the sentinel swapped back for the real user input. The one carve-out: if an extension call's *own* value argument explicitly contains `{{input}}`, the sentinel there is deliberately replaced with the real input before that extension executes — so extensions can still receive genuine user input as an argument, but the bulk of the resolution pass never sees raw (potentially template-injection-shaped) user text. This is a generally reusable technique for any system doing iterative string-template resolution where one of the substitution values is untrusted user content.

**Meta-pattern for pattern discovery (`suggest_pattern`)**: rather than building a separate recommendation subsystem, Fabric solves "which of hundreds of prompts do I need?" with *another prompt* — `suggest_pattern` is itself a Fabric pattern whose system message embeds a category taxonomy (20+ categories: AI, ANALYSIS, SECURITY, WRITING, EXTRACT, DEVELOPMENT, etc.) and explicit request-type-to-pattern mapping guidance, and asks the LLM to analyze the user's natural-language goal, categorize it, and recommend 1-3 concrete patterns with exact CLI invocation syntax. The catalog backing this is two small JSON files — `pattern_extracts.json` (first 500 words of each pattern's `system.md`, enough context for relevance judgment without loading the full definition) and `pattern_descriptions.json` (short description + tags per pattern) — both regenerated incrementally by a maintenance script (`extract_patterns.py`) that only processes newly-added pattern directories. This is a reusable pattern for tool/prompt discovery at scale: don't build a classifier, build a *catalog + a prompt that reads the catalog*, and keep the catalog's per-item footprint small (extract, not full content) so the discovery step itself stays cheap.

**Strategy-first prompt composition order**: "Strategies" (Chain-of-Thought, Tree-of-Thoughts, Reflexion, Self-Consistency, Self-Refinement, Least-to-Most, Atom-of-Thought, Chain-of-Draft, or plain "standard") are prompting-technique overlays, decoupled from both the task (Pattern) and background knowledge (Context), stored as small JSON files. `BuildSession` assembles the final system message in a strict order: Strategy prompt first (prepended at the very top) → Context content → Pattern content → language-enforcement wrapper if a non-English output language is requested. Putting the reasoning-style instruction *before* the task-specific instruction (rather than after, or interleaved) is a deliberate ordering choice — the model reads "how to think" before "what to do."

**Vendor-agnostic streaming abstraction**: `SendStream` pushes `domain.StreamUpdate` packets over a channel with three distinct types — content, usage (token metadata), and thinking (reasoning-model output) — giving callers (CLI printer, web UI, REST handler) one uniform interface regardless of which of the many supported vendors is actually generating the stream underneath.

## Practical how-tos

**Extending a pattern with an external tool call**: pattern authors can embed `{{ext:name:operation:value}}` inside a `system.md` file to invoke a registered external binary at render time (e.g. `{{ext:openai:chat:{{input}}}}` to have one pattern call out to another LLM mid-prompt-construction). Extensions must be registered via `fabric --addextension` first; the registry (`~/.config/fabric/extensions/extensions.yaml`) verifies both the config file and the executable via SHA-256 hash before allowing execution — a supply-chain check specifically because extensions run arbitrary local binaries.

**Built-in template plugins for common needs without an extension**: `{{plugin:text:upper:value}}` / lower / title / trim for string transforms, `{{plugin:datetime:now}}` for timestamps, `{{plugin:file:read:path}}` to inline local file content, `{{plugin:fetch:url}}` to inline remote content, `{{plugin:sys:env:VAR}}` for environment variables — these ship in the binary and don't require the extension registry's hash-verification overhead.

**Path-traversal guard on strategy/pattern file loading**: `LoadStrategy` explicitly cleans the requested path and verifies it still has the expected strategy-directory prefix before reading, rejecting anything that would escape via `../`-style traversal — worth replicating in any system that maps a user-supplied "name" string onto a filesystem read.

**Vendor lookup ambiguity handling**: the `PluginRegistry` supports case-insensitive vendor name lookups and explicitly warns when multiple configured vendors expose a model with the identical name — rather than silently picking one, it surfaces the ambiguity so the user can disambiguate with an explicit vendor flag.

## Gotchas & caveats

- **`ensureInput` silently appends `{{input}}` to any pattern lacking it** — if you're auditing what a custom or third-party pattern actually does with user input, don't assume the absence of an explicit `{{input}}` tag means input is ignored; it gets appended to the end of the prompt automatically.
- **Custom-pattern overrides are total, not merged** — a custom pattern with the same name as a system pattern fully replaces it (same last-write-wins-by-name semantics as agentmemory's skill merging and OpenHands' skill merging in the other repos in this batch); there's no per-section merge, so a small custom edit still means maintaining the entire pattern text yourself going forward, disconnected from upstream updates to that pattern.
- **The sentinel mechanism only protects the primary `{{input}}` slot**, not arbitrary user-supplied variable *values* passed via `-v key:value` — if a user-supplied variable value itself contains `{{...}}`-shaped text, it isn't run through the same sentinel-and-restore two-pass protection described for `{{input}}` specifically (the wiki text describes the input-sentinel mechanism only for the `{{input}}` case).
- **Extension execution is a real local-code-execution surface** — despite the SHA-256 hash verification of both config and executable, extensions run arbitrary registered binaries with data assembled from the current prompt context; the hash check guards against *tampering after registration*, not against registering something unsafe in the first place.
- **`store: false`-equivalent reasoning suppression is a display-layer strip, not a request-layer opt-out** — `SuppressThink` strips `<think>` blocks from the *final printed output*, which is different from telling the underlying provider not to generate or persist reasoning content in the first place; conflating the two could lead to assuming reasoning tokens were never sent/billed when they were just hidden from the terminal.
