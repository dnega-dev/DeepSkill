# OpenHands/OpenHands — Distilled Knowledge

## What it is

OpenHands is an AI-driven software development platform enabling autonomous code generation, editing, and task execution through LLM-powered agents [README.md:33-87]. It ships in several interfaces: a composable **Software Agent SDK** (Python library, external repo `openhands-sdk`), a **CLI**, a **Local GUI** (React SPA + REST API), a hosted **Cloud** SaaS, and a self-hosted **Enterprise** Kubernetes deployment. The codebase is mid-migration from a legacy **V0** monolithic architecture (deprecated since v1.0.0, scheduled for removal April 1, 2026) to a **V1** decoupled architecture that runs agents inside isolated sandboxes and delegates agent reasoning to the external Software Agent SDK. This distillation covers both, since V0 documents the actual in-process agent-loop mechanics (agent state machine, delegation, event stream) most transferable to other frameworks, while V1 documents the sandbox-isolation/service-oriented pattern OpenHands is moving toward.

## Architecture

**V0 (legacy, monolithic)**: FastAPI + Socket.IO server. `WebSession` (per-connection wrapper) → `AgentSession` (coordinates runtime + agent lifecycle, independent of transport) → `AgentController` (executes the agent step loop) → `Agent` (e.g. `CodeActAgent`) → `Runtime` (`DockerRuntime`/`LocalRuntime`/`RemoteRuntime`/`KubernetesRuntime`) → `EventStream` (persists/distributes events) → `FileStore`.

**V1 (current)**: App Server (`openhands/app_server/`) exposes REST; `LiveStatusAppConversationService` orchestrates conversation lifecycle; `SandboxService` (Docker/Remote/Process implementations) starts a Docker container or K8s pod running an **Agent Server** (`ghcr.io/openhands/agent-server:<version>-python`) which embeds the Software Agent SDK. App Server and Agent Server communicate over HTTP/REST (`httpx.AsyncClient`) — e.g. `POST /conversations` to start, `POST /conversations/{id}/messages` to send messages. State is persisted in PostgreSQL (`AppConversationInfo`, `AppConversationStartTask`, `SandboxInfo`), with Redis used for scaling/locking. This is a deliberate move from in-process coupling (V0) to full process/tenant isolation — each conversation's agent literally runs in its own container, communicating only via REST, so one tenant's crashed agent cannot take down another's or the app server itself.

**Sandbox implementations** (`SandboxService` abstract base, methods: `start_sandbox`, `get_sandbox`, `pause_sandbox`, `resume_sandbox`, `delete_sandbox`, `wait_for_sandbox_running`): `DockerSandboxService` (local Docker, auto port-mapping, injects `OH_SESSION_API_KEYS_0` for auth), `RemoteSandboxService` (proxies to a remote runtime API, keeps a local `StoredRemoteSandbox`/`v1_remote_sandbox` DB table to compensate for API limitations, hashes session API keys with SHA-256 before local storage), `ProcessSandboxService` (spawns the agent server as a plain Python subprocess, no container). Standard exposed ports: `AGENT_SERVER` (60000), `VSCODE` (60001), `WORKER_1`/`WORKER_2` (12000/12001). A `pause_old_sandboxes` cleanup routine sorts running sandboxes by creation time and pauses the oldest ones once a per-user `max_num_sandboxes` cap is exceeded — a simple LRU-by-age resource control.

**Agent Controller (V0) — the agent loop**: `AgentController.step()` → `_step()` checks preconditions (state must be RUNNING, no pending action, iteration/budget limits not exceeded, not stuck-in-loop per `StuckDetector`) → calls `agent.step(state)` which calls the LLM → gets back an `Action` → runs it through `_handle_security_analyzer()` → if confirmation required, sets `_pending_action` and transitions to `AWAITING_USER_CONFIRMATION`; otherwise publishes the action to the `EventStream` → if the action is "runnable" (has a `.run()` method), executes it against the `Runtime`, gets an `Observation` back, and publishes that too. `should_step()` gates whether an incoming event should trigger another step (e.g. a user `MessageAction` always triggers a step; an `AgentStateChangedObservation` never does — this prevents infinite self-triggering loops from the controller's own state-change notifications).

**Agent state machine**: `INIT → LOADING → RUNNING`, with `RUNNING` branching to `AWAITING_USER_CONFIRMATION` (confirmation mode) → `USER_CONFIRMED`/`USER_REJECTED`, to `AWAITING_USER_INPUT` (agent requests input), to `FINISHED`/`REJECTED` (terminal, via `AgentFinishAction`/`AgentRejectAction`), to `ERROR` (exception or limit exceeded — recoverable back to `RUNNING` on user resume), to `PAUSED`/`STOPPED` (terminal), and to `RATE_LIMITED` (recoverable to `RUNNING` on retry success, or `ERROR` once retries exhaust). Every transition calls `set_agent_state_to()`, which emits an `AgentStateChangedObservation`, persists state, and — critically — re-raises iteration/budget limits if recovering from `ERROR` back to `RUNNING` (so a resumed agent gets a fresh allowance rather than immediately re-hitting the same limit).

**Multi-agent delegation**: an `AgentDelegateAction` triggers `start_delegate()`, which creates a *child* `AgentController` sharing the same `EventStream` and global `Metrics` object but with its own iteration counter, `State`, and incremented `delegate_level`. Only the root parent actually subscribes to the event stream; a delegate receives events *forwarded* by its parent rather than subscribing independently. On the delegate finishing or erroring, `end_delegate()` computes delegate-specific metrics (vs. a `parent_metrics_snapshot` taken at delegation time) and emits an `AgentDelegateObservation` back to the parent.

## Key patterns & techniques

**Security-gated action confirmation**: an optional `security_analyzer` assesses each generated action's risk (`LOW`/`MEDIUM`/`HIGH`/`UNKNOWN`). In confirmation mode, only `LOW`-risk actions execute automatically; `MEDIUM`, `HIGH`, and `UNKNOWN` all require explicit user confirmation before the action is published to the event stream — meaning an *unassessed* action (no analyzer configured, or analyzer couldn't classify it) is treated as risky by default rather than safe by default, a fail-closed design choice.

**LLM retry via mixin composition**: `LLM` class multiply inherits from `RetryMixin` (wraps `completion()` in a `tenacity`-based retry decorator) and `DebugMixin` (adds debug logging), keeping retry logic transparent to callers. Retryable exceptions: `APIConnectionError`, `RateLimitError`, `ServiceUnavailableError`, `BadGatewayError`, `litellm.Timeout`, `LLMNoResponseError` (empty/null LLM response is itself treated as a retryable failure, not just network-level errors). Non-retryable and mapped to a hard `ERROR` state instead: `AuthenticationError`, `InternalServerError`, budget-exceeded `BadRequestError`, `ContentPolicyViolationError` — these are terminal because retrying won't help. `RateLimitError` specifically maps to a distinct `RATE_LIMITED` agent state (not `ERROR`) that can recover to `RUNNING` if a retry succeeds, escalating to `ERROR` only once retries are exhausted — a deliberate three-tier severity model (retry silently / wait-then-retry-with-visible-state / give-up-and-error) rather than binary retry/fail.

**Skill/microagent layered precedence** (the "memory" analog): agent knowledge is injected from four tiers, later overriding earlier by name: (1) Public Skills (community, `github:OpenHands/skills`), (2) User Skills (`~/.openhands/skills/`), (3) Org Skills (a dedicated per-org config repo — path convention differs by Git provider: GitHub/Bitbucket use `{org}/.openhands`, GitLab uses `{org}/openhands-config`, Azure DevOps uses `{org}/openhands-config/openhands-config`), (4) Repo/Project Skills (`.openhands/microagents/`, `.agents/skills/`, or a single `.cursorrules` file — highest priority, since project-specific instructions should win). Merging is a flat dict keyed by skill name (`_merge_skills`), so a project skill named identically to a public one fully replaces it rather than composing. Skills carry `KeywordTrigger` (fire on keyword match, e.g. `keyword:python,flask`) or `TaskTrigger` (fire on task-pattern match, e.g. `task:create web app`) — this is a lazy/conditional context-injection mechanism rather than dumping all loaded skills into every prompt.

**V1 skill-loading is a proxy pattern, not direct filesystem access from the app server**: the App Server never reads skill files itself — it authenticates and builds an `OrgConfig`/`SandboxConfig`, then makes a single stateless `POST /api/skills` call to the Agent Server *inside the sandbox*, which does all actual file-system/GitHub-API traversal and returns `list[SkillInfo]`. This keeps credential handling centralized in the app server while keeping filesystem/API access properly scoped to the sandbox that has the cloned repo. If the org-level skill source fails to load (repo not found/unauthorized), the org config is set to `None` and other sources still load normally; if the entire `/api/skills` HTTP call fails (timeout, network error), the exception is caught, a warning logged, and an *empty* skill list returned rather than blocking conversation startup — skill loading is treated as a best-effort enhancement, never a hard startup dependency.

**Environment variable auto-forwarding**: any environment variable prefixed `LLM_` or `LMNR_` on the app server is automatically forwarded into the sandbox's Agent Server process — a convention-based mechanism for propagating LLM provider credentials/config without an explicit per-key mapping table.

**CodeActAgent's unified action space**: rather than separate specialized tools per capability, the primary agent implementation consolidates bash execution, Python/IPython execution, file edit/read/write, browser navigation, sub-agent delegation, "think" (internal reasoning not shown to the user), "finish"/"reject" (terminal signals), MCP tool calls, and task-list tracking into one flat action vocabulary the LLM chooses from each step.

## Practical how-tos

**Polling pattern for eventually-consistent metadata**: `SetTitleCallbackProcessor` needs a conversation title that the agent server generates asynchronously. It polls up to 4 times with a fixed 3-second delay; HTTP errors during polling are logged as warnings but don't stop the loop; if a title is returned, polling stops and the callback disables itself (`ACTIVE → DISABLED`); if all 4 attempts return no title, the callback stays `ACTIVE` so the *next* relevant event (a new `MessageEvent`) retriggers polling rather than giving up permanently. Useful reusable pattern: bounded-attempt polling that fails open (stays active) rather than failing closed (disabling) when the resource legitimately isn't ready yet.

**Frontend rate-limit backoff**: React Query hooks retry only on HTTP 429 (rate limit), capped at 3 attempts, with delay computed dynamically per-error via `getRateLimitRetryDelayMs` rather than a fixed exponential schedule — i.e., respect a `Retry-After`-style hint from the error payload instead of guessing.

**Debugging LLM calls safely**: a `DEBUG_LLM` environment variable enables verbose litellm call logging, but the docs note this requires deliberate user confirmation because it can leak secrets into logs — paired with a `redact_text_secrets` utility and a `RedactURLParamsFilter` that specifically strips `session_api_key` from HTTP access logs, and a `StackInfoFilter` that only captures stack traces at ERROR+ level to reduce log noise.

**Graceful degradation in provider discovery**: `DefaultLLMModelService`'s model-listing against AWS Bedrock and Ollama catches provider-specific errors (missing credentials, HTTP failures) and returns an empty list for that provider rather than failing the whole model-discovery call — one broken provider integration shouldn't prevent users from seeing/selecting models from providers that *are* configured correctly.

## Gotchas & caveats

- **V0 is being actively removed** (target: April 1, 2026, per the wiki's own "Important Migration Context" notice) — the agent-loop mechanics described here (in-process `AgentController`, direct event-stream subscription, delegate controllers) are legacy patterns being replaced by the sandboxed V1 model where agent reasoning happens in an external SDK you can't directly instrument the same way. If building on OpenHands going forward, expect the V1 sandbox/REST model, not the V0 in-process controller.
- **Delegate controllers don't independently subscribe to the event stream** — only the root parent does, and it forwards events to active delegates. Any external tooling that assumes every `AgentController` instance is independently observable via the event stream would be wrong for delegates.
- **`RATE_LIMITED` is a distinct state from `ERROR`**, easy to conflate when building generic status-handling logic — a naive "is agent in an error state" check that only tests for `ERROR` will miss agents that are actually stalled on rate limiting (which is recoverable) vs. genuinely failed.
- **Confirmation-mode risk defaulting is fail-closed**: `UNKNOWN` risk (no analyzer, or analyzer couldn't classify) requires confirmation just like `HIGH` risk — don't assume "no risk assessment" means "treated as safe."
- **Org-repo path conventions differ silently by Git provider** (GitHub/Bitbucket: `{org}/.openhands`; GitLab: `{org}/openhands-config`; Azure DevOps: `{org}/openhands-config/openhands-config`) — hardcoding one convention across providers will silently fail to discover org-level skills on the others.
- **Skill merge is last-write-wins by exact name match**, not deep-merged content — a project skill sharing a name with a public one *fully replaces* it rather than extending/overriding specific fields, so accidental name collisions silently drop the lower-priority skill's content entirely.
- **`LLMNoResponseError` (empty response) is retried like a network error**, which is reasonable for transient LLM flakiness but means a persistently-empty-response failure mode (e.g. a misconfigured model) will spend the full retry budget before surfacing as an error rather than failing fast.
