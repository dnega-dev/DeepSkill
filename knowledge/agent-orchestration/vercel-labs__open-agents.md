# vercel-labs/open-agents — Distilled Knowledge

## What it is

Open Agents is Vercel's open-source reference application for building and running background coding agents [README.md:5-7]. It is a complete vertical stack — Next.js web UI, a durable agent workflow engine, and isolated execution sandboxes — meant to be forked and adapted as a foundation for custom AI-driven development workflows, rather than used as a hosted product per se. It takes a user from a natural-language prompt to a verified Pull Request without the user maintaining any local execution environment. Monorepo managed with Turborepo + Bun: `apps/web` (Next.js frontend, API routes, DB schema/migrations via Drizzle ORM), `packages/agent` (agent logic, tools, LLM orchestration — the `@open-agents/agent` package), `packages/sandbox` (Vercel Sandbox/Firecracker MicroVM wrapper), `packages/shared` (common types/hooks).

## Architecture

**Deliberate separation: the agent does not run inside the sandbox** [README.md:11-23]. This is the single most important architectural decision in the codebase. Three layers:
1. **Web Application** (`apps/web`) — auth (Vercel + GitHub OAuth), session/chat management, real-time streaming, repo selection, PR management.
2. **Agent Workflow** (`packages/agent`) — runs as a *durable workflow*, decoupled from any single HTTP request lifecycle, so long coding tasks survive network interruptions and browser refreshes. Orchestrates "thinking," tool selection, and conversation history.
3. **Sandbox VM** (`packages/sandbox`) — a Vercel Firecracker MicroVM providing filesystem/shell/git; supports hibernation and resumption so the environment persists across agent turns. The agent interacts with it exclusively through specialized tools over an API, never by running its own process inside the VM.

**Workflow execution**: `runAgentWorkflow` (`apps/web/app/workflows/chat.ts`) is the durable, resumable entry point for one agentic "turn." Flow: validate auth/session ownership → check if a workflow is already running for the `chatId` via `chat.activeStreamId` (resume if so, else start fresh) → loop calling `webAgent.stream(messages, tools)`, forwarding the streamed `UIMessageChunk`s to the client, treating each iteration as a persistable/recoverable "step" → detect if the workflow should pause for human interaction (`shouldPauseForToolInteraction`, e.g. an `ask_user_question` tool call or an action requiring approval) → on completion, persist the assistant message, record usage, and optionally run post-finish automation.

**Post-finish automation**: if `autoCommitEnabled`/`autoCreatePrEnabled` are set, the workflow chains: detect uncommitted changes in the sandbox → generate a commit message and push (`runAutoCommitStep`) → open a PR (`runAutoCreatePrStep`) — fully automated git flow triggered off the agent's own "stop" finish reason, no separate user action needed.

**The core agent — `openHarnessAgent`**: built on a `ToolLoopAgent` class from Vercel's `ai` package. Two lifecycle hooks matter: `prepareCall` (normalizes model selection, builds the system prompt fresh each call) and `prepareStep` (injects prompt-caching headers before every model interaction). It receives an `AgentSandboxContext` (sandbox state, working directory, current git branch) so the system prompt always reflects live environment state rather than a stale snapshot.

**Explorer/Executor subagent pattern**: rather than one agent doing everything, complex tasks delegate via a `task` tool to a `SUBAGENT_REGISTRY`. Two named roles: **Explorer** — fast, strictly read-only (uses `read`/`grep`/`glob`/read-only `bash`), specialized for codebase analysis without risk of side effects; **Executor** — "fire-and-forget," full write access, completes well-defined implementation tasks autonomously but explicitly *cannot* ask the user follow-up questions (so it must be given a fully-specified task up front, forcing the delegating agent to do the disambiguation work before handing off). This is a reusable capability/permission-scoped subagent split: one subagent type for safe exploration, another for committed execution, rather than a single subagent with the union of all permissions.

## Key patterns & techniques

**Aggressive tool-history compaction** (the main context-management technique): a four-stage pipeline in `packages/agent/context-management/aggressive-compaction-helpers.ts`. (1) `indexToolCalls` scans the message array and builds a `ToolCallIndex` keyed by `id:toolCallId` or `anon:index` for calls without stable IDs. (2) `findPendingCompactionCandidates` identifies tool calls *not* in a `recentToolCallKeys` protected set and not already compacted — i.e., only calls old enough to be safely summarized are touched; the most recent N calls are always left intact so the model retains full detail on what it just did. (3) `estimateCompactionSavings` computes potential character reduction via `JSON.stringify` length comparison and estimates token savings as `characters / 4`, gating whether compaction is even worth doing. (4) `compactToolData` replaces tool arguments and results with a short `compactedToolNotice` placeholder string. This is applied selectively (only past low-recency tool calls, only when savings clear a threshold) rather than blanket-summarizing everything — a technique for keeping long agentic sessions under context limits without losing recent, load-bearing detail.

**Message conversion pipeline before every LLM call** (`convertMessages`): dedupe redundant reasoning blocks (`dedupeMessageReasoning`) to avoid re-sending reasoning tokens the model already produced; convert specialized UI parts (e.g. `data-snippet`) into Markdown-formatted JSON for the LLM; run the AI SDK's `pruneMessages` to drop empty messages; set `ignoreIncompleteToolCalls: true` specifically to stop the model from seeing partial/dangling tool-call definitions left over from an interrupted stream (a stream that died mid-tool-call shouldn't leave a broken half-call in history for the next turn to choke on).

**Model-specific behavioral overlays**: rather than one-size-fits-all prompting, the framework branches on detected model family. Anthropic: models before 4.6 get legacy `enabled` thinking with a fixed 8000-token budget; 4.6+ get `adaptive` thinking with `effort: "medium"` default — i.e. newer models get a dynamically-sized reasoning budget instead of a hardcoded one. OpenAI: `store: false` is forced on *all* OpenAI models specifically to prevent sensitive reasoning content from being persisted server-side by the provider; GPT-5 variants must then also set `reasoning.encrypted_content` and `reasoningSummary: "detailed"` as a **required workaround** — without persistence, the Responses API would otherwise fail without these compensating fields. This encrypted-content-as-workaround-for-non-persistence detail is a specific, non-obvious gotcha worth remembering if integrating GPT-5 with `store: false`.

**Skills system**: Markdown files (`SKILL.md`) with YAML frontmatter (`name`, `description`, `options` like `userInvocable`/`disableModelInvocation`) discovered from `.agents/skills/` directories, distinguishing Global (platform-provided) vs. Project-level (in the user's repo) skills. Execution flow when the agent invokes the `skillTool`: validate the skill exists in session metadata → read the raw `SKILL.md` from the sandbox → strip YAML frontmatter via regex (`extractSkillBody`) → **prepend the skill's absolute directory path to the injected content** (`injectSkillDirectory`) specifically so the model can construct correct paths to auxiliary scripts/resources living alongside the skill file, not just the instructions text → substitute a `$ARGUMENTS` placeholder with user-supplied args (`substituteArguments`). Slash-command-triggered skills (`/commit`, `/plan`, `/review`) carry an explicit priority instruction: if a user message starts with `/`, the agent must call `skillTool` *first*, before any other action — this is enforced via system-prompt instruction text, not code-level interception, so it's a soft (LLM-obeyed) rather than hard guarantee.

**Skill integrity via lockfile**: `skills-lock.json` tracks `source` (e.g. `vercel/ai`), `sourceType` (e.g. `github`), and a `computedHash` for externally-sourced skills — a supply-chain-style integrity check to detect if a skill's content changed unexpectedly upstream, conceptually similar to a package-manager lockfile but for prompt/instruction content rather than code dependencies.

**Redis-backed skill caching**: skills are cached keyed by `sessionId` + `sandboxScope` (sandbox name or snapshot ID) with a 4-hour TTL, avoiding a full sandbox round-trip (`connectSandbox` + `discoverSkills`) on every request — cache invalidation is implicitly scoped to sandbox identity, so a new sandbox (different snapshot) naturally gets a fresh discovery rather than stale cached skills.

**Fail-closed tool approval gating**: each tool definition can carry a `needsApproval` predicate. `bash` uses `commandNeedsApproval` checking `DANGEROUS_COMMAND_PATTERNS` (e.g. `rm -rf`, `find -delete`) and `SENSITIVE_FILE_PATTERNS` (`.env`, SSH keys); file `read` requires approval for `.env`-pattern matches; **`web_fetch` sets `needsApproval: true` unconditionally for every single call**, plus performs its own DNS resolution check (`resolvesToPrivateHost`) to block requests to private/internal IP ranges — a defense-in-depth pairing of "always ask a human" with "and also block SSRF-style internal-network access even if approved." When approval is required, the workflow suspends and the frontend renders `ApprovalButtons`; approval/denial resumes or halts the specific tool call via callback.

## Practical how-tos

**Resuming an in-flight workflow instead of duplicating it**: the chat route checks `chat.activeStreamId` before starting a new `runAgentWorkflow` — if one is already running for that `chatId`, it reconciles and resumes the existing stream. This avoids the classic "double-fire" bug where a page refresh or duplicate request spins up a second concurrent agent run against the same conversation.

**Auto-hibernation with a grace buffer**: sandboxes hibernate automatically after 30 minutes of inactivity (`SANDBOX_INACTIVITY_TIMEOUT_MS`) and hit a hard Vercel-imposed ceiling of 5 hours (40 minutes in the `hobby` resource profile). A `TIMEOUT_BUFFER_MS` of 30 seconds is reserved before the hard SDK limit specifically to let `beforeStop` hooks run — if you're building similar sandbox lifecycle logic, budget an explicit grace window for cleanup hooks rather than assuming the stop signal gives you the full remaining time.

**Reconnect-or-create sandbox pattern**: `connectSandbox` checks if a named sandbox already exists; if so it calls `VercelSandbox.connect()`, and specifically catches `isSandboxNotFoundError` to fall back to `VercelSandbox.create()` — a resilient "try to resume, gracefully recreate on failure" pattern for any system managing named persistent remote resources.

**Credential brokering without VM-side exposure**: GitHub tokens are injected into the sandbox's *network policy layer* rather than as VM environment variables, so authenticated git operations (clone/push) work without the token being readable from inside the VM's own env — a way to grant capability without granting visibility of the secret itself.

**Resource profile for cheap/demo deployments**: setting `OPEN_AGENTS_RESOURCE_PROFILE=hobby` drops default vCPUs to 1 and caps sandbox timeouts to 40 minutes, useful for cost-constrained or trial deployments without a code change.

## Gotchas & caveats

- **`store: false` on OpenAI models is not simply "off"** — for GPT-5 variants specifically, disabling persistence requires *also* setting `reasoning.encrypted_content` and `reasoningSummary: "detailed"`, or the Responses API fails outright. This is a non-obvious coupling between two settings that look independent.
- **Compaction is irreversible and lossy by design** — `compactToolData` replaces actual tool arguments/results with a placeholder notice string; there's no mechanism described to "decompact" if the agent later needs the exact original tool output. Any workflow relying on being able to re-inspect exact historical tool call payloads after compaction has run would need its own separate persistence.
- **Skill invocation priority is prompt-enforced, not code-enforced** — the "call `skillTool` first if message starts with `/`" rule lives in the system prompt text given to the LLM, not in a hard pre-processing step. A model that doesn't follow instructions well could still act on a slash-command message without invoking the skill first.
- **`web_fetch` requiring approval for every call** is a strong default that will surface as friction in any fully-autonomous (headless) deployment — if building an unattended pipeline on this codebase, expect to need an explicit override path for that blanket `needsApproval: true`.
- **The Explorer subagent's read-only constraint and the Executor's "can't ask follow-up questions" constraint are enforced at the subagent-definition level** (which tools each type has access to / its own system prompt), not by a shared runtime sandbox permission system — so replicating this pattern elsewhere means encoding the constraint per-subagent-type rather than relying on infrastructure-level enforcement.
- **The wiki explicitly notes the managed hosted instance (`open-agents.dev`) applies non-`@vercel.com`-email trial gating** (1 session, 5 messages, no repo access) — a detail specific to the hosted demo, not the open-source framework's own behavior when self-hosted.
