# langflow-ai/langflow — Distilled Knowledge

## What it is

Langflow is an open-source platform for building and deploying AI-powered agents and workflows through visual authoring and programmatic APIs. It provides a visual flow editor plus built-in REST API and MCP server support, so "every workflow" can be turned into a callable tool. Version at time of the wiki snapshot: 1.10.0, Python >=3.10 <3.15, default port 7860.

Three-layer architecture:
1. **Frontend**: React 19 + TypeScript SPA using `@xyflow/react` for the visual flow canvas, Zustand for state, Tailwind + Radix UI for styling.
2. **Backend**: FastAPI server with REST/WebSocket APIs.
3. **Component system**: dynamic, code-generated components — Langflow Assistant can create entire flows or individual components from natural language, and components can be hand-customized as raw Python.

Monorepo package structure (a `uv` workspace):
- `langflow` — top-level package, CLI entry point (`langflow_launcher.py`), bundles extension packages (e.g. `lfx-duckduckgo`, `lfx-docling`).
- `langflow-base` — core application logic and service layer, depends on `lfx`.
- `lfx` — lightweight executor/CLI for serving flows standalone, integrates with MCP; contains the actual Graph Engine and Component Registry code.
- `langflow-sdk` — Python client for the REST API.
- Extension bundles (`lfx-ibm`, `lfx-arxiv`, etc.) — standalone pip packages adding provider-specific components.

This split matters: **the graph engine and component registry live in the lightweight `lfx` package**, decoupled from the full `langflow-base` application server — meaning flows can be executed by a minimal standalone executor without the full FastAPI/DB/service stack, which is presumably what powers "serve a flow as an MCP tool" without deploying the entire platform.

## Architecture (how it's built, key components)

### Component Registry (static component catalog)
Not maintained by hand — generated by `scripts/build_component_index.py`, which imports every component class from the `lfx.components` package, strips volatile fields (`timestamp`, `deprecated_at`) to avoid noisy hash churn, recursively sorts dict keys for determinism, and computes a SHA256 integrity hash over the whole index. The output is `component_index.json` (component specs) plus `stable_hash_history.json` (maps component name → per-version code hash, used to detect when a saved flow references an outdated component definition and needs an update prompt in the UI).

Each component entry captures: `display_name`/`description`/`icon` (UI metadata), `base_classes` (output types produced), `metadata.code_hash`/`.module` (full Python import path, e.g. `lfx.components.FAISS.faiss.FaissVectorStoreComponent`), `template` (input field definitions — each with an `_input_type` like `StrInput`/`BoolInput`/`HandleInput`/`IntInput` that tells the frontend which control to render), `outputs` (output ports: `method` to invoke, `types` allowed, and critically a `tool_mode: bool` flag), `field_order` (UI ordering).

The registry supports **localization**: component descriptions/labels are externalized to locale JSON files (`en.json`, `ja.json`, `pt.json`, `fr.json`, `de.json`) keyed by a pattern like `components.<component_id>.<field>.<hash>` — the hash suffix presumably invalidates a translation automatically when the underlying English text changes.

### Component lifecycle (five phases)
Definition (Python class inheriting `Component`/`CustomComponent` from `lfx`) → Registration (metadata captured into `component_index.json` at build time) → Instantiation (at flow-execution time, not app startup) → Initialization (parameter/secret resolution) → Execution (`build()` invocation) — looping back to Instantiation for the next vertex.

**Instantiation is dynamic code evaluation, not static imports**: a vertex's `params` dict actually contains a `code` field holding the **full Python source of the component class as a string**. `instantiate_class()` pops that `code` field, calls `eval_custom_component_code(code)` to compile/evaluate it into a live class object, then instantiates it with system metadata (`_user_id`, `_parameters`, `_vertex`, `_tracing_service`, `_id`). This is what makes "customize component source code directly in the UI" and "AI-generate a new component from natural language" both work — every component's actual implementation is stored and re-evaluated as source text per flow, not compiled once into the application.

**Initialization / secret resolution**: `update_params_with_load_from_db_fields()` iterates fields flagged `load_from_db_fields` (e.g. API keys), resolves them via `custom_component.get_variable(name, field, session)` against the database (inside a `session_scope()`), and — if `fallback_to_env_vars=True` and the DB lookup misses — falls back to `os.getenv()`. This is the credential-resolution layer: secrets referenced by name in a flow are resolved per-tenant from a DB-backed variable store, with an explicit environment-variable escape hatch for local/dev use.

**Execution dispatch** differs by base class: `build_component()` (modern `Component` classes) calls `set_attributes(params)` then `build_results()`; `build_custom_component()` (legacy `CustomComponent` classes with a bare `build()` method) detects sync vs async via `inspect.iscoroutinefunction` and additionally captures **artifacts** for UI rendering — a `repr` (string form via `custom_repr()`), `raw` data (post-processed), and a `type` (via `get_artifact_type()`, used by the frontend to decide whether to render a table, image, or plain text).

### Graph construction, validation, and execution
`Graph.from_payload()` deserializes flow JSON into a `Graph` (vertices, edges, predecessor/successor maps, in-degree counts, inactive-vertex tracking). Before this, `process_tweaks()`/`apply_tweaks()` applies caller-supplied field overrides (a `dict[str, dict]` mapping node IDs to parameter overrides) — notably **explicitly blocking tweaks from touching the `code` field**, a direct code-injection guard given that `code` is literally eval'd source. Tweaks also repair malformed JSON in `NestedDict`-typed fields via `validate_and_repair_json` and unwrap UI-exported template dict structures.

`Edge` cleaning happens both server-side and client-side: invalid edges (missing source/target) are dropped, and edges are filtered if source/target output/input types don't align, or if `tool_mode`/advanced-field conditions mismatch — keeping the graph topology consistent with each component's declared contract.

**Cycle handling**: Langflow deliberately supports controlled loops (not just DAGs). `find_all_cycle_edges()`/`find_cycle_vertices()` detect cycle membership; cycle edges are wrapped in a specialized `CycleEdge` class; a `MAX_CYCLE_APPEARANCES` constant caps how many times a cycle can re-fire at runtime, preventing runaway infinite loops while still allowing genuinely iterative flow patterns (see `LoopComponent` below).

**Topological sort** (`get_sorted_vertices()`) uses in-degree tracking + predecessor maps to compute execution order, treats cycle edges specially (respecting the iteration cap), and skips inactive vertices. Each `Vertex` carries one of three states: `ACTIVE`, `INACTIVE` (skipped by conditional logic), `ERROR` (failed) — with `ERROR → ACTIVE` and `INACTIVE → ACTIVE` transitions explicitly modeled, meaning the engine supports retry/reactivation rather than treating failure/exclusion as terminal.

**Two execution paths**, same underlying vertex-build mechanism but different orchestration:
| Mode | Entry point | Returns | Used by |
|---|---|---|---|
| Interactive Build | `POST /build/{flow_id}/flow` + `GET /build/{job_id}/events` (SSE) | `job_id`, then a stream of per-vertex build events | Playground UI |
| Programmatic Run | `POST /run/{flow_id_or_name}` | `RunResponse` (blocking or streaming) | API clients, webhooks |

Interactive build runs one vertex at a time via `JobQueueService`, streaming a `vertex_build` SSE event per completed node plus a final `end` event — giving the UI live per-node visibility into a running flow. Programmatic run (`run_graph_internal()` → `graph.arun(...)`) executes the whole graph in one call and returns/streams the aggregate `RunOutputs`.

### Parameter resolution across edges
`ParameterHandler` (per-`Vertex`) resolves each input from its connected upstream edges: merges multiple inputs into a list for list-typed fields, converts logical file sub-paths to absolute paths (storage-service-aware), and **coerces Langflow's own `Message`/`Data` wrapper objects down to plain strings for `str`-typed inputs** by extracting their contained text — a type-coercion layer that lets differently-typed component outputs still connect to simpler string inputs without the user manually inserting a converter node.

### Tool-calling convention: `component_as_tool` + `tool_mode`
Any component can expose a `component_as_tool` output of type `Tool`, toggled via a `tool_mode` flag on its template. This is the core mechanism that makes essentially every existing component (search, calculator, vector store lookup, custom API wrapper) usable as an agent tool with zero special-casing: an `Agent` node's input port simply accepts `Tool`-typed connections, and any component with `tool_mode` enabled can wire directly into it. The toolbar has an explicit "Tool Mode" toggle for any node whose template supports it, which mutates the backend template's `tool_mode` value.

### Multi-agent workflow patterns (from starter projects)
The wiki documents several concrete multi-agent compositions built purely from wiring `Agent` nodes and tool-providing components together in the visual graph — no separate "multi-agent framework," just graph topology:
- **Sequential chain**: `Agent1.response → Agent2.input_value → Agent3.input_value → ChatOutput`. Each agent has a distinct `system_prompt` (from a connected `Prompt` component) establishing its role (e.g. Research, Finance, Writer).
- **Aggregator pattern**: a terminal `Prompt` node with `custom_fields` (e.g. `research_agent_output`, `finance_agent_output`) receiving connections from multiple upstream agents simultaneously — a fan-in join point that synthesizes several specialized agents' outputs into one final context before a last agent or output node.
- **Agent-to-structured-data**: `Agent → StructuredOutput (dataframe_output: Table) → ParserComponent (back to Message)` — lets a free-form conversational agent's response be coerced into a structured table, then re-serialized to text for display.
- **Iterative loop over a dataset**: `DataSource (Table) → LoopComponent → Parser → LLM → back to LoopComponent → done (Table) → Output` — the `LoopComponent` explicitly manages stepwise iteration over a collection, feeding one item at a time to downstream processing and accumulating results, using the same cycle-detection/`MAX_CYCLE_APPEARANCES` machinery described above.
- **Tool-augmented single agents**: an agent wired to a `TavilySearchComponent`, `AgentQL` (web data extraction), `YouTubeTranscripts`, or `CalculatorComponent` via `component_as_tool` outputs — the same tool-mode mechanism regardless of what the underlying component actually does.

## Key patterns & techniques (transferable)

1. **Store component source as evaluated text, not compiled code.** Persisting a component's actual Python source string (in the `code` parameter) and re-evaluating it via `eval_custom_component_code()` at flow-build time — rather than only supporting pre-registered Python classes — is what enables both live in-UI code editing and AI-generated components. The tradeoff is an explicit security boundary requirement: tweaks/overrides must be blocked from touching that `code` field (a concrete injection-prevention rule worth replicating in any system that stores executable-source-as-data).
2. **`tool_mode` as a universal, opt-in "make this a tool" flag rather than a separate tool-authoring API.** Any component can become agent-callable by exposing a `component_as_tool` output — no parallel tool-definition schema to maintain. This maximizes reuse of an existing component library for agentic tool-calling, similar in spirit to AutoGPT's orchestrator-block-as-tool-source pattern but implemented as a per-component output toggle rather than an auto-derived function signature.
3. **Deterministic, hash-verified build artifacts for a component registry.** Sorting keys recursively, stripping volatile fields, and computing a SHA256 over the final JSON gives git-friendly diffs and a tamper/corruption check — a reusable pattern for any generated registry/manifest that needs to be both human-reviewable in version control and programmatically verifiable.
4. **Version-hash history for detecting stale saved artifacts.** `stable_hash_history.json` mapping component-name → per-version code hash lets the system compare a saved flow's embedded component hash against the current registry and flag "this component has changed since you saved" — a lightweight drift-detection mechanism applicable to any system where user-saved configurations reference versioned, evolving building blocks.
5. **Two execution modes sharing one core mechanism, differing only in event granularity.** Interactive Build (per-vertex SSE events) and Programmatic Run (whole-graph blocking/streaming) both bottom out in the same `instantiate_class`/`build_component` machinery — the UI-friendly incremental-feedback mode and the API-friendly single-call mode are not two separate execution engines, just two different event-emission granularities wrapped around the same vertex-build function. Worth considering for any system serving both an interactive UI and a programmatic API from one execution core.
6. **Explicit vertex state machine with reactivation, not just terminal success/failure.** Modeling `ACTIVE ⇄ INACTIVE` and `ERROR → ACTIVE` transitions (rather than one-shot pass/fail) supports both conditional branching (a node can become inactive and later active again based on upstream logic) and retry-after-fix workflows within the same state model.
7. **Bounded cycle iteration via an explicit appearance-count cap, not a hard DAG requirement.** Rather than forbidding cycles outright (simpler but limits iterative agent patterns) or allowing unbounded loops (dangerous), tracking per-cycle appearance counts against a `MAX_CYCLE_APPEARANCES` constant is a pragmatic middle ground for visual workflow tools that want to support genuine iteration (e.g. "process each item in this list") without risking runaway execution.
8. **Type-coercion at the edge-parameter layer, not pushed onto every component author.** Automatically coercing framework-native wrapper types (`Message`, `Data`) down to plain strings when connecting into a `str`-typed input means component authors don't need to defensively unwrap every possible upstream type — the coercion lives once, centrally, in `ParameterHandler`.
9. **Aggregator/fan-in via a template with named custom fields, not a special "join" node type.** Using an ordinary `Prompt` component whose `custom_fields` are populated by multiple upstream connections is a lightweight way to implement multi-source synthesis without inventing a dedicated join/merge node type — the join semantics live entirely in how the template renders its accumulated inputs.

## Practical how-tos

- **Build a sequential multi-agent chain**: connect `Agent1.response → Agent2.input_value` (Message type), give each agent a distinct `Prompt` component wired to its `system_prompt` input, terminate with `ChatOutput`.
- **Aggregate multiple agents' outputs into one final synthesis**: wire each agent's `response` output into distinct named `custom_fields` on a shared downstream `Prompt` component, then feed that prompt into a final agent or directly to output.
- **Give an agent access to a tool**: enable `tool_mode` on the tool-providing component (search, calculator, vector store, custom API wrapper), then connect its `component_as_tool` output into the `Agent` node's tool input port.
- **Iterate over a dataset with an agent/LLM per item**: feed a `Table`/dataframe-producing component into a `LoopComponent`, route its per-item output through parsing/LLM components, and loop the result back into the `LoopComponent` until `done`.
- **Inject dynamic values into a flow at run time without editing the saved flow**: use the `tweaks` parameter on `/run/{flow_id_or_name}` — a `dict[str, dict]` of node-ID → field-override; note this cannot override the `code` field.
- **Debug component drift after an upgrade**: compare a saved flow's embedded component hash against `stable_hash_history.json` to see if the component definition changed since the flow was last saved.
- **Serve a flow as an MCP tool or standalone executor without the full platform**: use the `lfx` package directly — it contains the Graph Engine and Component Registry independent of `langflow-base`'s full FastAPI/DB/service stack.

## Gotchas & caveats

- **Component `code` fields cannot be overridden via tweaks** — this is a deliberate security control, not an oversight; any integration expecting to dynamically swap a component's actual logic via the tweaks API at run time will find that path blocked by design.
- **Component instantiation involves runtime `eval()` of stored Python source on every flow build** — this is fundamental to Langflow's customization model but means the security posture of a Langflow deployment depends heavily on who can author/edit flows and components; treat flow-authoring permissions with the same care as code-deployment permissions.
- **Secret resolution falls back to environment variables only if `fallback_to_env_vars=True`** — a flow relying on this fallback in one deployment (e.g. local dev) may fail to resolve credentials in another (e.g. production with strict DB-only variable resolution) if that flag differs across environments.
- **Cycles are capped by `MAX_CYCLE_APPEARANCES`, not user-configurable per-flow** (per what's described) — a legitimately long-running iterative pattern (e.g. processing thousands of dataset rows via `LoopComponent`) could hit this global iteration ceiling; check the actual constant value before designing loop-heavy flows.
- **Interactive Build mode caches the in-progress `Graph` object in `ChatService`** — meaning build state has a server-side memory footprint tied to the playground session, distinct from the stateless-per-call nature of Programmatic Run mode.
- **Legacy `CustomComponent` (bare `build()` method) and modern `Component` (`build_results()`) classes are dispatched through entirely different code paths** (`build_custom_component()` vs `build_component()`) — a component migrated from the old base class to the new one needs to actually change which lifecycle method it implements, not just its parent class name.
- **Artifact type detection (`get_artifact_type()`) determines UI rendering (table/image/text)** — a custom component returning data in an unexpected shape may render incorrectly in the UI even if the underlying computation succeeded, since rendering is driven by a separate type-inference step from the actual result.
