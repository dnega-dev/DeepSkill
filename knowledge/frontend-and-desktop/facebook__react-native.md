# facebook/react-native — Distilled Knowledge

## What it is

React Native is a framework for building native mobile applications using React and JavaScript, rendering to platform-native views (Android `ViewGroup`/`View`, iOS `UIView`) rather than web views or a WebView. The JS runtime is Hermes (default) or JavaScriptCore. The repo (Yarn workspaces, root version `1000.0.0` dev-only, published packages track `0.87.0-main`) is organized as: `Libraries/` (shared JS), `ReactAndroid/` (Java/Kotlin + JNI), `React/` + `ReactApple/` (iOS Objective-C/Objective-C++), `ReactCommon/` (shared C++ core: JSI, Fabric renderer, Yoga layout engine), and `scripts/` (build/release automation). Companion packages: `@react-native/codegen` (spec-to-native-code generation), `@react-native/metro-babel-transformer` + `@react-native/babel-preset` (JS transform for Metro), `@react-native/dev-middleware` + `@react-native/debugger-frontend` (dev server / Chrome DevTools integration), `@react-native/community-cli-plugin`.

The framework is mid-transition from a legacy **Bridge** architecture to the **New Architecture**, and the wiki documents both simultaneously since they coexist and are individually feature-flagged.

## Architecture (how it's built, key components)

**Two communication models.** Legacy: `MessageQueue` serializes calls to JSON and ships them across an async-only bridge (`CatalystInstance`); native modules come from a `NativeModules` registry. New: **JSI** (JavaScript Interface), a lightweight C++ API (`jsi::Runtime`, `jsi::Value`, `jsi::Object`, `jsi::Function`, `jsi::HostObject` — a C++ object whose property access triggers C++ method calls) that lets JS engines embed directly into C++ applications with synchronous or async calls, no serialization required. `jsi::HostObject` is the mechanism by which native functionality (TurboModules, the Fabric UI manager) is exposed as a plain JS object.

**Runtime lifecycle — two parallel systems.** Legacy: `ReactInstanceManager` (deprecated — as of the wiki snapshot it's `@LegacyArchitecture`-annotated and its context-creation path throws `UnsupportedOperationException`) manages a `CatalystInstance`; thread-safe singleton with a background thread for context creation, lifecycle states `BEFORE_CREATE`/`BEFORE_RESUME`/`RESUMED`. New: `ReactHost` (an interface, not a concrete class) manages a single `ReactInstance` in Bridgeless mode — task-based API (`TaskInterface<T>`) for `start()`/`reload()`/`destroy()`, decoupled from Activity lifecycle (Activity can be null), supports multiple rendering surfaces via `createSurface()`. The choice between the two is made once, in `ReactActivityDelegate.onCreate()`, gated on `ReactNativeNewArchitectureFeatureFlags.enableBridgelessArchitecture()`. `ReactContext` is the shared abstraction (extends Android's `ContextWrapper`) providing `getJSModule`/`getNativeModule`, three `MessageQueueThread`s (UI, native-modules, JS), and lifecycle event dispatch; `BridgeReactContext` (legacy) and `ThemedReactContext` both extend it, and in Bridgeless mode a `BridgelessReactContext` overrides `getCatalystInstance()` to throw, and a `BridgelessCatalystInstance` shim throws `UnsupportedOperationException` for legacy bridge methods like `runJSBundle()` — deliberately preventing any code path from silently depending on the removed bridge.

**New Architecture — three interdependent pillars**, all controlled by feature flags that must agree (`DefaultNewArchitectureEntryPoint` overrides defaults to force `enableBridgelessArchitecture` and `useTurboModuleInterop` true together):
1. **TurboModules** — lazy-loaded native modules (not instantiated until first JS access), supporting synchronous method calls, replacing the eagerly-registered `NativeModules`. Flow: JS makes a JSI call → C++ `TurboModuleManager` → platform-specific manager (Android: Java `TurboModuleManager` → `TurboModuleManagerDelegate.createModule()`; iOS: `RCTTurboModuleManager` → `RCTInteropTurboModule` for legacy-ObjC interop, which dynamically parses ObjC method signatures/argument types to bridge JSI calls into ObjC method invocations).
2. **Fabric** — the C++ rendering engine; moves layout (Yoga) and the Shadow Tree into C++ so UI commits can be synchronous. `FabricUIManager` (native side) + `ComponentFactory` (registers native component providers) + `EventBeatManager` (synchronizes JS event loop with native UI frame timing).
3. **Bridgeless Mode** — the end state where the legacy bridge (`RCTBridge`/`CatalystInstance`) is fully removed; JS talks to native exclusively through JSI.

**Fabric rendering pipeline (three phases: Commit → Layout → Mount).** Core data structure: the **Shadow Tree**, a C++ mirror of the React component tree, scoped per `SurfaceId`, built from immutable `ShadowNode`s (any change clones a new node — `ShadowNode.cpp`). A `ShadowNodeFamily` tracks the "lineage" across clones, owning the shared `EventEmitter` and most-recent `State` so identity survives repeated cloning. `ComponentDescriptor` is the per-component-type (View, Text, ScrollView, ...) factory: creates initial Props/State, clones nodes/props, manages child appending.
- *Commit*: triggered by JS (via `UIManagerBinding`) or a native state update; `UIManager` creates/clones `ShadowNode`s and proposes a new root via a Transaction against the `ShadowTree`; hooks can intercept/modify the tree before it's finalized.
- *Layout*: **Yoga** (the Flexbox layout engine, itself part of this repo under `yoga/`) computes geometry — dimensions, padding, margins — respecting parent size constraints (`constrainMaxSizeForMode`); a `YogaLayoutableShadowNode` is the `ShadowNode` subclass that owns and syncs a `yoga::Node`.
- *Mount*: `Differentiator.cpp`'s `calculateShadowViewMutations` diffs the old and new tree (`oldChildPairs` vs `newChildPairs`) to produce a mutation list (Create/Update/Insert/Remove/Delete), including "flattening/unflattening" — nodes optimized out of, or reintroduced into, the *native* view hierarchy even though they remain in the shadow tree (an optimization to avoid unnecessary native view nesting). `MountingCoordinator` then hands the mutation list to the platform as a `MountingTransaction`.

`Scheduler` is Fabric's entry point: it initializes `UIManager`, sets up the `ComponentDescriptorRegistry`, and installs `UIManagerBinding` — a JSI `HostObject` exposed to JS as the global `nativeFabricUIManager` — as the JS-callable surface for the whole renderer. Native events (touch, scroll) flow the opposite direction through the same binding via `dispatchEvent`/`dispatchEventToJS`, with a `PointerEventsProcessor` able to intercept pointer events specifically.

**View Manager system (JS component ↔ native view bridge).** `ViewManager` (abstract base) defines `createView`/`updateProperties`/`getName`; `BaseViewManager` adds common cross-component properties (backgroundColor, opacity, transform, accessibility) and view recycling (`prepareToRecycleView` resets tags/animations/listeners before pushing the view onto a `mRecyclableViews` stack for reuse — avoids reallocating native views on every mount/unmount); `ReactViewManager` is the concrete `<View>`/`"RCTView"` implementation. `ViewManagerDelegate` maps prop names to setter methods (`setProperty`) instead of manual per-prop parsing inside the manager. Android's `ReactViewGroup` backs `<View>` and separately implements `ReactClippingViewGroup` (for `removeClippedSubviews`) and `ReactPointerEventsView` (pointer-events + hitSlop).

**View Transitions.** A `ViewTransitionModule` implements a `MountingOverrideDelegate` to intercept the normal mounting flow: `applyViewTransitionName` captures a view's layout metrics (origin, size, scale) as a snapshot; `createViewTransitionInstance` builds a temporary pseudo-`ShadowNode` that visually mimics the old view using the captured metrics, letting Fabric animate between old and new states as a declarative transition rather than an imperative animation API.

**Codegen (build-time spec-to-native-code pipeline).** A `SchemaType` intermediate representation (`libraryName` + a `modules` map of `ComponentSchema`/`NativeModuleSchema`) sits between hand-written JS/TS/Flow specs and generated native code. `ComponentShape` captures a Fabric component's `extendsProps`/`events`/`props`/`commands`; `NativeModuleSchema` captures a TurboModule's `aliases`/`enums`/`properties`. Type-specific generators consume the schema: `GeneratePropsCpp.js` emits C++ prop structs plus a `getDiffProps` for optimized prop-diffing; `GenerateModuleH.js` emits the C++ `CxxSpec` header a native module must inherit from, including a `methodMap_` that links JSI call names to native implementations; `GenerateModuleJavaSpec.js` emits the Android Java interface; `GenerateModuleJniCpp.js` emits the JNI glue between C++ and Java. The `generate-artifacts-executor` orchestrates this at build time (invoked from Gradle on Android, CocoaPods on iOS): it discovers codegen-enabled libraries by scanning `package.json`/`react-native.config.js` for a `codegenConfig` field, generates a `ReactCodegen.podspec` on iOS listing all discovered JS spec files as build inputs, and ensures `@react-native/codegen` itself is built before invoking the generators (`buildCodegenIfNeeded`). The overall build pipeline is three stages: (1) codegen (specs → generated C++/JNI/ObjC++ bindings), (2) Metro bundling (JS source → Babel transform via `@react-native/metro-babel-transformer`/`@react-native/babel-preset` → JS bundle), (3) native compilation (CMake on Android, Xcode on iOS) consuming the generated bindings — the JS bundle is packaged into the final AAR/APK or `.app` alongside the compiled native code.

## Key patterns & techniques (transferable knowledge)

- **Immutable tree + cloning for concurrent-safe UI state.** `ShadowNode` is immutable; every change produces a new node cloned from the old one. Combined with a stable `ShadowNodeFamily` identity that survives repeated clones, this is the same "double buffering via structural sharing" idea used elsewhere for safe concurrent tree mutation — you can build a new tree while the old one is still being read/rendered, and only swap at commit.
- **Three-phase pipeline (propose → measure → apply) for any UI renderer.** Commit (propose new logical tree) → Layout (compute geometry against constraints) → Mount (diff against previous tree, translate to a minimal mutation list, apply to the real platform surface) generalizes beyond React Native to any system translating a declarative description into imperative platform operations.
- **Structural flattening as a native-view-count optimization.** The differentiator can drop nodes out of the *native* hierarchy (while keeping them in the *shadow* hierarchy) when they contribute nothing visually distinct, and reintroduce them later — decoupling "logical tree shape" from "native view count" is a reusable technique for minimizing expensive native object allocation in any tree-to-native-widget renderer.
- **Delegate objects to route generic base logic to specific handlers.** `ViewManagerDelegate.setProperty` maps prop names to setters instead of each `ViewManager` subclass hand-writing a prop-parsing switch statement — same delegation idea as a plugin/handler registry, applied to prop application.
- **JSI HostObject as the "one FFI boundary" pattern.** Rather than many bespoke bridges, expose native capability as a single JS-visible `HostObject` (here, `nativeFabricUIManager`) whose property/method access dispatches into C++ — this collapses "N different native APIs" into "one object with N members," simplifying the JS-native seam to a single well-typed contract.
- **Feature-flag-gated dual implementations kept live simultaneously.** Both the legacy Bridge and the New Architecture ship in the same binary at once, selected by a single flag check at one call site (`ReactActivityDelegate.onCreate()`), with interop shims (`RCTInteropTurboModule`, Fabric-interop flags) letting old-style modules/components keep working under the new system during migration — a concrete pattern for staged migrations of foundational infrastructure without a flag-day cutover.
- **Deliberately breaking the old path once the new path is default**, not just deprecating it silently: `BridgelessReactContext`/`BridgelessCatalystInstance` throw hard exceptions on legacy-bridge method calls rather than silently no-opping — this surfaces migration bugs immediately instead of letting them hide as silent no-ops.
- **Schema-as-IR for multi-target codegen.** A single `SchemaType` intermediate representation is generated once from JS/TS specs, then fanned out to N independent generators (C++, Java, JNI, ObjC++) — the standard "one IR, many backends" compiler pattern, applied to cross-language native-module/component bindings instead of a general-purpose language.
- **View recycling pool to amortize native object construction cost.** `prepareToRecycleView` resets a view's mutable state and returns it to a reuse stack instead of destroying it — the same object-pool technique used in game engines and virtualized list UIs, applied at the native-view layer.

## Practical how-tos

- **Determining which architecture an app is running under**: check `ReactNativeNewArchitectureFeatureFlags.enableBridgelessArchitecture()` — this single flag decides whether `ReactActivityDelegate` constructs a `ReactHost`-backed (Bridgeless) or `ReactNativeHost`-backed (Bridge) delegate.
- **Debugging why a legacy native module doesn't work under the New Architecture**: check whether `useTurboModuleInterop()` is enabled and, on iOS, inspect `RCTInteropTurboModule`'s method-signature parsing — it dynamically bridges ObjC method signatures to JSI calls and mismatches here are a common interop failure point.
- **Debugging an unexpected native view hierarchy (extra or missing native views vs. the JSX tree)**: check the Differentiator's flattening/unflattening behavior — some logical shadow nodes are deliberately not materialized as native views.
- **Adding a new Fabric component's native prop**: trace through `SchemaType`/`ComponentShape` → `GeneratePropsCpp.js` (C++ prop struct + `getDiffProps`) → the platform `ViewManager`/`ViewManagerDelegate.setProperty` mapping — new props typically require regenerating codegen artifacts, not just editing platform code by hand.
- **Diagnosing "codegen didn't pick up my new library"**: the `generate-artifacts-executor` only discovers libraries with a `codegenConfig` field in `package.json` or `react-native.config.js` — verify that field exists and is well-formed before checking generator output.
- **Investigating a view-transition animation bug**: check the `ViewTransitionModule`'s three-step flow — snapshot capture (`applyViewTransitionName`) → pseudo-element creation (`createViewTransitionInstance`) → `MountingOverrideDelegate` intercepting the mounting transaction; a broken transition often traces to a stale or missing layout-metrics snapshot.

## Gotchas & caveats

- `ReactInstanceManager` (legacy) is not just deprecated but actively broken in this snapshot — its context-creation path throws `UnsupportedOperationException`; code still targeting it directly will fail, not just emit a warning.
- `BridgelessReactContext.getCatalystInstance()` and `BridgelessCatalystInstance`'s legacy methods throw hard exceptions rather than returning null/no-op — any code (including third-party libraries) that defensively calls legacy bridge APIs "just in case" will crash under Bridgeless mode instead of degrading gracefully.
- New Architecture feature flags are interdependent by design (Bridgeless requires TurboModule interop to be true) — flipping one flag without checking the others' required states can produce an inconsistent, partially-migrated runtime.
- Shadow tree flattening means the native view hierarchy is NOT a 1:1 mirror of the shadow/JS component tree — tooling or debugging code that assumes structural parity between the two will misreport view relationships.
- `ShadowNode` immutability means holding a reference to a node across a commit gives you a stale snapshot, not a live view — always re-fetch through the current `ShadowNodeFamily` rather than caching a `ShadowNode*` across renders.
- Codegen artifacts are a build-time dependency: `buildCodegenIfNeeded` must run and `@react-native/codegen` must be compiled before the generators execute — build-order/caching issues in custom build setups can silently use stale generated bindings.
- View recycling means a `ViewManager`'s `prepareToRecycleView` must fully reset all mutable state (tags, animations, listeners) — anything left behind will leak into the next component instance that reuses the pooled native view.
