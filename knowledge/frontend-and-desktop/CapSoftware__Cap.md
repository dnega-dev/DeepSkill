# Cap (CapSoftware/Cap) — DeepWiki Knowledge Distillation

## What it is

Cap is an open-source screen recording and video sharing platform for creating and sharing screen recordings. It consists of two coordinated applications: a Tauri (Rust + SolidJS) desktop app that handles screen/camera/audio capture, real-time GPU-accelerated video editing, and local export to MP4/GIF; and a Next.js (React + Effect-TS) web app that provides shareable-link video hosting, AI transcription/summarization, team collaboration, and analytics. Two recording modes: **Instant Mode** (uploads segments while recording, for immediate sharing) and **Studio Mode** (records locally first for high-quality editing before upload/export). Users can configure custom S3-compatible storage (AWS S3, R2, MinIO) to own their media.

## Architecture

**pnpm/Turborepo monorepo** split into `apps/desktop` (Tauri+SolidJS), `apps/web` (Next.js 15+/Effect), shared TypeScript packages (`@cap/database` Drizzle ORM, `@cap/web-backend` Effect services, `@cap/web-domain` domain models, `@cap/web-api-contract`/`@cap/web-api-contract-effect` type-safe API definitions, `@cap/ui-solid`), and a Rust workspace under `crates/` (`recording`, `rendering`, `editor`, `export`, plus platform-specific encoder/decoder crates like `enc-avfoundation`, `enc-ffmpeg`, `enc-mediafoundation`, `video-decode`, `frame-converter`). The desktop app owns all compute-intensive media operations locally; the web app owns cloud services (hosting, AI, auth, billing).

**Recording pipeline is a trait-based, type-state-programmed Rust builder** (`crates/recording/src/output_pipeline/core.rs`). `VideoSource`/`AudioSource` traits abstract capture backends (screen via `scap-direct3d`/`scap-screencapturekit`, camera, system-audio loopback, microphone); a `Muxer` trait hierarchy (with `VideoMuxer`/`AudioMuxer` sub-traits) abstracts output writers (`AVFoundationMp4Muxer` and `MacOSFragmentedM4SMuxer` on macOS, FFmpeg-based muxers elsewhere). `OutputPipelineBuilder<TVideo>` uses Rust's type-state pattern — `NoVideo` vs `HasVideo<TVideo>` marker types — so the compiler statically prevents constructing an audio-only pipeline with video-specific configuration; `with_video()` transitions the type, and `build::<TMuxer>()` is only callable once the required sources are attached. A `TaskPool` spawns and names every async/thread task (video encoder, audio mixer, capture source, muxer writer) and monitors them for failure, funneling any task's error into a single `done_tx` channel.

**Audio/video timestamp synchronization has multiple explicit correction layers**: a `TimestampAnomalyTracker` detects and corrects three anomaly classes (backward jumps from clock skew/frame reordering, large forward jumps from system sleep/wake, and excessive consecutive anomalies signaling an unhealthy stream — hard-coded thresholds: 60 consecutive anomalies triggers an error, 1.0s backward / 2.0s forward jump thresholds). A `VideoStartGate` buffers/trims audio frames until the first video frame's timestamp is known, so A/V start together (within a 500ms `AV_START_ALIGNMENT_LIMIT_NS` trim window). Pause/resume support has two complementary trackers: `SharedPauseState` adjusts frame timestamps by subtracting accumulated paused duration, while `SharedWallClockPause` separately tracks total pause duration for wall-clock calculations. Audio timestamps, unlike video's captured wall-clock timestamps, are generated purely from cumulative sample counts (`AudioTimestampGenerator`) for exact synchronization.

**Rendering/decoding is a multi-backend GPU pipeline built on `wgpu`**. Decoders (`AVAssetReader` on macOS/AVFoundation, `MediaFoundation` on Windows/DXVA, FFmpeg hardware wrappers via D3D11VA/VideoToolbox, and a pure-software FFmpeg fallback) feed a `DecoderPoolManager` that caches ~30-60 decoded frames (`FRAME_CACHE_SIZE`) for smooth editor scrubbing without full re-decode, using presentation-timestamp-to-frame-number mapping and a `ScrubDetector` that adjusts decode priority when rapid seeking is detected. Frames flow through composable `RendererLayers` (`BackgroundLayer`, `DisplayLayer` for the screen capture, `CameraLayer` for the webcam overlay with background-blur support, `CursorLayer` rendering SVG-rasterized or circle cursors with interpolation) into a `CompositeVideoFramePipeline` that runs a WGSL compute shader (`composite-video-frame.wgsl`) to produce the final RGB composite, then a `YuvToRgbaConverter`/`RgbaToNv12Converter` pair converts color spaces on the GPU (avoiding CPU readback where possible — on Windows the converter can consume `ID3D11Texture2D` handles directly from the decoder).

**Live preview streams rendered frames to the SolidJS UI over a local WebSocket**, not shared memory or a native window handle: `pack_ws_frame` serializes raw pixel bytes (RGBA or NV12) plus a fixed trailing metadata footer (stride, height, width, frame number, target time in ns, and an optional NV12 magic number `0x4e563132`) into one binary message. The frontend receives this in a Web Worker (`frame-worker.ts`) to avoid blocking the UI thread, optionally using a zero-copy `SharedArrayBuffer` path (`SharedFrameBuffer`) when supported, and renders via WebGPU onto an `OffscreenCanvas`.

**The editor backend (`EditorInstance`) and export system share the same rendering core** but diverge downstream: the editor streams composited frames over WebSocket for live preview (with a `Playback` loop that prefetches decoded frames into an LRU cache and runs parallel decode tasks to sustain 60fps scrubbing/playback), while export writes composited, YUV-converted frames to a `SharedNv12Buffer` that's handed to format-specific encoders (`crates/export/src/mp4.rs` via FFmpeg/MediaFoundation H.264/HEVC with AAC audio; `crates/export/src/gif.rs` via the `image` crate with GIF palette generation, video-only). Cursor position and zoom level are interpolated frame-by-frame using a **spring-mass-damper simulation** (`crates/rendering/src/spring_mass_damper.rs`) rather than linear/eased tweening, to produce physically fluid-feeling camera and cursor motion.

## Key patterns & techniques

**Windows export runs out-of-process specifically to isolate GPU-driver/MediaFoundation crashes from the main app**: `begin_export_session` increments a global atomic guard, then `run_out_of_process_export_attempt` spawns the Cap executable itself with an `export` subcommand as a sidecar process; the sidecar streams JSON progress messages (`Progress`, `Completed`) over stdout back to the parent, which parses and forwards them to the UI. If hardware-accelerated export fails inside the sidecar, the system automatically retries the same export in a `SoftwareSafe` mode — a documented crash-recovery fallback rather than a hard failure.

**Segmented/fragmented output for long recordings and progressive upload**: instead of one monolithic MP4, the pipeline can write DASH-style segments (`init.mp4` + numbered `segment_NNN.m4s` files + a `dash_manifest.mpd`) via an FFmpeg DASH muxer context, with a versioned JSON segment manifest (`version`, `manifest_type` = "video"/"audio", `init_segment` path, `segments[]`) written atomically after each segment completes — this both prevents single-file corruption on crash and enables uploading a recording while it's still being captured (the basis of Instant Mode). A `RecoveryManager` scans project directories on startup for incomplete recordings and attempts to concatenate the available fragments into a playable result.

**Frame-drop and channel-pressure health monitoring feeds directly into UI-visible events**: a `FrameDropTracker` flags `PipelineHealthEvent::FrameDropRateHigh` when drops exceed 5% over a 5-second window; a `ChannelPressureTracker` logs a warning when an internal channel reaches 80% capacity; a `VideoStartGate` has a 500ms wait-with-timeout after which it lets audio start without gating on video (avoiding an indefinite stall if video capture is slow to produce its first frame). Disk space is actively monitored during macOS recording with two thresholds (500MB minimum to start, 200MB critical during recording) to preempt silent write failures.

**Three parallel type-safety layers bridge desktop, web frontend, and web backend**, each suited to a different integration surface: `@cap/web-api-contract` (Zod schemas consumed via `ts-rest`, the primary contract the desktop app's `apiClient` uses against protected/public REST endpoints like `getS3Config`); `@cap/web-api-contract-effect` (Effect `HttpApi` groups with middleware-based auth injection, used by newer Effect-native web routes); `@cap/web-domain` (Effect `Schema`-based domain entities and `@effect/rpc` definitions, e.g. a `Video` class that is the single source of truth for video shape across the whole stack, including branded ID types and `Option`-wrapped optional fields like `transcriptionStatus`). Repositories use `decodeSync` to validate raw database rows into these domain schemas before they enter application logic, and domain errors are modeled as `TaggedError` subclasses (`NotFoundError`, `VerifyVideoPasswordError`, `RecursiveDefinitionError`) rather than generic exceptions, enabling exhaustive type-tag-based error handling.

**Native FFmpeg dependencies are platform-specific pre-built binaries fetched and prepared by a setup script, not compiled from source or fetched via a package manager**: on macOS, `scripts/setup.js` downloads a pre-built `Spacedrive.framework` tarball (from the Spacedrive project's `native-deps` releases, per-architecture) containing FFmpeg + related libs, trims unused libraries to reduce bundle size, and code-signs every `.dylib` individually (macOS 13+ requires this) using `APPLE_SIGNING_IDENTITY` or ad-hoc `-` signing for local dev, before copying into both `target/Frameworks/` (for bundling) and `target/debug/` (for runtime discovery during development). On Windows, it downloads an official FFmpeg 7.1 "shared" build from `GyanD/codexffmpeg`, splits it into DLLs (→ `target/debug`/`target/release`) versus headers+libs (→ `target/native-deps/`), and separately locates `libclang.dll` via Visual Studio's `vswhere.exe` for Rust FFI bindgen, writing the result into `.cargo/config.toml`.

**Two-stage code signing pipeline differs materially by platform**: macOS needs library signing (setup script) + application signing (Tauri, via `APPLE_CERTIFICATE`) + separate notarization (App Store Connect API keys) — three distinct steps. Windows needs Authenticode signing of the unsigned installer via a third-party service (SignPath) followed by a *second*, unrelated re-signing pass using Tauri's own private key (`TAURI_SIGNING_PRIVATE_KEY`) purely to produce the `.sig` file the auto-updater needs — i.e. the artifact that satisfies Windows SmartScreen and the artifact that satisfies Tauri's updater are signed independently with different keys for different purposes.

**Hardware video encoding falls back gracefully through a preference chain**: `H264EncoderBuilder` tries hardware encoders first (`h264_videotoolbox` on macOS, `h264_nvenc`/VCE-equivalent elsewhere) before falling back to software encoding, and a `resolution_limits` module pre-computes GPU-compatible dimensions (forcing even width/height, capping at platform maximums like 4096px) specifically to avoid encoder initialization failures that would otherwise surface as opaque runtime errors deep in the FFmpeg/MediaFoundation call stack.

## Practical how-tos

- **Trace an A/V sync bug**: check whether `TimestampAnomalyTracker` logged a backward/forward jump anomaly near the affected timestamp, and separately verify the `VideoStartGate` didn't time out (500ms) waiting for the first video frame — a gate timeout means audio started before video was ready, which is a distinct failure mode from a mid-stream anomaly.
- **Add a new video/audio capture source**: implement the `VideoSource` or `AudioSource` trait (`setup`, `video_info`/`audio_info`, `start`, `stop`) and register it through the builder's generic `with_video<TVideo>()`/`with_audio_source<TAudio>()` methods — the type-state builder ensures you cannot forget to attach video before calling `build()` if a `HasVideo` bound is required downstream.
- **Diagnose a crash during export on Windows**: check whether the export ran out-of-process (it should, by design) and whether the sidecar's JSON stdout stream reported a `SoftwareSafe` fallback retry — a fallback retry succeeding means the failure was a hardware/driver issue, not a logic bug.
- **Update the bundled FFmpeg version**: on Windows, update the `GyanD/codexffmpeg` release reference in `scripts/setup.js`; on macOS, coordinate with the upstream `spacedriveapp/native-deps` release version, since Cap consumes a pre-built framework rather than building FFmpeg itself.
- **Add a new domain entity shared between desktop and web**: define it in `@cap/web-domain` using Effect `Schema` (branded IDs, `Option` for nullable fields) so both the Effect-based web backend and any RPC consumers get compile-time and runtime validation from the same definition, rather than duplicating a shape in Zod (`web-api-contract`) and a separate TS interface.

## Gotchas & caveats

- The type-state builder pattern for `OutputPipeline` means a compile error, not a runtime error, is the first sign of a missing video/audio source — if a pipeline fails to build, check the generic type parameters (`NoVideo`/`HasVideo<T>`) before assuming a logic bug in `setup()`.
- GIF export has no audio support at all (video-only) — this is a hard format limitation, not a missing feature to be added later per the wiki's phrasing.
- The two Windows code-signing passes (SignPath Authenticode vs Tauri updater signing) serve entirely different consumers (OS trust vs auto-updater trust) — resigning for one does not satisfy the other, and both must succeed independently for a release to be both installable without SmartScreen warnings and auto-updatable.
- Segment manifests are versioned (`version` field, currently 5 per the wiki) — a manifest reader must handle version skew if recovering old incomplete recordings after a schema change.
- The desktop app has three different type-contract systems in play simultaneously (`web-api-contract` Zod, `web-api-contract-effect` Effect HttpApi, `web-domain` Effect Schema/RPC) that are not fully unified — new endpoints should be checked against which system the target route family already uses rather than assumed to follow one project-wide convention.
- Native FFmpeg dependency setup (`pnpm cap-setup`) is a required, separate step before building the desktop app — standard `cargo build`/`pnpm install` alone will not fetch or place the platform-specific FFmpeg binaries.
